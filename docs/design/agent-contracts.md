# Контракты агентов

Дата: 2026-08-04. Статус: после дополнительного ревью исправлен недостижимый
`cap_exhausted_new`, а владелец закрыл защищённый выбор Q44 строгой границей
`reaffirmed_closed` и выбрал B в Q45 для follow-up observations. Контракты
содержательно закрыты, включая запрет follow-up при закрывающем решении;
Q46 требует полного списка одновременных споров в одном вопросе и одного
кампанийного действия в ответе. Реальным рантаймом не проверены.

Что рантайм даёт агенту на вход и что обязан получить на выходе. Всё, что не
проходит валидацию здесь, — `contract_error`: попытка не состоялась, счётчики
капа не двигаются, тратится `contract_retry_budget`.

Документ важен не формой, а списком проверок: **контракт findings стоит на том,
что модель точно ссылается на ID**, и каждая непроверенная вольность в формате
превращается в потерянное замечание.

---

## 1. Транспорт

### 1.1. Как возвращается результат

Через **stdout**, обрамлённый уникальными маркерами:

```
<<<METASWARM-RESULT-BEGIN>>>
{"schema": "review.observations.v1", ...}
<<<METASWARM-RESULT-END>>>
```

Не fenced-блок ` ```json `, хотя это было бы привычнее. Причина конкретная:
ревьюер приводит фрагменты кода в `evidence`, и среди них законно встречается
JSON — тогда «найти json-блок в ответе» становится угадыванием. Маркер такой
формы в исходном коде не встречается.

Правила разбора:

- маркеры должны встретиться **ровно по разу**; ноль или два — `contract_error`;
- всё вне маркеров игнорируется: рассуждения модели до и после — это норма, а не
  нарушение;
- содержимое между маркерами обязано быть одним JSON-object не больше
  `1 MiB` в UTF-8; массив/scalar на верхнем уровне, duplicate keys и любое
  non-finite число — как явные `NaN`/`Infinity`, так и переполнение обычного
  литерала `1e999` — `contract_error`;
- финальный вывод извлекается адаптером (`extract_result()`), а не чтением
  сырого stdout: у каждого вендора свой stream-json.

**Ревьюер ничего не пишет в файлы** — ни результат, ни черновики. Он работает в
disposable read-only checkout, и любая мутация аннулирует его вклад в кворум
(`decision.md` §9.2). Это же причина, по которой вывод идёт через stdout, а не
через файл-приёмник.

### 1.2. Версия схемы

Каждый ответ несёт `"schema": "<имя>.v<N>"`. Несовпадение с ожидаемым —
`contract_error` до всякого разбора полей. Версия схемы контракта входит в
манифест попытки вместе с `prompt_template_id + hash` и `rubric_id + hash`.

В v1 реестр закрыт восемью именами: `review.observations.v1`,
`review.reconciliation.v1`, `review.dispositions.v1`, `review.decisions.v1`,
`verification.plan.v1`, `graph.breakdown.v1`, `handoff.cutoff.v1` и
`human.question.v1`. Все модели используют строгие типы и
`extra="forbid"`: неизвестное поле или строка вместо числа не игнорируется и не
приводится. `verification.result.v1` пишет сервис, поэтому в этот реестр
ответов агента не входит.

### 1.3. Язык

Промпты, схемы и содержимое артефактов — **английский**. Тексты, адресованные
человеку (`question_text`, варианты ответа, пояснения в Telegram) — **русский**.
Это разделение проходит по полю, а не по документу: в одном и том же JSON
`title` замечания на английском, а `question_text` — на русском.

### 1.4. Ошибка валидации возвращается агенту

Повтор после `contract_error` осмыслен, только если агент видит, что именно не
прошло. В промпт повторной попытки добавляется блок:

```
PREVIOUS ATTEMPT REJECTED
  - observation #3: neither severity_suggested nor unchanged_from present
  - missing dispositions for open findings: F-12, F-19
Fix these and resend the full result. Partial results are not accepted.
```

Без такого блока три попытки подряд дают одну и ту же ошибку, а бюджет
расходуется.

## 2. Что подаётся на вход

### 2.1. Компактный ledger

Список открытых замечаний идёт в промпт компактным (`decision.md` §7.2): ID,
severity, однострочное summary из `finding.title`, статус. Полный текст и
evidence подтягиваются только для тех ID, которые агент трогает.

```
OPEN FINDINGS
  F-12  high      Race between checkpoint commit and state flush   awaiting_fix
  F-19  medium    Missing index on blocker(run_id)                  awaiting_fix
  F-23  low       Inconsistent error wording                        awaiting_fix
```

`title` — ground truth, который reconciler задаёт в `new`-группе при создании
личности. Он не переписывается между кругами намеренно: если summary плывёт,
модель видит «то же, но другими словами» — тот самый anchoring, от которого
защищает вся конструкция с выданной личностью.

**Ревьюеру в круге проверки ledger подаётся расширенным** — с идентификаторами,
на которые ему разрешено ссылаться:

```
OPEN FINDINGS (you own F-12 and F-19)
  F-12  high    last_observation=O-4-1  Race between checkpoint commit and state flush
  F-19  medium  last_observation=O-4-3  Missing index on blocker(run_id)
```

Без колонки `last_observation` поле `unchanged_from` в ответе ревьюера
**невыполнимо**: `O-*` выдаёт рантайм уже после того, как ревьюер отправил свой
слепой вывод, и агент этих ID никогда не видел — ни в промпте, ни в своей
сессии. В первой редакции контракт требовал ссылку, которую взять было неоткуда.

Ссылаться разрешено **только на показанные ID**; любой другой — `contract_error`.
Это заодно закрывает три из четырёх инвариантов `unchanged_from` (тот же
finding, тот же период, назад по времени) на уровне подачи, а не проверки:
показывается ровно то наблюдение, на которое ссылка законна.

### 2.2. Закрытые замечания — только в reconciliation

В reconciliation дополнительно подаются **закрытые** замечания тех кампаний, чей
предмет входит в предмет текущей: и принятые отказы, и `verified_fixed`
(`decision.md` §7.4).

```
CLOSED FINDINGS (same issue: reaffirm or reopen; different/uncertain issue: new)
  F-04  high   accepted_reason  reviewer  Retry budget shared across vendors
  F-07  medium verified_fixed   reviewer  Off-by-one in cap check
  F-09  high   human_decision   human     Ship without worktree isolation
```

Колонка authority показывается не для красоты: переоткрытие `human`-закрытия
всегда возвращается человеку независимо от severity, и агент должен понимать,
что предлагает.

`new` не переименовывает известный закрытый finding: он означает, что новое
observation описывает другую проблему либо reconciler не может безопасно
отождествить их. Если связь установлена, применяются только
`reaffirmed_closed`/`reopen_closed` и строгая проверка §4.

### 2.3. Чего в промпте нет никогда

- значений секретов — только `secret_ref` резолвится рантаймом в окружение;
- ledger в фазе `blind_discovery` — ни открытых, ни закрытых;
- в первом раунде кампании — выводов параллельной линии.

## 3. Ревьюер: слепая фаза

`schema: review.observations.v1`

```json
{
  "schema": "review.observations.v1",
  "observations": [
    {
      "title": "Checkpoint commit can race with state flush",
      "body": "If the service dies between git commit and the state transaction, recovery creates a second commit with identical content.",
      "file": "service/effects/git_service.py",
      "line_start": 88,
      "line_end": 104,
      "evidence": "commit() is called before store.transaction() closes",
      "severity_suggested": "high"
    }
  ]
}
```

| Поле | Обязательно | Правило |
|---|---|---|
| `title` | да | ≤ 120 символов, одна строка |
| `body` | да | ≤ 4000 символов |
| `file` | нет | Путь относительно корня checkout; должен существовать на этой ревизии |
| `line_start` / `line_end` | нет | Оба или ни одного; `line_end >= line_start` |
| `evidence` | нет | ≤ 2000 символов |
| `severity_suggested` | **да, в этой фазе** | Ровно из `low`, `medium`, `high`, `critical` |
| `unchanged_from` | **запрещено в этой фазе** | Ledger не подавался — ссылаться не на что |

Проверки, дающие `contract_error`:

1. Значение severity вне enum. **Никаких приведений «похоже на high»** — молчаливая
   подстановка здесь означает молчаливое изменение решения об эскалации.
2. Отсутствие `severity_suggested`.
3. Присутствие `unchanged_from` (см. `db-schema.md` §14, уточнение 2).
4. `file`, не существующий на проверяемой ревизии.
5. Больше `max_observations_per_attempt` записей (дефолт 100) — защита от
   вырождения, а не от многословия.

Пустой список — законный результат: ревьюер не нашёл ничего.

## 4. Reconciliation

`schema: review.reconciliation.v1`

Вход зависит от context: для первичного `discovery` — все blind observations
круга, для `fix_check_new` — только элементы `new_observations` текущей проверки;
в обоих случаях у каждой записи уже есть `observation_id`, рядом передаётся
ledger. Follow-up observation внутри `decisions[*]` сюда не входит: его внешний
`finding_id` уже задаёт target (§6). Выход — **классификация каждого переданного
наблюдения ровно одним исходом** и предложенные группы.

```json
{
  "schema": "review.reconciliation.v1",
  "groups": [
    {
      "observation_ids": ["O-4-1", "O-4-7"],
      "outcome": "new",
      "title": "Checkpoint commit can race with state flush"
    },
    {
      "observation_ids": ["O-4-3"],
      "outcome": "existing_open",
      "finding_id": "F-12"
    },
    {
      "observation_ids": ["O-4-5"],
      "outcome": "reaffirmed_closed",
      "finding_id": "F-04"
    },
    {
      "observation_ids": ["O-4-9"],
      "outcome": "reopen_closed",
      "finding_id": "F-07",
      "reason": "The off-by-one is back after the refactor in commit a1b2c3d."
    }
  ]
}
```

Валидация — восемь проверок, все до записи:

| # | Проверка | Нарушение |
|---|---|---|
| 1 | Каждое наблюдение, переданное в текущий reconciliation context, упомянуто | Потерянное наблюдение — `contract_error` |
| 2 | Ни одно переданное наблюдение не упомянуто дважды | Пересечение групп — `contract_error` |
| 3 | `outcome` из четырёх допустимых | `contract_error` |
| 4 | `existing_open` ссылается на **открытый** ID допустимого scope | `contract_error` |
| 5 | `reaffirmed_closed` — только на **закрытый** ID с `last_resolution = accepted_reason`; `reopen_closed` — на любой **закрытый** ID допустимого scope | `contract_error` |
| 6 | `reopen_closed` несёт непустой `reason` | `contract_error` |
| 7 | `new` не несёт `finding_id`; остальные несут | `contract_error` |
| 8 | `new` несёт непустой `title`; остальные три исхода `title` не несут | `contract_error` |

Проверка 8 не даёт двум ошибкам уйти ниже по потоку. Без title новая identity
падает только на `finding.title NOT NULL` при записи; title на существующем ID
становится тихим обходом правила, что ground truth меняет только человек.

Проверка 5 — явное решение владельца Q44. Если это другая проблема либо связь с
прежним ID неуверенная, reconciler выбирает `new`. Если это тот же finding,
после `verified_fixed`, `policy_closed` и `human_decision` допустим только
`reopen_closed`; human-закрытие затем проходит двухшаговый гейт §4.2. Ответ
человека `keep_closed`, который создаёт `reaffirmation`, не является тихим
исходом агента `reaffirmed_closed`.

Проверки 1 и 2 вместе означают **исчерпывающее разбиение**: наблюдение нельзя
потерять и нельзя положить в две группы. Это инвариант 2, и он проверяется
запросом, а не доверием.

Правило разрешения неоднозначности записано отдельно, потому что оно
контринтуитивно: **при сомнении оставить два замечания безопаснее, чем молча
склеить разные проблемы.** Склеенное замечание закрывается одним disposition, и
вторая проблема исчезает без следа; два похожих — это шум, который видно.

«Заявил `new` для того, что открыто» — не ошибка валидации (проверка 4 ловит
только явную ссылку на закрытый ID), а **видимая аномалия**: CLI показывает новые
ID, похожие на недавно закрытые по файлу и близости title, без автоматического
слияния. Сохранённый слепой вывод при этом остаётся доказательством.

### 4.1. Что делает с кругом каждый исход

| Исход | `link_type` | Круг | Автору идёт |
|---|---|---|---|
| `new` | `first_seen` | Входит в текущий | да |
| `existing_open` | `recurrence` | Входит в текущий | да |
| `reaffirmed_closed` | `reaffirmation` | **Не порождает** | нет |
| `reopen_closed` | `reopening` | Переводит в текущий | да, по `resolution_authority` |

`reaffirmed_closed` — единственный исход, не создающий работы: прежнее решение в
силе, автору ничего не идёт, человеку тоже. Связь при этом пишется всё равно —
иначе не отличить «перепроверили и подтвердили» от «не смотрели».

### 4.2. Переоткрытие того, что закрыл человек — два шага

`reopen_closed` на записи с `resolution_authority = 'human'` **не входит в круг
сразу**. Отмена явного решения человека не полномочие системы (`decision.md`
§7.4), поэтому такой исход — вопрос человеку, и связь пишется только после
ответа:

```
reconciliation вернул reopen_closed(F-09, reason)
  где finding_status(F-09).last_authority = 'human'
    │
    ├─ TX: human_question(reason = 'reopen_human_closed')
    │      + notification_outbox + blocker + событие
    │      Наблюдение остаётся без связи — круг не закрывается.
    │
    └─ ответ человека:
         «переоткрыть»       → link_type = 'reopening',  замечание в круг
         «держим закрытым»   → link_type = 'reaffirmation', круга нет
```

Без этой двухшаговости reconciliation попадает в тупик: связать наблюдение как
`reopening` — значит отменить решение человека автоматически, не связать —
значит нарушить исчерпывающее разбиение и получить `contract_error` на
собственной валидации. Ни один из четырёх исходов сам по себе такую ситуацию не
разрешает, поэтому она разрешается ожиданием.

Наблюдение всё это время лежит записанным и неизменяемым — оно существует раньше
личности, и отложенная привязка ничего не ломает.

Вопрос человеку здесь несёт: текст переоткрытия от ревьюера, исходную причину
закрытия и `escalation_severity` на момент закрытия. Порог не применяется:
`human`-закрытие возвращается человеку независимо от severity.

**Цена: круг стоит целиком из-за одного несвязанного наблюдения — и это
осознанный выбор, а не недосмотр.** Остальные наблюдения круга уже
классифицированы и формально могли бы уйти автору в работу, пока человек думает.
Записано здесь, чтобы позже это не «оптимизировали» молча.

Почему не отдаём:

- **Dispositions круга — всё или ничего** (§5). Если человек ответит
  «переоткрыть», множество открытых ID изменится под уже работающим автором:
  либо его ответ окажется неполным, либо придётся заводить второй частичный
  круг.
- **Кап поедет.** Переоткрытое замечание пришлось бы класть в новый круг, то
  есть тратить правку автора на то, к чему он отношения не имеет.
- **Автор правил бы по неполной картине** — не зная, что вернулось замечание,
  которое может конфликтовать с его решением.

Спекулятивно начать и откатить на «переоткрыть» тоже нельзя: откат авторской
попытки, успевшей сделать ревизию, — это компенсация checkpoint-коммита
(`architecture.md` §8), дорогая и заметная в истории ветки.

Задержка при этом ограниченная: стоит **эта ветка**, соседние независимые
работают, и `Run` остаётся `running`. А сам путь редкий — нужно, чтобы человек
раньше в этом же прогоне решил судьбу замечания, и чтобы более поздняя кампания
объявила его вернувшимся. Оптимизировать редкий путь ценой контракта
dispositions — плохой размен.

### 4.3. Кто исполняет reconciliation

Отдельная роль `reconciler`, не линия. Причины:

- ей нужен ledger, а линии в слепой фазе его не видят — совместить в одном
  агенте «не видел прежних findings» и «сопоставь с прежними findings»
  невозможно;
- она видит наблюдения **обеих** линий, то есть по определению не слепа;
- её вывод — классификация, а не суждение о коде, и рубрика ей не нужна.

Практически: `role = 'reconciler'`, профиль берётся из конфига стадии,
**свежая сессия** (не продолжение чьей-либо линии), политика контекста
`explicit` — только наблюдения круга и ledger. В `reviewer_exposure` эта попытка
**записывается**: reconciler видел содержимое наблюдений по этой ревизии, и на
следующей кампании свежим он уже не считается.

По умолчанию профиль reconciler'а — тот же, что у линии с наименьшим индексом,
но сессия новая. Это дёшево и не создаёт пятого участника там, где их и так
впритык; если окажется, что reconciler систематически подыгрывает своей же
линии, профиль разводится конфигом — без изменения кода.

## 5. Автор: dispositions

`schema: review.dispositions.v1`

```json
{
  "schema": "review.dispositions.v1",
  "dispositions": [
    { "finding_id": "F-12", "disposition": "fixed" },
    { "finding_id": "F-19", "disposition": "rejected",
      "reason": "The index exists; the query planner picks it — see EXPLAIN output in the body." },
    { "finding_id": "F-23", "disposition": "wont_fix",
      "reason": "Wording is consistent with the rest of the CLI; changing it here would create the inconsistency." }
  ]
}
```

| Проверка | Нарушение |
|---|---|
| Покрыт **каждый** открытый ID круга | `contract_error` |
| Нет ID вне списка открытых | `contract_error` |
| Нет повторов | `contract_error` |
| `rejected` и `wont_fix` несут непустой `reason` | `contract_error` |
| `disposition` из трёх допустимых | `contract_error` |

**Всё или ничего.** Либо все открытые ID закрыты одной транзакцией, либо не
засчитывается ни один. Как именно провалилась попытка, зависит от места обрыва:
процесс убит на середине — `interrupted`; процесс закончил, но выдал частичный
набор — `contract_error`. В обоих случаях круг не состоялся, и кап не двигается.

Разница между `rejected` и `wont_fix` — не оттенок: `rejected` означает «замечание
неверно», `wont_fix` — «замечание верно, но чинить не будем». Ревьюер
рассматривает их одинаково (`accepted_reason` или `insists`), но человеку при
эскалации показывается именно то, что сказал автор.

## 6. Ревьюер: проверка исправлений и отказов

`schema: review.decisions.v1`

Эту фазу ведёт **владелец finding'а** — линия с наименьшим индексом среди тех,
чьи наблюдения вошли в группу этой кампании. Остальные линии в этом круге
замечание не судят.

```json
{
  "schema": "review.decisions.v1",
  "decisions": [
    { "finding_id": "F-12", "decision": "verified_fixed" },
    { "finding_id": "F-19", "decision": "insists",
      "note": "EXPLAIN shows a scan on the blocker table for the open-question query.",
      "observation": {
        "title": "Missing index on blocker(run_id)",
        "body": "…",
        "unchanged_from": "O-4-3"
      }
    },
    { "finding_id": "F-23", "decision": "accepted_reason" }
  ],
  "new_observations": [
    {
      "title": "Cancellation leaves a stale blocker",
      "body": "The fix adds a new early return before the blocker is cleared.",
      "file": "service/review.py",
      "line_start": 211,
      "line_end": 218,
      "evidence": "cancelled is returned before clear_blocker()",
      "severity_suggested": "high"
    }
  ]
}
```

Допустимые пары — CHECK на уровне базы, но проверяются и здесь, чтобы вернуть
внятную ошибку:

| Disposition автора | Допустимый исход |
|---|---|
| `fixed` | `verified_fixed`, `still_present` |
| `rejected`, `wont_fix` | `accepted_reason`, `insists` |

Несовместимая пара — `contract_error`.

Follow-up `observation` внутри элемента `decisions` относится к внешнему
`finding_id` этого же элемента и допустим **только** для `still_present` и
`insists`: оба решения оставляют finding открытым. При `verified_fixed` или
`accepted_reason` вложенный observation противоречил бы закрытию того же
finding и даёт `contract_error`; отдельная проблема должна находиться в
`new_observations`. Для допустимого follow-up личность уже известна, поэтому
второй агент её не классифицирует: после полной валидации ответа T1.6 проверяет
`unchanged_from` на тот же finding и текущий период, а T1.7b атомарно пишет
`review_observation` и `finding_observation_link(link_type=recurrence)` вместе с
решением. Любая ошибка отклоняет весь ответ до записи; observation без link
отдельно не коммитится. Это решение владельца Q45.

### 6.1. Новое замечание, найденное при проверке правки

`new_observations` — обязательный массив, пустой в обычном случае. Он нужен не
для повторного описания выданных finding ID, а для действительно новых проблем,
которые ревьюер впервые заметил, проверяя авторскую правку. Без этого поля
`cap_exhausted_new` недостижим: все личности возникали бы в первичном круге, а
T1.4 принимает решение только после последующих `fix_check`.

Элемент имеет ту же форму, что observation слепой фазы (§3): собственная
`severity_suggested` обязательна, `unchanged_from` и `finding_id` запрещены,
проверки пути/range/лимита те же. Если проблема похожа на существующий finding,
ревьюер всё равно не угадывает его ID в этом поле. После того как все решения
по выданным ID прошли валидацию, общий набор `new_observations` текущего
`fix_check` передаётся отдельному reconciler'у вместе с **post-decision
ledger** и проходит те же четыре исхода §4. То есть все валидные решения
текущего check уже учтены: ID, только что закрытый как `verified_fixed` или
`accepted_reason`, виден reconciler'у закрытым и не принимается в
`existing_open`. Так новый ID выдаётся только reconciliation, а не схемой
решений.

До завершения этого reconciliation `review_round.result` не записывается и cap
не проверяется. Только новая identity получает `first_round_id` текущего
`fix_check`; reopened finding сохраняет свой исходный `first_round_id`. Оба
входят в open set, но к `cap_exhausted_new` приводит именно впервые выданная в
этом круге identity. Campaign всё время остаётся в `fix_cycle`; это подшаг
проверки, а не возврат в состояние кампании `reconciliation`.

**Про `unchanged_from` у follow-up observation.** Здесь он законен и здесь же
единственно осмыслен:
ревьюер видит открытое замечание, помнит своё прежнее наблюдение и заявляет, что
серьёзность не изменилась. Значение берётся **из колонки `last_observation`
расширенного ledger** (§2.1) — другого источника у агента нет и быть не может.

Правила ссылки (`db-schema.md` §5.3): только назад по порядку, только в пределах
того же finding'а и того же периода открытости, без циклов, цепочка обязана
заканчиваться явной `severity_suggested`. Нарушение — `contract_error` на приёме.
Campaign/order/effective severity защищает база; принадлежность тому же finding
и периоду проверяет T1.6 до атомарной записи observation + `recurrence` в T1.7b.

Каждое наблюдение по-прежнему несёт **ровно одно** из двух: свою
`severity_suggested` либо `unchanged_from`. Отсутствие обоих отклоняется, потому
что иначе «ревьюер подумал и подтвердил» не отличить от «не упомянул, и мы
унаследовали» — а без этого различия систематический перекос severity нечем
измерить.

`still_present` и `insists` оставляют замечание открытым. `insists` при
`escalation_severity` не ниже порога **сразу** создаёт вопрос человеку, не
дожидаясь исчерпания кругов; спор ниже порога закрывается принятием отказа
автора с `resolution_authority = policy` и записью в audit trail.

## 7. Верификация

`schema: verification.plan.v1`

```json
{
  "schema": "verification.plan.v1",
  "steps": [
    { "cwd": ".", "argv": ["pytest", "-q", "tests/"], "expect": "exit_zero",
      "step_timeout_s": 600 },
    { "cwd": ".", "argv": ["ruff", "check", "."],     "expect": "exit_zero" }
  ],
  "rationale": "Project has pytest suite and ruff config; no build step."
}
```

Ключевое ограничение: **`argv` — список, а не строка**. Никакого shell:
`&&`, `|`, `$(...)`, `>` и подстановки переменных не интерпретируются и являются
поводом для отказа политики.

`steps` обязан содержать хотя бы один шаг, а `rationale` — непустое объяснение
выбора. Пустой план не означает «проверять нечего»: он создаёт ложный зелёный
результат и потому отклоняется как `contract_error` до policy check.
`expect` в `verification.plan.v1` имеет ровно одно значение — `exit_zero`.
Добавление `exit_nonzero`, проверки текста или другой семантики потребует новой
версии схемы и синхронного изменения валидатора T1.7 и исполнителя T1.14.

Дальше план не исполняется агентом. Его исполняет детерминированный сервис,
проверив каждый шаг (`architecture.md` §10). Это единственное место во всей
системе, где команды, придуманные моделью, исполняются кодом, — и потому
единственное, где пять проверок политики команд из `architecture.md` §10
выполняются кодом, а не промптом.

Отказ политики — не молчаливый пропуск шага, а вопрос человеку: модель
предложила запретное, и это стоит увидеть.

`schema: verification.result.v1` пишет уже сервис, не агент: команда, код
возврата, усечённый вывод, `failure_signature` для сравнения «та же причина или
другая».

## 8. Разбивка на задачи

`schema: graph.breakdown.v1`

```json
{
  "schema": "graph.breakdown.v1",
  "tasks": [
    { "id": "T1", "title": "Store: schema and migrations", "body": "…" },
    { "id": "T2", "title": "Review domain: cap and transitions", "body": "…" }
  ],
  "dependencies": [ { "parent": "T1", "child": "T2" } ]
}
```

Импорт атомарный (`decision.md` §6.2): сначала разобрать весь вывод, потом
проверить, потом записать одной транзакцией.

| Проверка | Нарушение |
|---|---|
| ID уникальны | `contract_error` |
| Оба конца каждого ребра существуют | `contract_error` |
| Нет self-edge | `contract_error` |
| Нет циклов | `contract_error` **с выводом конкретного пути цикла** |
| Нет дублирующихся рёбер | `contract_error` |

Вывод пути цикла — не удобство отладки. Это то, что попадёт в промпт повторной
попытки, и без него агент будет чинить наугад.

## 9. Cut-off

`schema: handoff.cutoff.v1`

Пишет уходящий агент. Критерий приёмки: **принимающий должен суметь действовать,
прочитав ровно один файл.**

```json
{
  "schema": "handoff.cutoff.v1",
  "task": "Проверить headless-контракты vendor CLI и обновить дизайн.",
  "current_state": "Фикстуры Claude и Codex сняты; cursor-agent недоступен.",
  "next_action": "Сверить fake CLI с сырыми stdout/stderr и закрыть T0.2.",
  "touched_files": [
    { "path": "fixtures/vendor-cli/README.md", "purpose": "Формат и режимы фейка" }
  ],
  "open_questions": [],
  "acceptance_criteria": ["Все fixture-пары воспроизводятся byte-for-byte."],
  "referenced_files": ["docs/design/vendor-cli-contracts.md"],
  "referenced_shas": ["2761ee1307162e946b23363bb01dab697eaea6de"]
}
```

`task`, `current_state`, `next_action`, `touched_files` и
`acceptance_criteria` обязательны и непусты. `open_questions` обязательно
присутствует, но пустой массив честно означает «нет вопросов».
`referenced_files`/`referenced_shas` — единственный машиночитаемый список
ссылок: свободный текст не разбирается эвристиками и не заменяет запись в этих
полях. Валидатор сверяет каждый объявленный reference со snapshot репозитория,
переданным caller'ом, а renderer строит кликабельные ссылки только из
проверенного списка.

Проверяется структурно и кодом, без единого вызова модели:

| Проверка | Что ловит |
|---|---|
| Все обязательные секции присутствуют; задача, состояние, следующее действие и затронутые файлы непусты; `open_questions` явно присутствует | Шаблонная передача |
| Критерии приёмки непусты | «Готово» без определения готовности |
| Упомянутые файлы резолвятся на текущем SHA | Ссылки на несуществующее |
| Упомянутые SHA существуют | То же |
| Есть digest содержимого | Целостность |

Digest не сочиняет агент. После успешной валидации сервис канонически
сериализует payload как UTF-8 JSON с сортировкой ключей, compact separators и
`ensure_ascii=false`, вычисляет SHA-256 именно этих bytes и передаёт bytes +
digest владельцу артефакта T1.13. Так digest проверяет именно сохранённое
содержание, а не самоотчёт модели; перестановка ключей во входном JSON digest
не меняет.

Модельная самопроверка приёмки в v1 не делается: принимающий склонен отвечать
«понял», а обычный механизм вопроса человеку уже покрывает реальную блокировку —
и срабатывает там, где непонимание проявилось, с конкретным контекстом.

## 10. Вопрос человеку

`schema: human.question.v1`

Формулирует агент, отправляет рантайм.

```json
{
  "schema": "human.question.v1",
  "question_text": "Автор трижды правил F-12, ревьюер по-прежнему видит гонку между checkpoint-коммитом и фиксацией состояния. Правки исчерпаны.",
  "context": "Затрагивает восстановление после падения: возможен дубль коммита.",
  "options": [
    { "key": "A", "label": "Разрешить ещё одну правку", "confidence": 0.4 },
    { "key": "B", "label": "Принять как есть", "confidence": 0.2 },
    { "key": "C", "label": "Остановить ветку", "confidence": 0.4 }
  ]
}
```

Требования — к вопросу, не к ответу: суть в двух фразах, чем вызван и на что
влияет, варианты с оценкой уверенности там, где они уместны. **Вопрос без
вариантов законен** — бывают вопросы вида «расскажи, как надо».

**У review-вопросов `dispute`, `cap_exhausted_same` и `cap_exhausted_new`
варианты стандартные, и это контракт, а не сочинение агента** (`decision.md`
§8):

| Вариант | Что делает система |
|---|---|
| Разрешить ещё одну правку | `stage_execution.max_author_revisions += 1`, та же кампания остаётся в `fix_cycle`, цикл продолжается с прежними счётчиками |
| Принять как есть | Открытые замечания закрываются с `resolution_authority = human`, кампания завершается как `closed_escalated` |
| Остановить ветку | Кампания завершается как `closed_escalated`, ветка помечается неуспешной, соседние продолжают |
| Свой текст | Интерпретирует агент, лимит один переспрос |

При `reason=dispute` вход формирователя содержит **все** findings текущего check,
чья `escalation_severity` не ниже порога. Они идут одной упорядоченной
последовательностью (severity по убыванию, затем `finding_id`) и превращаются в
один вопрос. Для каждого в context сохраняются ID, severity, порог и версия
политики; сокращать список до одного finding запрещено (Q46).

До ответа человека кампания не закрыта: текущий круг уже имеет
`result = escalated`, но `review_campaign.state = fix_cycle`, а ветка стоит на
blocker'е `human_question`. Поэтому вариант «ещё одна правка» продолжает именно
этот цикл, не обнуляя его счётчики; терминальный `closed_escalated` используется
только для окончательного ответа.

В самом тексте вопроса обязательно различаются два случая: «автор трижды не смог
починить одно и то же» (`reason = cap_exhausted_same`) и «ревьюер нашёл новое на
последней проверке» (`cap_exhausted_new`). Это разные ситуации, и человек
выбирает в них разное — ради этого причина остановки хранится в состоянии, а не
выводится из счётчика.

Ответ — свободный текст. Короткий «A» закрывает гейт **детерминированно, без
участия модели**; свободный текст интерпретирует агент и обязан переспросить,
если не понял. Переспрос ограничен, дефолт — один: дальше бот просит ответить
ключом варианта в reply с ID вопроса.

Для `reason = dispute/cap_exhausted_same/cap_exhausted_new` интерпретатор обязан
вернуть ровно одно из трёх кампанийных действий таблицы. Per-finding или
смешанный ответ не записывается как принятый `human_answer`, не снимает blocker
и не применяется частично: это переспрос в пределах лимита, после которого бот
требует ключ одного варианта.

Для трёх review-причин validator получает reason отдельным immutable context и
требует ровно ключи `A/B/C` с нормативными labels таблицы; confidence каждого
варианта — число от 0 до 1. Для остальных причин `options` может быть пустым,
но при наличии ключи уникальны, labels непусты, confidence находится в том же
диапазоне.

## 11. Сводка проверок

Это чек-лист машинной границы. Все нарушения ниже дают `contract_error`, кроме
пяти явно помеченных отказов verification policy: они сохраняют валидный план,
не тратят `contract_retry_budget` и порождают вопрос человеку по §7.

**Транспорт:** маркеры не ровно по разу или стоят в неверном порядке ·
содержимое не один строгий JSON-object · duplicate key/non-finite число,
включая `1e999` · неизвестная или неожиданная `schema` · неизвестное
поле/неверный тип · превышен лимит `1 MiB`.

**Наблюдения:** нет ни `severity_suggested`, ни `unchanged_from` · есть оба ·
severity вне enum · `unchanged_from` в слепой фазе · `unchanged_from` не на
показанный ID · `unchanged_from` вперёд, в другой finding, в другой период, с
циклом · `file` не существует на ревизии · `line_end < line_start` · превышен
лимит числа наблюдений.

**Reconciliation:** наблюдение не упомянуто · упомянуто дважды · `outcome` вне
четырёх · `existing_open` на закрытый ID · `reaffirmed_closed` на открытый либо
закрытый не через `accepted_reason` · `reopen_closed` на открытый ·
`reopen_closed` без `reason` · `new` с `finding_id` · ссылка на ID вне
допустимого scope · `new` без непустого `title` · существующий ID с `title`.

**Dispositions:** не покрыт открытый ID · ID вне списка · повтор · отказ без
обоснования · значение вне трёх.

**Decisions:** пара disposition/decision несовместима · решение вынесено не
владельцем · не покрыт ID, требующий решения · `new_observations` отсутствует
или не массив · новый observation без `severity_suggested` · с
`unchanged_from`/`finding_id` · с невалидным file/range/severity либо сверх
лимита · follow-up observation при `verified_fixed`/`accepted_reason` ·
follow-up observation с `unchanged_from` другого finding или периода.

**План верификации:** пустой `steps`/`rationale` · `argv` строкой или пуст ·
`expect` не равен `exit_zero` · неположительный `step_timeout_s` —
`contract_error`; shell-синтаксис · `cwd` вне разрешённого · исполняемое вне
allowlist · путь из denylist · адрес production-среды —
`VerificationPolicyRejection` и вопрос человеку, а не retry.

**Граф:** дубль ID · висячее ребро · self-edge · цикл · дубль ребра.

**Cut-off:** пустая обязательная секция · нерезолвимый файл или SHA.

**Вопрос человеку:** для review-причины не ровно нормативные `A/B/C` · duplicate
key · пустой label · confidence вне `[0,1]`; для остальных причин пустой список
вариантов законен.

Каждая строка отсюда обязана иметь тест с синтетическим финальным выводом между
маркерами, отдающим ровно этот битый ответ. Исполняемый fake CLI и vendor
envelope подключаются следующей задачей T1.8: T1.7 зависит только от T1.1 и не
имеет права заранее дублировать адаптер. Это дешевле, чем ловить ошибки на
реальных прогонах, и надёжнее, чем надеяться на дисциплину моделей.
