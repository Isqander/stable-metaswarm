# Cut-off: фаза M0 — контракты вендорских CLI

Передача от агента, писавшего тех-дизайн (Windows, без доступа к вендорским CLI),
агенту, работающему в WSL2 и на VPS.

Форма — по шаблону `handoff.cutoff.v1` из `../design/agent-contracts.md` §9.
Критерий приёмки того шаблона: **принимающий должен суметь действовать, прочитав
ровно один файл.** Если после этого файла остаются вопросы «а что дальше» — это
дефект передачи, о нём стоит сказать.

**База:** коммит `2761ee1307162e946b23363bb01dab697eaea6de`, ветка `main`.
Весь тех-дизайн зафиксирован на нём; все ссылки ниже проверены на этом SHA.

---

## 1. Задача

Выяснить и зафиксировать, **как на самом деле ведут себя пять вендорских
CLI-профилей в неинтерактивном режиме**, и сделать из снятых ответов фикстуры и
фейковые исполняемые для тестов.

Это фаза 0 из `../design/task-plans.md` §4 — единственный настоящий внешний
неизвестный всего проекта. Всё остальное решение построено на чтении чужих
исходников и рассуждении; здесь мы впервые смотрим на реальность.

Результат влияет на адаптеры, **не на стек**. То есть плохие новости здесь не
отменяют архитектуру, но могут поменять состав профилей и способ разбора вывода.

## 3. Следующее действие

**Начни с T0.3, а не с T0.1.** Это тридцать секунд работы и потенциально самая
дорогая новость проекта: если `claude-m` и `claude-z` резолвятся в одну и ту же
фактическую модель, независимых мнений три, а не четыре, и допущение
`decision.md` §15 пересматривается **до** того, как написана первая строка кода.

Дальше по порядку: T0.1 (инвентарь) → T0.2 (фикстуры и фейки) → T0.4 (cursor на
VPS) → T0.5 (бонус, см. §6).

### T0.3 — какая модель отвечает на самом деле

Для каждого из трёх claude-профилей нужны **два независимых ответа**:

1. **Что говорит сам CLI в метаданных.** У `claude -p --output-format json`
   (или `stream-json`) в финальном объекте обычно есть поле `model`. Это и есть
   `actual_model` в нашей терминологии — на нём стоит правило свежести
   ревьюера.
2. **Что говорит модель о себе текстом.** Спросить «which model are you, exactly».

**Оба нужны, и расхождение между ними — тоже результат.** Модели за прокси часто
называют себя чужим именем: MiniMax может представиться Claude, потому что
обёртка эмулирует Anthropic API. Верить надо метаданным CLI, а текстовый ответ
записать как наблюдение.

Что проверяем: три профиля дают **три разные** пары `provider + model`. Если два
совпали — останавливайся и пиши, дальше это меняет план.

### T0.1 — инвентарь headless-контрактов

Девять сценариев на каждый профиль. Нумерация фиксированная — под неё названы
файлы фикстур.

| # | Сценарий | Что выясняем |
|---|---|---|
| S1 | `<bin> --version` | Версия для манифеста попытки и drift check |
| S2 | Минимальный промпт: «Reply with exactly: PONG» | Заводится ли headless вообще, как выглядит чистый вывод |
| S3 | Запрос идентичности модели | То же, что T0.3, но для всех пяти |
| S4 | Структурированный вывод (`stream-json` / `json`) | Есть ли машинно выделяемый финальный результат |
| S5 | Продолжение сессии | Возвращается ли session id и как его передать обратно |
| S6 | Read-only режим | Как включается, что происходит при попытке записи |
| S7 | `SIGTERM` на середине длинного ответа | Успевает ли корректно завершиться, за сколько, нужен ли `SIGKILL` |
| S8 | Несуществующий флаг + отсутствующий рабочий каталог | Коды выхода на ошибках |
| S9 | Длинная задача с паузами в выводе | Как выглядит «жив, но молчит» — под heartbeat |

**Гипотезы, которые надо проверить, а не принять.** Они получены чтением чужих
исходников (bernstein, Gas City) на этапе ресёрча и **ни разу не запускались**:

- `claude -p '<промпт>'`, `--output-format stream-json`, `--resume <session-id>`;
- коды выхода Claude Code: `0` успех, `1` общая ошибка, `2` неверное
  использование, `3` переполнение контекста, `4` отказ в правах, `130` SIGINT,
  `137` SIGKILL, `143` SIGTERM;
- в `result` от stream-json — `subtype` со значениями `error_max_turns`,
  `error_context_window`, `error_permission`;
- `codex exec '<промпт>'`;
- `cursor-agent -p '<промпт>' --output-format stream-json --workspace <dir>`,
  read-only через `--mode ask`.

Любая из них может оказаться устаревшей. Пиши как есть, а не как ожидалось.

### T0.2 — фикстуры и фейковые CLI

Сырые ответы сохранять по схеме:

```
fixtures/vendor-cli/<profile>/S<N>.argv     точная командная строка
fixtures/vendor-cli/<profile>/S<N>.stdout   сырой stdout
fixtures/vendor-cli/<profile>/S<N>.stderr   сырой stderr
fixtures/vendor-cli/<profile>/S<N>.exit     код возврата
fixtures/vendor-cli/<profile>/S<N>.notes    что бросилось в глаза
```

Дальше — скрипт, который по argv находит фикстуру, печатает её в тот же поток и
выходит с тем же кодом. Плюс режимы порчи, включаемые переменной окружения:

| Переменная | Поведение |
|---|---|
| `FAKE_MODE=broken_json` | Валидный по форме вывод с поломанным JSON внутри |
| `FAKE_MODE=silent` | Ничего не печатает, висит |
| `FAKE_MODE=no_finish` | Печатает и не завершается |
| `FAKE_MODE=ignore_term` | Ловит SIGTERM и продолжает работать |
| `FAKE_MODE=slow` | Печатает с паузами — под проверку soft/hard timeout |

Эти пять режимов покрывают большинство приёмочных сценариев `decision.md` §14,
поэтому фикстуры делаются аккуратно: на них будет стоять вся фаза 1.

## 5. Критерии приёмки

Проверяемые утверждения, каждое — да или нет:

1. Для каждого из пяти профилей заполнена строка таблицы по девяти сценариям.
   Прочерк допустим только с пометкой «проверено, не поддерживается».
2. Три claude-профиля дают три **различные** фактические пары `provider+model`,
   подтверждённые метаданными CLI, а не самоописанием модели. Если нет —
   расхождение записано и вынесено на решение.
3. Для каждого профиля известно, **как машинно выделить финальный результат**.
   Если у какого-то CLI такого способа нет — зафиксировать, что для него
   основным становится путь с маркерами (`agent-contracts.md` §1.1).
4. Коды выхода и их значения выписаны по факту, а не по гипотезе из §3.
5. Известно поведение на `SIGTERM`: успевает ли завершиться и за какое время.
   Отсюда возьмётся значение grace-периода перед `SIGKILL`.
6. Фикстуры лежат по схеме из §3, фейковый CLI по ним неотличим от настоящего
   для простого вызова, и пять режимов порчи работают.
7. **В фикстурах нет ни одного секрета.** Токены, ключи и содержимое
   `ANTHROPIC_API_KEY` заменены на `<REDACTED>` до коммита. Проверить глазами,
   а не полагаться на то, что их там «не должно быть».
8. `cursor-agent` на VPS: либо получен ответ в headless по подписке без
   браузера, либо зафиксировано, что профиль недоступен. Второе не блокирует
   v1.

## 6. Дополнительно, если будешь в WSL2 (T0.5, ~5 минут)

В `architecture.md` §4.5 recovery ищет осиротевшие процессы агентов по маркеру
`METASWARM_ATTEMPT_ID` в `/proc/*/environ`. Это **допущение**, сделанное без
проверки на реальном WSL2-ядре.

Проверить: запустить любой долгий процесс с этой переменной в окружении и
прочитать её обратно из `/proc/<pid>/environ` от того же пользователя.

```bash
METASWARM_ATTEMPT_ID=probe-1 sleep 300 &
tr '\0' '\n' < /proc/$!/environ | grep METASWARM_ATTEMPT_ID
```

Если не читается — скажи сразу: это меняет механику recovery, а она уже
описана как несущая. Запасной путь есть (файл-маркер в каталоге состояния рядом
с pid), но выбирать его надо осознанно.

## 7. Открытые вопросы

Ни один не блокирует старт — все они разрешаются тем, что ты увидишь.

1. **Ограничение по частоте запросов.** Девять сценариев × пять профилей — 45
   вызовов. Если подписка начнёт ограничивать, разнеси по времени; фиксировать
   поведение при rate limit — это сценарий S8 бонусом, он нам всё равно нужен.
2. **`claude-m` и `claude-z` сейчас живут самодельными скриптами-обёртками в
   `~/.local/bin`** (так описано в требованиях). Для T0.3 годятся и они, но в
   фикстуры пиши argv **целевого** вида — прямой вызов `claude` с
   `ANTHROPIC_BASE_URL` в окружении. Обёртки мы отменяем: секрет не должен
   проходить через `bash` и светиться в `ps aux`.
3. **Насколько велик сырой вывод.** Если stream-json одного ответа окажется в
   мегабайты, схему хранения транскриптов придётся уточнять. Просто отметь
   порядок величины.
4. **Стабильность формата между версиями.** Если увидишь в выводе что-то, что
   выглядит как «недавно поменяли» — отметь. Версии CLI входят в drift check, и
   знать, что там ломается, полезно заранее.

## 8. Чего делать не надо

- **Не начинать писать код системы.** Фаза 1 идёт после M0 и в другом порядке,
  чем кажется естественным: сначала домен, потом обвязка (`task-plans.md` §8.3).
- **Не чинить окружение автоматизацией.** Принятое решение: окружение готовит
  человек, система его не чинит и не доустанавливает (`decision.md` §4).
- **Не подгонять факты под дизайн.** Если CLI ведёт себя иначе, чем предполагает
  `architecture.md` §9 — прав CLI. Правь документ.
