## 2. Решение

**Ставим на связку `beads` + `Gas City`, пишем поверх свой pack, доноров
используем точечно.**

```
beads (bd)              состояние: граф задач, гейты, метаданные попыток
   ▲
Gas City (gc)           рантайм: запуск профилей, control-беды check/retry/drain,
   ▲                    worktree, транскрипты, внешние сообщения
наш pack                конвейер стадий + детерминированные чекеры
   ▲
доноры                  metaswarm (промпты/рубрики), bernstein (адаптеры + Telegram),
                        Orca (дизайн цикла ревью), Conductor (язык описания)
```

Решающий довод не тот, что был у ресёрчей. Их довод — «beads даёт durable-паузу».
Он **наполовину неверен** (раздел 4). Настоящий довод — **пятиосевая модель агента
в Gas City буквально совпадает с требованием Q27a**, и такой модели больше нет
ни у кого:

| Ось | Где задаётся | Что закрывает у нас |
|---|---|---|
| Harness — какой CLI | `provider = "claude"` | CLI-семейство, адаптер |
| Model — какой ярлык модели | `option_defaults = { model = "opus" }` | уровень модели |
| **Upstream — кто обслуживает модель** | `[upstreams.<name>]` + `upstream = "..."` | **`claude-m` / `claude-z`** |
| Transport — как gc им управляет | `session = "acp"` \| tmux | — |
| Runtime — где он исполняется | `[session] provider = "subprocess"` | правило «не tmux» из Q1 |

Источник: `refs/gascity/docs/guides/configuring-an-agent.md:16-38`.

То есть профиль `claude-z` — это не форк и не обёртка, а:

```toml
# city.toml
[upstreams.zai]
base_url = "https://api.z.ai/api/anthropic"
api_key  = "$ZAI_KEY"                 # ссылка на секрет, не сам секрет

[providers.claude-z]
base            = "builtin:claude"
option_defaults = { model = "opus" }  # у Z.AI за "opus" стоит glm-5.2
```

Абстрактные `base_url`/`api_key` рендерятся на env-имена **того харнеса**, к
которому применены: у `claude` → `ANTHROPIC_BASE_URL`/`ANTHROPIC_API_KEY`, у
`codex` → `OPENAI_*` (`configuring-an-agent.md:129-155`). Секрет пишется как
`$VAR` и разворачивается при резолве, в конфиг не попадает
(`:190-196`). Отсутствие биндинга — **жёсткая ошибка, а не молчаливый
no-op** (`:153-155`). Это ровно два требования, которые Q27a сформулировал как
новые.

Плюс `cursor-agent` уже есть встроенным пресетом
(`refs/gascity/internal/worker/builtin/profiles.go:437`,
`docs/guides/harness-recipes.md:149-158`), а у каждого пресета объявлен
headless-режим: `claude -p`, `codex exec`, `gemini -p`, `agy --print`
(`profiles.go:126,197,273,711`).

**Чего это решение НЕ покупает** — раздел 4. Там же честный список того, что
придётся дописать, и раздел 7 с альтернативой на случай, если цена окажется
неподъёмной.

## 4. Что НЕ готово, вопреки ресёрчам

Это самая полезная часть документа. Пять мест, где «есть из коробки» на деле
означает «есть поле в структуре».

### 4.1. Human-гейт в beads не работает сам по себе

Ресёрчи (и предыдущий мета-ресёрч) утверждали: `bd gate --type human` с
`Timeout` и `Waiters` — готовый durable-примитив. Проверка:

| Утверждение | Реальность | Где |
|---|---|---|
| Гейт блокирует ветку | ✅ верно | `gate.go:375-382`, ребро `blocks` |
| Состояние durable | ✅ верно | в Dolt/git |
| `bd gate check` закрывает гейт | ❌ **`human` не проверяется вообще** | `gate.go:651-670`: `switch` знает `gh:run`, `gh:pr`, `timer`, `bead`, всё остальное — `default: continue` |
| `Timeout` эскалирует | ❌ **применяется только к `timer`** | `gate.go:944-950` |
| `Waiters` уведомляет | ❌ **поле пишется, читается на экран и всё** | во всём репозитории нет кода доставки |
| Эскалация встроена | ⚠️ есть, но шелл-аут в **`gt escalate`** — бинарь Gas Town | `gate.go:1008-1021` |

Разработчики Gas City это знают и написали прямо:

> «creating a `type=human` gate produces ZERO notification — the gate bead is
> built, the blocks edge is added, a line prints to stdout, and the human who
> must resolve it is never told (proven ABSENT in gascity/beads: gate creation
> has no post-create notify hook; **the only gate watcher skips human gates
> entirely**)»
> — `packs/core/orders/notify-on-human-gate-creation.toml:2-8`

Их же обходной путь мы и заберём: два ордера, `notify-on-human-gate-creation`
(на событие `bead.created`) и `renudge-stale-human-gates` (cooldown 5м,
re-nudge не чаще раза в час) — оба bash, оба шлют через `gc mail send --notify`
(`assets/scripts/gate-sweep.sh:28-29` подтверждает: подметаются только `timer` и
`gh`).

**Что это значит для нас.** Q21 отменил таймауты и напоминания — то есть
половина недостающего нам и не нужна. Остаётся написать: вопрос → гейт →
Telegram → ответ → закрытие гейта. Это наша работа при любой основе.

### 4.2. `[steps.gate]` в формулах — инертная конструкция

В спецификации есть отдельный раздел «Accepted But Inert»
(`formula-spec-v2.md:890-916`), где перечислены четыре конструкции, которые
парсятся и ничего не делают. Две касаются нас:

- **`[steps.gate]`**: сам гейт-бид создаётся и блокирует шаг, но значения `type`
  (`gh:run`, `gh:pr`, `timer`, `human`, `mail`) — «doc-comment vocabulary…
  the parser never validates them and no bundled watcher acts on them.
  **Zero bundled formulas use `gate`**».
- **`until`-цикл**: метка пишется, никто её не читает, цикл делает **ровно одну
  итерацию**. Для повторов надо использовать `check`.

Не баг, а честно задокументированная незавершённость. Но планировать «повесим
human-гейт в формуле» нельзя.

### 4.3. Неизвестные ключи: в конфиге — фатально, в формулах — молча

Это важно, потому что по Q40 флоу пишет агент.

- **`city.toml` / `pack.toml`**: любой неизвестный ключ — фатальная ошибка с
  подсказкой «did you mean» (`internal/config/undecoded.go:68-76`, `:151-158`).
- **Формулы**: `toml.Unmarshal(data, &formula)` без проверки `Undecoded()`
  (`internal/formula/parser.go:233`). Единственное исключение —
  `[steps.check]`, где ключи валидируются явно (`internal/formula/types.go:639,661`).

Вывод: **шаг «показать, что понял парсер» обязателен**, но нужен именно для
формул. `gc formula show <name> --json` есть (`cmd/gc/cmd_formula.go:82,89`),
падение конвейера на расхождении пишем сами.

### 4.4. Финалайзер ревью написан и никем не вызывается

`internal/reviewquorum` — чистая библиотека с 32 КБ тестов. Поиск по всему
репозиторию: **ни одного вызова `reviewquorum.Finalize` из production-кода.**
Формула это признаёт сама:

> «The `internal/reviewquorum.Finalize` Go finalizer is not invoked by this step
> yet.» — `mol-review-quorum.toml:183`

Синтез вердикта в поставляемой формуле делает агент. Пока переход состояния
решает LLM, кап циклов — рекомендация, а не гарантия. Хорошая новость: подключить
готовую и оттестированную функцию exec-чекером — работа на часы, не на недели.

Отдельно: контракта разрешения findings там нет. `Finding` — это
`Title/Body/File/Start/End/Severity/Lanes/Evidence` (`types.go:83-93`). Ни
`disposition`, ни `reason`, ни решения ревьюера по отказу. Подтверждает вывод
Q11: **готового нет ни у кого.**

### 4.5. Кап у Orca заканчивается не эскалацией

`stopPolicy` (`ReviewLoop.scala:41-63`): при `iteration >= maxIterations`
открытые issue сворачиваются в `ignored` с причиной `"max iterations (N)
reached"`, и **флоу едет дальше**. Это не «встала ветка и ждёт человека»
(Q14), это «сдались и поехали».

И там же зафиксирована арифметика, на которой легко налететь:

> «`maxIterations` counts FIX attempts, not evaluations, so a loop built on this
> policy performs up to `maxIterations + 1` evaluations.» — `:46-47`

Полезно сравнить с Gas City, где семантика другая: `max_attempts` — «Total
run/check attempts **including the first**» (`formula-spec-v2.md:661`).

**Пересчёт под Q13** («три правки автора, до четырёх проверок»): первая работа +
проверка, потом до трёх правок, каждая с проверкой = **4 запуска автора и 4
проверки**. В Gas City это `max_attempts = 4`. Ставить 3, читая «кап три», —
готовая ошибка на единицу.

### 4.6. extmsg маршрутизирует в живую сессию, а не в гейт

`internal/extmsg/` — реально реализованный слой: durable-биндинги
разговор↔сессия, транскрипты, группы, reaper, generic HTTP-адаптер. Но
`HandleInbound` (`inbound.go:147-232`) делает: найти адаптер → нормализовать →
резолвить биндинг/группу/дефолтный маршрут → **дописать в транскрипт живой
сессии** → выпустить событие. Сессии узнают о новом через
`gc transcript check --inject`.

Это «переписываться из Telegram с работающим агентом», а не «ответить на вопрос
и разблокировать ветку». У нас ветка на паузе, живой сессии нет. Склейка
«ответ → закрытие гейта» — наша.

Ещё две детали. Telegram-адаптер — это **отдельный процесс**, а не конфиг:
`HTTPAdapter.VerifyAndNormalizeInbound` возвращает ошибку, «out-of-process
adapters verify and normalize on their side» (`http_adapter.go:49-53`). И
регистрации адаптеров живут в памяти и **не переживают рестарт контроллера**
(`adapter_registry.go:15-18`) — адаптер обязан перерегистрироваться сам.

### 4.7. Чекер в `[steps.check]` — скрипт, не агент

`check.mode` поддерживает единственное значение `"exec"`, обязателен непустой
`check.path` (`formula-spec-v2.md:662-663`, валидация — `internal/formula/types.go:661`).
То есть в цикле «А сделал — Б проверил» роль Б исполняет **shell-скрипт**.

Значит наш ревьюер-агент запускается изнутри этого скрипта: скрипт диспатчит
свежего агента, дожидается, разбирает его структурированный вывод и возвращает
код. Это рабочая форма — но её надо спроектировать, а не «включить».

### 6.3. Дорого, но именно это и делает систему

Шесть работ. Ни одна не имеет готового аналога — это и есть ответ на вопрос
«что писать самим».

#### (1) Контракт разрешения findings — самое дорогое

Закрывает Q11, Q12, Q12a, Q17, часть Q9. Готового нет: у Gas City вердикт
бинарный, у Orca типизирован только отказ, у metaswarm — PASS/FAIL.

Минимальный состав:

| Поле | Зачем |
|---|---|
| Устойчивая идентичность finding между кругами | понять, что вернулся **тот же**, а не похожий. Ключ из `finalize.go:204-213` — про склейку параллельных линий, не про сквозную идентичность |
| `disposition`: `fixed` / `rejected` / `wont_fix` | что сделал автор |
| Обоснование отказа | текст автора |
| Решение ревьюера по отказу: принял / настаиваю | без него отказ = способ молча игнорировать |
| `severity` по фиксированной шкале | по ней принимается автоматическое решение об эскалации (Q12a) |
| Провенанс: кто нашёл, в каком круге, на какой ревизии | аудит и защита от stale approval |

Ложится в `Metadata` бида — форк beads не нужен. Обнаружение спора =
`rejected` + «настаиваю» + severity выше порога → эскалация.

Заготовки, которые сокращают работу: `IgnoredIssue(title, reason)` и
`FixOutcome(fixed, ignored)` из Orca, требование «каждый входящий issue попадает
ровно в один список», `unaccountedFor` и `ConfidenceGate` оттуда же.

**Оценка: 2-3 недели** с промптами и притиркой на реальных прогонах.

#### (2) Человеческий гейт от вопроса до ответа

Закрывает требование №4, Q18, Q19, Q22. Разобрано в 4.1 и 4.6: блокировка есть,
уведомления нет, обратного маршрута нет.

Цепочка: агент формулирует вопрос с вариантами и уверенностью → создаётся
гейт-бид → Telegram-сообщение → ответ (кнопка закрывает детерминированно,
свободный текст интерпретирует агент) → гейт закрывается → ветка едет.

Опора: bernstein `telegram.py` целиком, ордера Gas City как форма, `bd gate
create` / `bd gate resolve` как механика.

**Оценка: 1.5-2 недели.**

#### (3) Ревьюер-агент внутри цикла проверки

Закрывает требование №5, Q15, Q16. Из 4.7: чекер — exec-скрипт. Нужен скрипт,
который диспатчит **заведомо свежего** участника (по паре модель-провайдер, а не
по имени бинаря — Q27/Q28), дожидается, разбирает структурированный вывод,
пишет findings в бид и возвращает код.

«Свежесть должна обеспечиваться технически» (Q15) — значит скрипт обязан знать,
кто уже видел эту ревизию артефакта, и отказываться назначать его снова.

**Оценка: 1.5-2 недели.**

#### (4) Ревизии артефактов и неизменяемые попытки

Закрывает Q7 (артефакт в другом репозитории → связь по SHA), Q23 (ручная правка
рождает новую ревизию, апрувы предыдущей протухают), защиту от stale approval.

Форма — цепочка `design:A1 → review-B:A1 → revision:A2 → review-B:A2 →
review-C:A1`, без циклических зависимостей между бидами. Схема beads это держит
без расширения ядра.

**Оценка: 1 неделя.**

#### (5) Признак живости шага и убийство зависшего

Закрывает Q35. Нужен сигнал, отличающий «думает десять минут» от «завис» —
поток вывода или изменения файлов. Лизинг и heartbeat в beads
(`types.go:57-67`) — половина механики, вторая половина наша.

**Оценка: 0.5-1 неделя.**

#### (6) Маскировка секретов в транскриптах

Закрывает Q27a. Мы храним транскрипты сырыми, профиль передаёт токен через
окружение — без маскировки ключи от всех бэкендов окажутся в логах. Опора:
`env_isolation.py` из bernstein.

**Оценка: 2-3 дня.**

## 7. Альтернатива, если Gas City окажется неподъёмным

Довод против выбранного пути честный и весомый: 1301 Go-файл, автор называет
проект «100% vibe coded», а `refs/gascity/AGENTS.md` описывает не upstream, а
**форк с миссией интеграции** (Gas City + T3 Code + DoltLite-бэкенд beads) — то
есть в клоне лежит не нейтральный SDK. Мы берём оттуда пять подсистем из
семидесяти.

**План Б: `bd` + свой тонкий раннер на Go.** Тогда придётся написать самим:
управление профилями (пятиосевая модель — самое ценное, что мы теряем), диспетчер
control-бидов (check/retry/drain), жизненный цикл worktree, запуск и разбор
headless-вывода трёх CLI, транскрипты. По объёму это ещё 4-6 недель поверх
дорогой части — и результат будет заведомо беднее по профилям.

**Тревожные сигналы, при которых переключаемся:**

- эксперимент из раздела 8 не проходит пункты 1-2 без правки Go в `gc`;
- обновление `gc` ломает наш pack чаще раза в месяц;
- выясняется, что `subprocess`-рантайм не держит долгие шаги наравне с tmux.

**Что делаем в любом случае, чтобы план Б остался дешёвым:** правило «владелец
прогресса ровно один — beads». Всё состояние — в бидах и их `Metadata`, ничего
существенного в файлах Gas City. Тогда замена `gc` — это замена исполнителя,
а не потеря графа работы.

## 8. Что проверить экспериментом до того, как писать pack

Вертикальный срез, по убыванию влияния на решение. Каждый пункт — либо
подтверждает выбор, либо отменяет его:

1. **`[steps.check]` с `max_attempts = 4` и exec-чекером, который диспатчит
   агента-ревьюера.** Проверяем не то, что кап срабатывает, а что исход шага
   **читается ордером** и что на исчерпании можно повесить гейт.
2. **Гейт на биде: ветка встала, независимая ветка реально работает.** Это
   требование №4 целиком, и именно оно ломает большинство кандидатов.
3. **Профиль `claude-z` через `[upstreams]`**: запускается ли `claude` с
   подменённым `ANTHROPIC_BASE_URL` и получаем ли мы `glm-5.2`, попросив `opus`.
   Если да — Q27a закрыт конфигом, и это главный довод за Gas City.
4. **Убийство контроллера посреди шага и продолжение командой** (Q38): не
   создаются ли дубли, видно ли, что было завершено.
5. **`cursor-agent -p --output-format stream-json`** в реальном headless-прогоне
   на VPS: заводится ли по подписке без браузера (Q1b).
6. **`gc formula show --json` против намеренно испорченной формулы**: видно ли
   расхождение (4.3).

Пункты 1-3 стоит сделать до того, как форма пака зафиксируется. Остальное — по ходу.

## 10. Три отложенных вопроса — теперь можно ответить

Все три были отложены «до выбора стека» (`open-questions.md`, шапка).

### Q0. Одна кодовая база или две?

**A, и уверенность выросла с 75% до ~90%.** На выбранном стеке РабОрк и СвойОрк —
это **один pack и два города**: разные `city.toml`, разные `[upstreams]`, разные
рецепты проектов. Все семь накопленных различий (среда, права на git, куда пишутся
артефакты, параллельность, длительность) выражаются конфигом города, а не кодом.
Правило «различия только на периферии» получает механическую опору: попытка
развести поведение внутри цикла проверки означала бы два разных pack'а, и это
было бы сразу видно.

### Q10. Worktree или последовательно у СвойОрка?

**B на старте у обоих, A — дешёвое расширение потом.** Worktree-жизненный цикл
уже написан (`mol-scoped-work.toml`), fan-out есть (`[steps.drain]`), так что
включение параллельности — правка конфига. Но нерешённым остаётся то, что и
раньше: слияние параллельных веток с конфликтами. Если разрешение конфликтов
придётся поручать агенту со своим циклом проверки — это отдельная стадия
конвейера, и B выигрывает надолго. Начинаем последовательно, включаем `drain`,
когда появится задача, где это действительно больно.

### Q30. Служебные шаги — CLI, API или код?

**Код там, где детерминированно; агент там, где нужно суждение. Голый API не
нужен.** Стек даёт этому чёткую границу: детерминированное — это exec-чекер
control-бида (дедупликация findings, схлопывание вердиктов, переход состояния —
`reviewquorum.Finalize` уже написан), суждение — обычный шаг с профилем. Причём
переход состояния **обязан** быть кодом, иначе кап циклов остаётся
рекомендацией (4.4).

## Как пользоваться этим документом

Если новая проверка кода противоречит написанному здесь — правь **этот файл** и
дописывай в раздел 9, какое утверждение отменено. Раздел 9 — не признание в
ошибках, а рабочий инструмент: без него через месяц никто не вспомнит, почему
одно и то же утверждение то появляется, то исчезает.

Все ссылки вида `путь:строка` — на пинованные SHA из `refs/pinned.tsv`. При
обновлении клонов номера строк поедут; сначала перепроверь, потом правь.
