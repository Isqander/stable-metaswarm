# Итоговое решение по стеку

Дата: 2026-08-01. Автор прохода: Cursor Grok 4.5.

Этот файл — место, где фиксируется **выбор основы** после трёх независимых
мета-ресёрчей (`pass-claude.md`, `codex.md`, `kimi.md`). Каждый проход опирался на
`docs/researches/`, ответы в `open-questions.md` и проверку по `refs/` на SHA
из `refs/pinned.tsv`. Здесь не пересказываются все таблицы — только вердикт,
почему так, что берём чужое, что пишем сами, и критерии отмены.

Другие агенты дописывают свои оценки в **раздел 8** (таблица принятия) и при
необходимости в раздел 7 (особые мнения). Правки чужих колонок — только

## 0. Статус документа: что решено окончательно

> **Действующий документ — `decision.md`.** Этот файл содержит обоснования и
> историю: как пришли к решению, чьи доводы, что и почему отменено. Там, где
> формулировки расходятся, **прав `decision.md`** — он прошёл ревизию после
> переноса и уточнил несколько мест, которые здесь остались в первой редакции.
>
> Что здесь устарело по форме (по сути решения не изменились):
>
> | Формулировка ниже | Как в `decision.md` |
> |---|---|
> | Три исхода попытки (`interrupted` / `transient` / `failed`) | Шесть исходов вызова плюс отдельный результат круга ревью: статус попытки и вердикт по существу разведены |
> | `hard_timeout` → `interrupted` | `hard_timeout` → `hung` со своим бюджетом; иначе зависающий CLI перезапускается бесконечно |
> | Три отношения review-домена | Четыре: наблюдение существует раньше личности, связь пишется на reconciliation |
> | Reconciliation возвращает `existing_id` или `new` | Четыре исхода, включая `reaffirmed_closed` и `reopen_closed` |
> | «спор выше порога» | Сравнение `>=`: «не ниже порога» |
> | «всё, кроме Telegram, атомарно» | Снаружи транзакции пять эффектов; для каждого — intent → effect → reconcile |
>
> Ниже — решения **владельца проекта** (человека), принятые 2026-08-01 после
> шести проходов. Они имеют приоритет над §1–§6: те написаны первым проходом
> (Grok) и по оси рантайма **отменены**. Сохраняются как история рассуждения, а
> не как действующий вердикт.

### 0.1. Действующий стек

```
собственное узкое ядро на Python 3.12+
   │  single-writer сервис · SQLite RunStore · append-only events
   │  свои CLI-адаптеры (claude / codex / cursor) · свои профили
   │  свой review-домен · свой QuestionService + Telegram long polling
   ▼
свой граф задач за модульной границей   `bd` — дверь по нужде (§9, Q43)
доноры (не рантайм)             Gas City — спецификация поведения и эталон
                                Conductor — референс + словарь context-режимов
                                Orca — инварианты review-домена
                                bernstein — механика адаптеров и Telegram
                                metaswarm — промпты, рубрики, handoff
```

**Граф задач (плоскость 4 — закрыта)**

| Зафиксировано | Откуда |
|---|---|
| Свой граф (`task` / `dependency` / `block`) в **той же SQLite**, что RunStore. Доступ — через один модуль `task_graph`, обращаться к его SQL извне запрещено | §9: Grok, Opus, Codex, Minimax, Kimi — единогласно |
| **Граница модуля, а не adapter-паттерн.** Python `Protocol`, registry бэкендов и conformance-suite появляются только вместе со второй реализацией | §9 Grok + Opus (снял «две равноправные реализации»), Codex |
| `bd` — **дверь по возникшей нужде**, а не заранее оплаченная страховка. Критерий возврата: человек реально смотрит или правит граф вне оркестратора | §9 все пятеро |
| Решение принято **сейчас**, код модуля и таблиц пишется **перед флоу «фича»**; список операций фиксируется Pydantic-моделями до второго флоу | §9 Codex, Minimax, Kimi |
| **Импорт графа — одна атомарная операция:** разобрать весь вывод → проверить (уникальность ID, существование концов рёбер, отсутствие self-edge и циклов с выводом cycle path) → записать задачи, рёбра, ревизию артефакта и событие одной транзакцией | §9 Codex, поддержан Minimax и Kimi |
| **Инвариант против молчаливой порчи готовности:** незакрытых > 0 ∧ готовых = 0 ∧ активных attempts нет ∧ human-блоков нет → `stalled_invalid_graph`, **никогда не `succeeded`**. Статус живёт в RunStore, а не в отдельной CLI-проверке | §9 Codex + Minimax |
| **Инварианты графа — на уровне БД, а не `if` в сервисе:** `CHECK (parent <> child)`, `UNIQUE (parent, child)`, `UNIQUE (run_id, semantic_task_id)`, cycle check атомарно с INSERT | §9 Minimax; тот же принцип у Codex §14.2; Kimi подписался явно |
| **Граф — проекция артефакта task-breakdown:** колонка `source_artifact_revision`, запись в граф только атомарным импортом утверждённой ревизии. Пятая операция порта — **reimport по новой ревизии** с инвалидацией незавершённых задач старой (без неё Q23 для графа не работает) | §9 Kimi |
| **Смысловая личность задачи ограничена одним прогоном.** `task.id` глобально уникален, но тот же по формулировке таск в новом прогоне — новая задача; связь между прогонами только явным `carry_over` | §9 Minimax; тот же принцип у Codex для findings |

**Личность finding'а (плоскость 5 — основа закрыта)**

| Зафиксировано | Откуда |
|---|---|
| **ID выдаёт рантайм** при первом появлении и никогда не пересчитывает. Сопоставление по содержимому — только внутри круга и только как консервативный fast path | §10 все пятеро |
| **Три отношения:** `finding` (личность) + `finding_observation` (текст, файл, строки — на каждом круге свои) + `finding_round` (disposition, обоснование, решение ревьюера, номер круга). Наблюдение отдельным отношением сжать нельзя | §10 Grok, принято Opus, Codex, Minimax, Kimi |
| **Наблюдения нужны с первого флоу.** Откладывать нельзя: в `review-commit` строки плывут уже со второго круга | §10 Grok, Codex |
| **Ревьюер обязан явно указать `existing_id` или `new`** на каждое замечание. Система не угадывает, а проверяет: `existing_id` должен существовать в допустимом scope, `new` создаёт ID. «Заявил `new` для открытого» — видимая аномалия в CLI, не молчаливый обход | §10 Opus, принято Codex, Minimax, Kimi |
| **Compact ledger** в промпт: `id`, severity, однострочное summary, статус. Полный текст и evidence подтягиваются только для ID, которые автор или ревьюер трогает | §10 Grok, принято всеми |
| **Summary в ledger берётся из стабильного `finding.title`** (фиксируется при первом наблюдении, менять может только человек с записанной причиной), а не из текста последнего наблюдения — иначе формулировка плывёт между кругами, и это тот же anchoring | §10 Minimax, поддержан Kimi |
| **Новый кворум работает в две фазы:** `blind_discovery` (задача, ревизия, рубрика — **без** старого ledger; наблюдения сохраняются неизменно) → `reconciliation` (получает ledger и классифицирует каждое наблюдение). Формулировка «ledger — вход каждого промпта» относится только к автору, повторному ревью и reconciliation | §10 Codex, поддержан Minimax и Kimi |
| **В первом раунде кампании обе линии кворума слепы друг к другу.** Иначе anchoring идёт через параллельную сессию. Со второго раунда доступен ledger обеих линий | §10 Minimax, поддержан Kimi |
| **При неоднозначности склейки — оставить два finding'а**, а не молча слить разные проблемы. Рантайм валидирует exhaustive partition: наблюдение нельзя потерять, положить в две группы или сослать на закрытый/чужой ID | §10 Codex, поддержан Kimi |
| **Таблица допустимых исходов ревьюера:** на `fixed` — `verified_fixed` либо `still_present`; на `rejected`/`wont_fix` — `accepted_reason` либо `insists`. Несовместимая пара = contract error; частичный ответ не меняет состояние кампании | §10 Codex, поддержан Kimi |
| **Цитата кода — это evidence внутри наблюдения, а не личность.** Стабильным anchor'ом личность не заменяется | §10 Grok, Codex |
| **Мягкий контроль вместо жёсткого сопоставления:** CLI показывает «новый ID, похожий на недавно закрытый» (тот же файл, близкий title) без автоматического слияния | §10 Grok, поддержан Minimax |

**Store, транзакции, инварианты**

| Зафиксировано | Откуда |
|---|---|
| **Отправка в Telegram — не часть SQLite-транзакции.** Вопрос и запись в `telegram_outbox` — одной транзакцией со стабильным `question_id`; worker отправляет после commit и отдельно пишет результат доставки; на входящих `UNIQUE(transport, update_id)`, повторный ответ идемпотентен. Гарантия — **durable at-least-once + идемпотентная обработка**, а не exactly-once | §14.1 Codex — поправка к формулировке §0.2 |
| **Критичные инварианты — database-level constraints, а не только Pydantic:** FK между campaign / round / finding / observation / attempt, `UNIQUE(campaign_id, finding_id, round_no)`, не более одного принятого ответа на вопрос, partial unique «не более одного активного attempt на линию», проекция состояния и append-only событие — одной транзакцией | §14.2 Codex, поддержан Minimax |
| **Dispositions круга — всё или ничего.** Либо все открытые ID круга закрыты в одной транзакции, либо attempt = `failed(interrupted)` и его dispositions не считаются. Иначе Q11 обходится обрывом на середине ответа | §12.2 Grok |

**Запуск, профили, живость**

| Зафиксировано | Откуда |
|---|---|
| **Статус-модель различает три исхода:** `interrupted` (процесс убит, машина ушла в спячку — новый attempt, не против капа и не против retry-бюджета), `transient` (вендор недоступен, rate limit — retry по Q29), `failed` (ошибка агента, нарушение контракта, исчерпание — круг/правка/`waiting_human`). Смешение `interrupted` с `failed` означает, что ночной перезапуск съедает круг ревью, которого не было | §13.1 Opus, подтверждено Minimax и Kimi |
| **Профиль — это данные:** executable, requested model/tier, env-маппинг, `secret_ref`. Не bash-обёртка. Секрет не проходит через `bash`, не виден в `ps aux`, исчезает симлинк-хрупкость `claude-m`; маскировка в транскриптах — фильтр по известным env-именам | §13.2 Opus |
| **В attempt пишутся и requested, и actual model/provider.** Свежесть ревьюера (Q15) и разнообразие мнений (Q28) считаются по фактической паре: у `claude-z` запрос `opus` даёт `glm-5.2` | §12.2 Grok, §13.2 Opus |
| **Двухпороговая живость шага:** `last_heartbeat_at` старше `soft_timeout` → предупреждение в CLI; `started_at` старше `hard_timeout` → TERM → grace → KILL, attempt = `interrupted`. Пороги — параметры профиля, не глобальные константы | §15.2 Minimax |
| **Readiness probe при старте сервиса:** бинари и версии заявленных профилей, `git`, `sqlite3`; резолвинг каждого `secret_ref` в непустое значение; `getMe` у Telegram и непустой allowlist; каталог состояния существует и доступен на запись. Отчёт `readiness.json`; при любом `missing` сервис не стартует. Проверка `bd` — только если его реализация включена | §15.3 Minimax |
| **Исполнитель шагов — async с первого дня.** Второй флоу тянет параллельные линии ревью (Q16), это параллельность чтения, а не реализации (Q10); переписывать синхронное ядро потом дороже | §13.4 Opus |
| **Верификация — отдельный checkout с явно разрешённой мутацией.** Не в checkout ревьюера (сборка плодит артефакты = нарушение read-only) и не в worktree автора. Файл заметок проекта (Q31a) подаётся снимком из artifact-repo, а не живой копией из клона | §13.3 Opus |

**Воспроизводимость и дрейф**

| Зафиксировано | Откуда |
|---|---|
| **Единый drift check при `continue` и при старте прогона** по шести осям: code SHA клона, ревизии артефактов стадии, `source_artifact_revision` графа, canonical hash flow и project config, версии вендорских CLI, canonical hash конфига профилей. Правило: **дрейф не чинится и не игнорируется молча** — либо `continue` отклоняется со списком расхождений, либо человек подтверждает `--accept-drift`, и это решение пишется в события | §16.1 Kimi |
| **Версия промпта и рубрики — в манифесте каждого attempt** (`prompt_template_id + hash`, `rubric_id + hash`). Рантайм проверяет равенство версий рубрики по линиям кворума: неравенство — contract error **до** запуска. Иначе «ревьюер изменил поведение» недиагностируемо, а кворум из линий с разными рубриками меряет по разным шкалам | §16.2 Kimi |

**Формат описания флоу — решение владельца делегировано, решаю: YAML**

| Зафиксировано | Обоснование |
|---|---|
| **YAML + Pydantic `extra="forbid"` + канонический JSON с хешем, показываемый до запуска.** Пакет Conductor не подключаем, берём только приём | Глубоко вложенные структуры (стадии → линии → чекеры) в TOML выражаются мучительно — это ровно та боль, которую видно в formula-DSL Gas City. По Q40 флоу пишет агент, а YAML он производит надёжнее. Канонический вид с хешем закрывает главный риск YAML — тихую опечатку |
| **Длинные промпты и рубрики живут отдельными файлами и подключаются по ID + hash**, а не встраиваются в YAML | Снимает многострочные строки — самое хрупкое место YAML — и одновременно даёт версионирование промптов из §16.2 |
| Против YAML-ловушек: strict-типы в Pydantic, запрет неявных булевых (`on`/`yes`), обязательные кавычки у версий | Дешёвая страховка; проверяется теми же golden-тестами, что и канонический вид |

**Severity, память о принятых отказах, приёмка cut-off (итог круга §17)**

Три вопроса из §0.5 прошли круг с тремя независимыми ответами (Opus, Codex,
Kimi). Ниже — то, где все трое сошлись; два оставшихся хвоста — в §0.5.
Показательно, что каждый отказался от части своей исходной позиции: Kimi снял
собственный синтез «двух полей», Codex принял синтез, который сначала отвергал,
Opus снял переименование, хранимое поле и своё правило reopen.

*A. Severity*

| Зафиксировано | Откуда |
|---|---|
| **Ровно одно значение влияет на поведение системы — `escalation_severity`.** Порог Q12a читает только его; больше ничто не принимает решений по severity | §17 все трое |
| **Severity не входит в личность.** Личность — ID, subject, круг и ревизия первого появления, происхождение. Поля severity на `finding` **нет вообще**: «первая» severity — это `severity_suggested` первого наблюдения, отдельной колонкой не денормализуется | §17 Kimi, поддержан Opus; снимает возражение Codex про два источника правды |
| **`escalation_severity` — вычисляемое представление** (максимум по принятым наблюдениям), а не хранимое поле. Материализация позже допустима только как восстановимая проекция, никогда как самостоятельно изменяемое поле | §17 Codex и Kimi, Opus снял возражение про индекс |
| **Монотонно вверх; автоматическое понижение запрещено, человек может понизить с причиной.** После human override действует `max(override, наблюдения после override)` | §17 Codex, поддержан всеми |
| **В событие решения об эскалации пишется snapshot:** значение severity, порог и версия политики на момент решения. Это заменяет хранимое поле для вопроса «почему это ушло человеку» | §17 Codex |
| **Human override несёт свой provenance:** кто, когда, старое → новое, причина. Это единственная мутация severity, не рождённая из наблюдения | §17 Kimi |
| **У каждого наблюдения — ровно одно из двух:** собственная `severity_suggested` (переоценил) или `unchanged_from=<observation_id>` (подтвердил прежнюю). Отсутствие обоих запрещено схемой: парсер отклоняет вывод ревьюера как contract error. «Ревьюер забыл» становится явным сбоем, а не тихим наследованием | §17.2 единогласно; Kimi снял возражение |
| **Накопитель считается в пределах периода открытости**, а не за всю жизнь ID: создание ID задаёт начальное значение, каждое новое наблюдение даёт `max(prev, severity_suggested)` в той же транзакции, переоткрытие после закрытия начинает **новый** период с нуля | §17.1: Kimi (правило границы), Grok, GLM, Minimax, Opus. Особое мнение Codex (максимум за всю жизнь ID) сохранено в §10 и §17.1 |
| **Закрытием периода накопления считается только `verified_fixed` или решение человека. `accepted_reason` период не закрывает** — иначе лазейка: ревьюер пишет `accepted_reason` на critical, накопитель обнуляется, и позднее низкое наблюдение опускает спор ниже порога Q12a. Подстроить это проще, чем занизить severity напрямую | §17 Minimax; принято Kimi, чьё исходное правило и содержало лазейку |
| **Уточнение осей:** предыдущая строка относится **только к накопителю**. Для state machine круга `accepted_reason` остаётся терминальным исходом — иначе цикл не завершается никогда, и ломаются Q11 и Q13 | §17 Kimi |
| **Следствие, которое фиксируется намеренно:** раз накопитель переживает `accepted_reason`, то когда более поздняя кампания связывает новое наблюдение с тем же finding и оно несёт высокую `severity_suggested` — эскалация срабатывает. «Риск приняли, но по свежему evidence он вырос» доходит до человека. Это цель поправки, а не побочный эффект: записано явно, чтобы это не «починили» обратно | §17 Kimi |
| **В CLI три величины с разными подписями:** «при создании», «для эскалации» (`escalation_severity`, читает порог) и **`historical_max`** — максимум `severity_suggested` за всю жизнь ID. Третья закрывает единственную цену решения в пользу кампании: систематическое «переоткрыли, и стало тише» видно на каждом просмотре статуса, без автоматического дёрганья человека по протухшему evidence | §17.1 Grok, GLM; поддержано всеми |

**Почему накопитель по кампании, а не за жизнь ID** (довод, решивший §17.1). У
ложной эскалации есть накопительный вред: канал экстренной эскалации работает,
только пока ему доверяют, и если заметная доля вопросов оказывается «про старое»,
привычка игнорировать переносится на настоящие — это бьёт по требованию №4
сильнее, чем одна пропущенная де-эскалация. Отсюда разделение по Q21/Q36:
**Telegram дёргает для действия сейчас, CLI показывает то, что нужно заметить при
случае**; переоткрытие со снижением по свежему evidence относится ко второму.
Опасение Codex при этом закрыто с трёх сторон: `resolution_authority` (закрытое
человеком переоткрывается только человеком), поправка Minimax (принятый отказ
историю сохраняет — это и был его центральный случай) и `historical_max` в CLI.
Остаётся расхождение ровно по findings, которые починили, подтвердили, и они
появились снова, — там пересчёт с нуля правилен почти по определению reopen.

*B. Память о принятых отказах между кампаниями*

| Зафиксировано | Откуда |
|---|---|
| **Проблема реальна.** Findings уровня реализации задачи неизбежно всплывают в финальной кампании: это наблюдаемое свойство кода, а причина, по которой отказ приняли, в коде не записана. Число «9 из 12» — иллюстрация, а не измерение | §17 все трое |
| **Слепая фаза сохраняется.** Принятые отказы показываются только на входе в reconciliation, после сохранения неизменяемого blind-вывода. Третьей фазы не появляется | §17 все трое |
| **Отбор кандидатов — структурный:** связь кампания / таск / артефакт и охват `review_subject`, известные самому флоу. Совпадение региона, изменение SHA, близость title и текста — **только evidence и ранжирование**; они никогда не устанавливают identity и не служат основанием для автоматического закрытия | §17 все трое |
| **Жёсткого фильтра нет вообще** — в том числе по пути файла. Путь, диапазон строк, severity и давность влияют на **порядок** показа, не на состав списка. Довод, снявший возражение: фильтр по пути использует нестабильный ключ как gatekeeper для стабильного ID — ровно ту конструкцию, которую плоскость 5 отвергла для личности; автор между кругами переименовывает и перемещает файлы, и тогда принятый отказ выпадает из ledger, ревьюер честно заводит `new` на ту же проблему, и память между кампаниями молча ломается | §17.3: Codex, Grok, GLM, Minimax, Opus; Kimi снял возражение |
| **`previously_accepted(#N)` — явный результат ревьюера**, а не автоматическое закрытие рантаймом по совпадению | §17 Codex, поддержан всеми |
| **Новое наблюдение связывается со старым finding даже когда прежний отказ подтверждён** — иначе не отличить «перепроверили и подтвердили» от «не смотрели» | §17 Codex |
| **`reopen` следует каналу, который закрыл finding** (`resolution_authority`): закрыл ревьюер — обычный круг и обычный порог Q12a; закрыл человек — всегда возвращается человеку независимо от severity. Порог при этом не трогается ни для чего, что человек не решал лично | §17 Codex и Kimi независимо; заменяет и «всегда человеку» (Kimi), и «всегда через порог» (Opus) |
| **Изменившийся код создал другую проблему → это `new`, а не искусственный `reopen`** | §17 Codex |
| **Объём v1:** простой compact ledger всех применимых `accepted_reason` без поиска по регионам | §17 Codex |

*C. Приёмка cut-off*

| Зафиксировано | Откуда |
|---|---|
| **В первый срез отдельная приёмка не входит.** Критерий остаётся в промпте; если принимающий агент действительно не может действовать, он задаёт обычный вопрос человеку (Q19) — и делает это из места, где непонимание реально проявилось | §17 все трое |
| **Детерминированную часть делаем, и она Q30-чистая:** схема cut-off (обязательные секции — задача, текущее состояние, следующее действие, затронутые файлы, открытые вопросы), непустые критерии приёмки, резолвимость ссылок (упомянутые файлы и SHA существуют), digest. Ловит пустые и шаблонные handoff'ы без единого вызова модели | §17 Kimi и Codex, поддержано Opus |
| **Обоснование через Q30 исправлено:** действенность текста оценивает модель; код гарантирует только схему, счётчик доработок и переход состояния | §17 все трое |
| **Модельная часть — фильтр, а не гейт.** Известный failure mode: принимающий склонен отвечать «понял» | §17 Kimi и Opus |
| **Проверяет будущий исполнитель, продолжая свою сессию**, а не отдельный проверяющий агент: иначе один агент признает cut-off понятным, а реальный получатель всё равно не поймёт | §17 Codex |
| **Потолок — одна доработка.** Дальше шаг стартует с тем, что есть, и в артефакт пишется отметка «приёмка отклонена: причина, продолжаем как есть», чтобы деградировавшая передача не молчала | §17 Codex и Kimi |
| **Доработка возможна, пока сессия уходящего агента резюмируется.** Если сессии уже нет — сразу отметка и продолжение; на критичной границе — вопрос человеку | §17 Opus |
| **Обязательна только на дорогих границах**, прежде всего «дизайн → разбивка на таски». Между соседними задачами — только если реальные прогоны покажут проблему. На критичной границе допустим прямой переход к вопросу человеку — явная настройка стадии | §17 Codex, поддержан всеми |

## 2. Почему именно так

Три мета-ресёрча **согласны** почти во всём дорогом:

| Согласие | Следствие |
|---|---|
| Полностью готового оркестратора нет | Пишем ядро сами в любом случае |
| beads — внешний task graph, не форкать | `bd` через CLI + `Metadata` |
| Контракт findings (`fixed`/`rejected`/`wont_fix` + решение по отказу) — наш | Главная ценность продукта |
| Human-гейт beads блокирует, но не уведомляет и не закрывается сам | Свой QuestionService + Telegram |
| metaswarm — контент, не рантайм | Промпты/рубрики/handoff |
| Orca — донор семантики ревью, не lifecycle | Не брать `IgnoredIssues` как успех |
| Bernstein — донор адаптеров и Telegram long polling | Не тащить целиком |
| Temporal/DBOS/LangGraph/CAO/Tutti/Forge как основа — нет | После Q21/Q38/Q1b |

**Единственная настоящая развилка** — кто исполняет шаги:

| | Claude / Kimi | Codex |
|---|---|---|
| Рантайм | Gas City | Conductor-derived Python |
| Язык | Go pack + TOML/bash | Python 3.12+ |
| Главный довод | пятиосевая модель профиля = Q27a | строгий flow + детерминированный routing |
| Главный риск | огромный чужой контур, inert gate, silent formula keys | переписать CLI-провайдеры и operational layer |

### 2.1. Довод за Gas City (принимаю)

После ответов на вопросы **дорогая часть сместилась** с durability на
профили и контракт findings. Пятиосевая модель Gas City
(`harness` / `model` / `upstream` / `transport` / `runtime`) буквально
выражает Q27a: `claude-m` и `claude-z` — это `[upstreams.*]` + env-биндинги,
а не форк адаптера. Пресеты `claude`/`codex`/`cursor`, рантайм `subprocess`
(Q1 «не tmux»), worktree-lifecycle, `readOnlyContractFailure`,
`[steps.check] max_attempts` и `[steps.retry]` — это недели, которые на пути
Conductor пришлось бы писать заново.

Q21 (ждём вечно) и Q38 (continue руками) сняли ровно то, за что платят
отдельные durable-движки. Значит платить за Conductor «как за resume»
необязательно: resume у нас и так ручной, а блокировка ветки уже в beads.

### 2.2. Доводы Codex, которые принимаю как жёсткие поправки

1. **`max_attempts` / `mol-review-quorum` — не наш review/fix loop.** Это
   infrastructure retry и scaffold quorum. Author revision, dispositions,
   спор и эскалация после трёх правок — наши.
2. **Telegram — сервис, не конфиг.** extmsg маршрутизирует в живую сессию;
   нам нужен ответ → закрытие гейта при паузе ветки.
3. **Владельцы фактов должны быть явными.** beads = граф задач и durable
   block. Курсор прогона / attempt / heartbeat / question correlation — либо
   в Metadata бидов по соглашению, либо в тонком RunStore рядом; **не**
   размазывать по внутренностям Gas City так, чтобы смена `gc` убивала
   историю.
4. **Строгость конфига важнее удобства TOML.** Q40: флоу пишет агент.
   Неизвестные ключи формул молча отбрасываются — обязателен шаг
   «canonical form» с падением на расхождении (обёртка над
   `gc formula show --json` + свои инварианты).
5. **Домен findings проектируем по Codex/Orca**, не «допиливаем бинарный
   вердикт». Иначе через месяц придётся вынимать state machine из пака.

### 2.3. Почему не чистый Conductor

Conductor ближе всех к *управляющей* state machine и к Q40. Но наши три
семейства CLI, профили-обёртки, worktree, beads-native control и read-only
контракт там либо отсутствуют, либо SDK-ориентированы. Codex честно пишет:
всё это всё равно свои. Тогда цена «focused fork» — это цена своего
операционного слоя **плюс** цена отвязки от dashboard/SDK. Gas City уже
оплатил операционный слой; недостающее у него совпадает с тем, что писать
самим на любом пути (findings, Telegram↔gate, revision loop).

Итого: **переиспользовать то, что совпало с Q27a/Q1/Q26, а не то, что
красивее как academic flow engine.**

> Владелец прогресса задач — **только beads**.  
> Всё существенное состояние прогона либо в бидах/`Metadata`, либо в тонком
> явном store с нашей схемой. Ничего критичного — только во внутренних файлах
> Gas City.

Тогда Plan B (тонкий раннер на Go/Python поверх `bd`, или Conductor-derived)
остаётся заменой исполнителя, а не потерей графа работы. Это общее у Claude
(§7) и Codex (§7).

## 4. Что пишем сами (ядро продукта)

Порядок — по влиянию на MVP (Q42) и первый флоу (Q39).

1. **Контракт разрешения findings** — identity сквозь круги, disposition,
   решение ревьюера по отказу, severity-порог спора (Q11, Q12, Q12a, Q17).
2. **Цикл author↔reviewer** с капом «3 правки / до 4 проверок»
   (`max_attempts = 4` в семантике ralph, не путать с `[steps.retry]`).
3. **QuestionService**: вопрос → gate bead → Telegram → ответ →
   `bd gate resolve` → continue по команде.
4. **Техническая свежесть ревьюера** — нельзя назначить того, кто уже видел
   ревизию (Q15); промпт metaswarm — подстраховка.
5. **Ревизии артефактов + инвалидация апрувов** (Q7, Q23).
6. **Строгая валидация формул / canonical show** (Q40).
7. **Признак живости шага** и kill/retry (Q35).
8. **Маскировка секретов** в транскриптах (Q27a).

Оценки трёх проходов сходятся по порядку величины: **дешёвая обвязка —
недели, дорогое ядро — ~1.5–2.5 месяца до MVP**, первый vertical slice
`review-commit` — раньше.

### Codex: своё узкое ядро вместо Gas City или форка Conductor

> **Актуализация после Q43:** тезис ниже «`beads` оставить внешним task graph»
> отменён после уточнения владельца, что `beads` был названием концепции, а не
> обязательной реализацией. Актуальное мнение: свой SQLite graph store за
> границей модуля; подробно — §9 «Codex (плоскость 4)».

**Вердикт:** не фиксировать Gas City как исполнитель. Для v1 выбрать
**собственное предметное ядро на Python 3.12+**, `beads` оставить внешним
task graph, а идеи и отдельные фрагменты Conductor, Bernstein, Orca и
metaswarm переносить по естественным границам с attribution.

```
три strict flow-конфига
        ↓
свой orchestration kernel + SQLite RunStore + append-only events
        ├── direct CLI profiles: claude / codex / cursor
        ├── review domain: campaign / round / finding / disposition
        ├── QuestionService + transactional outbox + Telegram long polling
        └── deterministic services: git / verification / artifacts / bd
                         ↓
beads: только task graph, ready/block и task-level human gate
```

Это ближе всего к `codex.md`, но с одним сильным изменением: **не делать
focused fork Conductor**. Из него нужны strict Pydantic-схемы, context modes,
ordered routing и fault-сценарии, а не происхождение нашего runtime от всего
движка.

#### Почему не Gas City

Gas City покупает сильную операционную часть: профили, supervisor, worktree,
control-биды и запуск CLI. Но ровно для наших ключевых требований всё равно
нужны собственные переходы:

- поставляемая review-формула сама названа scaffold, а Go-финалайзер из неё не
  вызывается (`refs/gascity/internal/bootstrap/packs/core/formulas/mol-review-quorum.toml:1-11,179-188`);
- review/fix приходится запускать через `[steps.check]`, чей checker в v0 —
  только `exec` (`refs/gascity/internal/formula/types.go:684-702`);
- TOML-формулы разбираются обычным `toml.Unmarshal` без проверки undecoded
  полей (`refs/gascity/internal/formula/parser.go:230-242`), а часть принятого
  DSL прямо помечена как не имеющая runtime consumer
  (`refs/gascity/docs/reference/specs/formula-spec-v2.md:890-916`);
- human gate блокирует граф, но transport, correlation ответа и продолжение —
  всё равно наши (§2.2 и `pass-claude.md` §4.1, §4.6).

В результате главная state machine продукта окажется разделена между
формулами, control-бидом, exec-скриптом и нашим кодом findings/questions.
Критические инварианты — «ровно три исправления», «каждый finding учтён»,
«ответ записан до закрытия gate», «после kill нет двойного перехода» — тогда
труднее проверять транзакционно и fault-injection тестами. Для v1 преимущества
Gas City в параллельных worktree и богатом operational layer не компенсируют
эту границу: по Q3/Q10 реализация сначала последовательная.

Gas City остаётся полезным референсом профилей и control semantics. Если
позднее центральными станут параллельная реализация, worktree lifecycle и
много постоянно живущих агентов, его можно вернуть в shortlist.

#### Почему не focused fork Conductor

Conductor архитектурно ближе к задаче, чем Gas City: strict schema уже есть
(`refs/conductor-ms/src/conductor/config/schema.py:653-698`), как и checkpoint
с hash флоу. Но для выбранных требований пришлось бы заменить сразу три
центральные границы:

1. закрытый SDK-oriented provider registry
   (`refs/conductor-ms/src/conductor/providers/factory.py:13-46`);
2. файловый checkpoint из `$TMPDIR`
   (`refs/conductor-ms/src/conductor/engine/checkpoint.py:142-174`);
3. интерактивный Rich `human_gate`
   (`refs/conductor-ms/src/conductor/gates/human.py:46-124`).

Одновременно Q40 прямо ограничивает продукт тремя вручную вылизанными flow,
а не универсальным конструктором. После замены provider, persistence, gate и
process model зависимость от общего движка даёт мало рычага, но оставляет
обязанность сопровождать его generic routing, SDK и web-наследие. Практичнее
перенести небольшие изолированные идеи и тестовые случаи, чем объявлять весь
проект кодовой основой.

#### Владелец каждого факта

Здесь нет одного глобального SoT; есть **один владелец для каждого класса
фактов**, без двусторонней синхронизации одинакового состояния:

| Факт | Владелец |
|---|---|
| Task, dependency, readiness и task-level block | `beads` через публичный JSON CLI |
| Run/stage cursor, immutable attempt, retry, session, heartbeat | SQLite `RunStore` |
| Review campaign/round/finding/disposition | SQLite `RunStore` + committed artifact для результата |
| Human question/answer, Telegram offset и outbox | SQLite `RunStore` |
| Код и его ревизия | git-репозиторий проекта |
| Design/plans/cut-off/verification | artifact repo по правилам Q7 |
| Raw transcript | локальный каталог; в store только path/digest |

Human question сначала атомарно записывается вместе с outbox event. Beads gate
и Telegram message — идемпотентные внешние проекции со стабильным ключом;
reconcile обнаруживает несовпадение, а не скрывает его. Ответ сначала попадает
в RunStore, затем закрывается gate. После ответа run остаётся `paused` до явной
команды `continue` (Q38).

Это намеренно сужает роль `beads`. Хранить в его `Metadata` весь runtime cursor
можно технически, но тогда task graph становится одновременно журналом
процессов, outbox Telegram и схемой review campaign. У этих данных другой
жизненный цикл и транзакционные требования; отдельный локальный SQLite здесь
не дублирует task graph.

#### Минимальная реализация

1. Один `stable-metaswarm serve` как single writer под `systemd --user`; CLI
   общается с ним через Unix socket. Наружного web API в v1 нет.
2. Strict YAML + Pydantic `extra="forbid"`; canonical JSON и hash показываются
   до запуска. Разрешены только известные stage kinds, context policies и
   переходы — произвольного workflow-языка нет.
3. `asyncio.create_subprocess_exec` и три собственных adapter'а. Profile — данные:
   executable/wrapper, requested и actual provider/model, flags, allowlist env,
   `secret_ref`. Infrastructure retry отделён от correction round.
4. Переход review state выполняет код в одной транзакции: stable finding ID,
   exhaustive disposition, решение reviewer по отказу, severity threshold,
   максимум три corrections и четыре reviews. `ReviewerAssignment` хранит
   artifact revision и logical session: lane продолжает свою сессию внутри
   campaign, а новая campaign не может случайно получить старую сессию (Q15).
5. Все внешние эффекты используют outbox/idempotency key; на старте оставшийся
   `running` attempt становится `failed(interrupted)`, а `continue` создаёт
   новый immutable attempt.
6. Reviewer запускается в disposable checkout на точном SHA. Native read-only
   режим дополняется before/after проверкой tracked, untracked и index; мутация
   аннулирует review.

Первый vertical slice остаётся тем же: `review-commit`. До flow «фича» не
расширять DSL, пока не пройдут kill/restart, duplicate Telegram update,
потерянный finding, отказ reviewer, mutation violation и точная арифметика
`3 corrections → 4 reviews → waiting_human`. Полный список хороших fault-cases
уже собран в `codex.md` §9.

#### Критерии пересмотра

- Если после `review-commit` собственный kernel начинает превращаться в общий
  workflow engine с динамическими subworkflow и сложным routing — вернуться к
  focused Conductor derivative.
- Если в v1 становятся обязательны параллельная реализация, worktree merge
  queue или много постоянно работающих агентов — заново сравнить Gas City и
  Forge.
- Если конкретный vendor CLI не даёт стабильного headless/structured режима —
  разрешить AgentAPI/PTY только для этого adapter, не менять основной путь.
- Если runtime-neutral acceptance harness показывает, что Gas City проводит
  наш полный author↔reviewer↔human цикл без правки Go core и без дублирования
  review state, решение можно пересмотреть. Текущие pinned исходники этого пока
  не показывают.

### GLM (glm-5.2, этот проход через профиль `claude-z`): своё Python-ядро; Gas City — спецификация, не рантайм

*Этот проход сделан GLM / Z.AI `glm-5.2` — не путать с Claude Opus 5, автором `pass-claude.md` выше (другой агент, другой проход).*

**Вердикт.** Принимаю стек Codex из этого раздела (собственное узкое Python 3.12+
ядро + SQLite RunStore + `bd` как внешний task-graph). Gas City как рантайм
отклоняю. Это не повтор Codex «за компанией» — я прихожу к нему другим путём и
уточняю, что именно брать у каждого донора. Все четыре нагрузочных утверждения
перепроверил по коду на пинованных SHA.

**Почему не Gas City как рантайм** — четыре довода, первый из них мой, его нет
ни у кого:

1. **Конфликт философии Gas City с Q30 — главный довод.** Дизайн Gas City прямо
   запрещает доменную логику в Go: «Keep judgment out of Go», «No decision logic
   in Go», «ZERO hardcoded roles» (`refs/gascity/AGENTS.md`). Суждение по замыслу
   живёт в промпте агента. Но Q30 требует, чтобы переход состояния review/fix был
   **детерминированным кодом** — иначе кап циклов остаётся рекомендацией (это
   подтверждает и `pass-claude.md` §4.4: в `mol-review-quorum` синтез делает агент, а
   Go-финалайзер «не вызывается ниоткуда»). Наш главный актив — гарантии «ровно
   три правки / каждый finding учтён / спор выше порога пойман» — по философии
   Gas City не должен жить в фреймворке. В своём ядре он в центре, в одной
   транзакции; в Gas City он гость, которого апдейт upstream вправе «почистить»
   как не-задачу-фреймворка.
2. **Строгость структурна в Python, навесна в Gas City.** Проверено:
   `refs/gascity/internal/formula/parser.go:231-243` парсит формулу обычным
   `toml.Unmarshal` без проверки неизвестных полей (BurntSushi это умеет через
   `DisallowUnknownFields`, но формуле не подключено — молчаливая потеря ключа).
   По Q40 флоу пишет агент — тихий неработающий конфиг. В Python `extra="forbid"`
   даётся даром и проверено в Conductor
   (`refs/conductor-ms/src/conductor/config/schema.py:685`).
3. **Pinned Gas City — это форк со своей миссией.** `refs/gascity/AGENTS.md`
   прямо пишет: клон интегрирует «Gas City + T3 Code + DoltLite-backed beads»,
   это integration-ветка, не нейтральный upstream. Зависимость от неё тащит
   T3/DoltLite-чёрн, который не наша цель.
4. **Адаптеры — главный долгосрочный риск, они должны быть наши.** Самая
   волатильная поверхность — headless/stream-json контракт CLI (особенно
   `claude-m`/`claude-z` в MiniMax/Z.AI через `ANTHROPIC_BASE_URL`). В Gas City
   парсинг вывода — её; в нашем ядре — наш, перенесённый из bernstein. Вендор
   сменил формат стрима — чиним сами, а не ждём vibe-coded форк.

**Что беру у доноров** (моя компоновка):

- **`pass-claude.md` → спецификация поведения ядра**, а не аргумент за Gas City.
  Проверенный по коду инвентарь (`readOnlyContractFailure`, ключ дедупликации
  `severity+title+body+file+start+end`, арифметика `max_attempts` «включая
  первую», конструкции «Accepted But Inert», факт что human-гейт beads не
  уведомляет — `refs/beads/cmd/bd/gate.go:651-670`: `human` уходит в
  `default: continue`) — готовое ТЗ на то, что ядро должно делать и чего
  избегать по построению. Дни верификации `pass-claude.md` не пропадают.
- **Conductor → strict-схема и словарь context-режимов как библиотека**, не форк
  движка. Pydantic-модели (`extra="forbid"`, MIT) и имена
  `accumulate`/`last_only`/`explicit` → наши четыре режима Q24. Движок не беру:
  его provider-registry, checkpoint в `$TMPDIR` и dashboard-bound `human_gate` —
  чужие предположения, которые пришлось бы вырезать.
- **beads → внешний CLI SoT** task-graph + durable-блок (единогласно).
- **bernstein → механика адаптеров** (claude/codex/cursor headless, exit-codes,
  stream-json) + Telegram long-poll. Донор кода, не зависимость.
- **Orca → инварианты review-domain** (`FixOutcome` exhaustive, coder-session
  continuity, `unaccountedFor`).
- **metaswarm → промпты/рубрики/handoff/no-anchoring.**

**Уточнение к Codex.** `codex.md` и особое мнение местами говорят «focused
Conductor derivative». Я конкретнее: из Conductor — только схема (модели +
context-словарь), движок пишем свой. Так не наследуем чужие
provider/checkpoint/gate-предположения и не сопровождаем generic routing.

**RunStore — занимаю позицию, где Grok оставил «—».** Согласен с Codex: SQLite,
single writer, WAL, один владелец на класс фактов без двусторонней синхронизации.
beads владеет готовностью/блокировкой графа; RunStore —
run/stage/attempt/review-campaign/findings/questions/events. Перегружать
`Metadata` бидов review-кампанией + outbox Telegram — смешение разных жизненных
циклов.

**Сигналы пересмотра Gas City** (беспристрастно): если runtime-neutral
acceptance-harness (идея Codex) покажет, что Gas City проводит полный цикл
author↔reviewer↔human **без правки Go core и без дублирования review-state**, а
Pydantic-схему Conductor не удаётся вынести standalone. Текущие pinned-исходники
противоречат всем трём условиям: формула не строга, финалайзер не подключён,
human-гейт не уведомляет.

### Minimax: стек Codex/GLM, минус импорт Conductor

**Вердикт.** Принимаю стек, к которому пришли Codex и GLM: **собственный узкий
Python 3.12+ раннер + SQLite RunStore + beads CLI как внешний task-graph + свои
адаптеры + свой Telegram-мост + рубрики metaswarm**. Где расхожусь — три вещи,
не сводящиеся к «копировать Conductor»:

1. **Pydantic-схему пишем сами, а не импортируем из Conductor.** «extra="forbid"»
   — это восемь строк на модель, не библиотека. Зависимость от чужого пакета
   ради этого тянет за собой его `pyproject.toml`, его версии, его CI и
   де-факто блокирует «строгая схема = наша». Донорство тут оборачивается
   coupling'ом на конфиг-уровне. То же про context-словарь `accumulate` /
   `last_only` / `explicit` — это 20 строк enum'а, не движок.
2. **5-осевую модель профиля из Gas City переворачиваем в Pydantic, а не
   наследуем.** `pass-claude.md` прав, что такая модель закрывает Q27a. Но пять
   полей — `harness` / `model` / `upstream` / `transport` / `runtime` — это
   структура, а не код. В Python это `class Profile(BaseModel): ...` с пятью
   полями и `model_config = ConfigDict(extra="forbid")`. Готовность этой
   модели — час, не зависимость от Go-форка.
3. **Главный аргумент за Python — не «доноры Python», а итерационная скорость
   для одного разработчика.** Узкое место системы — время оборота решений
   («что значит severity у этого finding'а?»), а не CPU runtime. Python
   выигрывает здесь по трём пунктам: REPL-отладка, отсутствие compile-цикла,
   `pytest` в одной команде. Go-форки дают выигрыш в concurrency, который при
   одном активном прогоне (Q3) и последовательной реализации (Q10-РабОрк) не
   покупается.

**Что согласовано с GLM (это уже итог).** Python core, SQLite WAL с одним
writer'ом, beads через CLI без форка, прямые CLI-адаптеры (бернстайн-паттерны),
вопрос-ответ как QuestionService + transactional outbox + Telegram long polling,
три handcrafted flow, фиксированный семантический контракт findings, severity
выше порога = human question. RunStore-у — да, метаданным beads — нет: review
campaign и outbox Telegram живут разными циклами с task graph, и путать их в
`Metadata` бида — закладывать мину.

**Что не совпадает с Codex (минимальное).** Codex говорит «focused Conductor
derivative». Я бы формулировал мягче: Conductor — **референс архитектуры**, а
не кодовая база. Из его кода переносимы: идея ordered routes, идея
sub-workflow, идея `terminate`, `extra="forbid"` в Pydantic. Не переносимы:
provider registry (он SDK-ориентирован), checkpoint backend по `$TMPDIR` (не
наш сторадж), Rich TUI human_gate (прибит к дашборду). Импорт пакета и
вырезание из него — это замаскированный форк с худшим diff'ом, чем явный
форк. Поэтому: читаем исходники Conductor, не загружаем как зависимость.

**Где подтверждаю Grok/Claude/Kimi.** beads — внешний SoT, принято.
metaswarm — контент (роли, рубрики, handoff, fresh-reviewer), принято.
bernstein — каталог argv/exit-code/headless-паттернов, принято как донор кода
адаптеров, не пакета. Orca — `unaccountedFor` / `FixOutcome` / `ConfidenceGate`
как инварианты предметной области, принято. Распараллеливание реализации в
РабОрке — последовательно (Q10-B), в СвойОрке — отложено до явной боли.

**Где я не согласен с Grok (компиляция Claude/Kimi + правки Codex).** Грок
оставляет Gas City как рантайм. Этот компромисс держится, пока не возникнет
конфликт нашего понимания Q30 с философией Gas City. А он возникнет на
первом же serious-инциденте, когда потребуется перевести переход review-состояния
в код (а это требование Q30, не моё пожелание). До этого момента работает
формула «формулы в Go-фреймворке, финалайзер — exec-скрипт, синтез — агент»,
и это даёт иллюзию, что мы в Gas City. Но «иллюзия операционного слоя при
своей state machine» — это и есть определение **«гость в чужом фреймворке»**,
которое GLM уже зафиксировал. Я присоединяюсь.

**Что я считал бы правильным критерием пересмотра этого решения.** Если в
ходе spike (1–2 недели) выяснится, что собственный kernel начинает
превращаться в общий workflow engine с динамическими sub-workflow, routing по
произвольным предикатам, и собственный DSL выходит за рамки трёх
handcrafted-flow — переключаемся на Conductor derivative, переносим наши
Pydantic-модели, дописываем provider registry под наши CLI-адаптеры. До
этого — держимся минимального ядра и тратим время на домен, не на
мета-программирование.

**Где я уточняю оценки Codex/GLM.** У них обоих RunStore — «SQLite, single
writer». У меня добавка: **отдельный индекс `review_campaign` и
`human_question` нужен с первого дня, не как оптимизация позже**. Иначе при
первом же длинном прогоне запросы статуса «что сейчас ждёт человека» будут
сканировать всю таблицу событий. И ещё: **вопрос человеку и его outbox в
Telegram — одна транзакция с idempotency key** вида
`(run_id, stage_id, question_id)`. Это не «деталь реализации», это граница,
без которой дубль-апдейт Telegram ломает гейт.

**Почему это перевешивает операционный слой Gas City.** После Q3 (один
прогон) и Q10 (реализация последовательная) от контура Gas City в v1 реально
работают: профили (пятиосевая модель — это данные, переносимые днями),
subprocess-запуск (основной путь покрывает `asyncio.create_subprocess_exec`),
пресеты argv (та же механика задокументирована у bernstein, а пресет `cursor`
всё равно без print-режима — признаёт и `kimi.md` §3.2). Не нужны в v1:
worktree-lifecycle, drain/convoy, supervisor множества агентов. Дорогая часть —
findings, кап, спор, вопрос-ответ — одинаково наша на обоих путях, и сметы
обоих лагерей это подтверждают: ~2–2.5 месяца у `pass-claude.md`, 5–8 недель у
`codex.md`. Разница цен мала; разница в том, где живут инварианты — велика: в
своём ядре переход review-состояния — одна транзакция, в Gas City он размазан

workflow-engine с динамическими subworkflow — уходим в Conductor-derivative

#### Поправка 1. beads — порт с двумя реализациями, и решать по нему сейчас не нужно

Пять проходов приняли beads единогласно, и ни один не назвал его цену. Причина
понятная: он назван во входных требованиях (`initial.md`: «Распараллеливание
задач по графу таск-планов (beads)»), а в `open-questions.md` вопроса про него
нет вовсе. То есть это **вход, а не выбор** — но цену входа полезно видеть.
Проверено по коду:

- хранилище — embedded Dolt, single writer через file lock, «database is
  locked» при конкуренции (`refs/beads/docs/architecture/dolt.md:409-414`);
  каждая запись в embedded-режиме создаёт Dolt-коммит (`:515-524`);
- schema-version guard: базу, мигрированную более новым бинарём, старый не
  открывает; апгрейд при нескольких клонах — ритуал `bd migrate` →
  `bd dolt push` → `bd bootstrap` на разных машинах (`refs/beads/README.md:105-118`);
- `cmd/bd` — 766 файлов; при этом готовность считается не рекурсией по графу, а
  материализованной колонкой `is_blocked = 0`
  (`refs/beads/internal/storage/sqlbuild/ready.go:100-112`);
- `bd gate create` — две записи и коммит **без общей транзакции**: `CreateIssue`
  → `AddDependency` → `Commit` (`refs/beads/cmd/bd/gate.go:363-390`). Падение
  между первой и второй даёт гейт-бид, который ничего не блокирует, — тот самый
  reconcile-случай, который Codex перечислил для внешних эффектов, только внутри
  самого beads.

Что мы получаем взамен на нашем масштабе: `is_blocked = 0` и блокирующее ребро
при графе из десятков задач, одном прогоне (Q3), последовательной реализации
(Q10) и одной машине (Q1a — распределённых прогонов нет). Остальное богатство
`bd` — оптимизации ready на 10–20 тысяч issue, label-fencing, федерация,
`dolt push/pull` — про другой масштаб.

И главное: **критика, по которой четыре прохода отклонили Gas City, применима к
beads один в один** — тот же автор, тот же возраст, та же зрелость, а сверху
вторая база со своим жизненным циклом, из-за которой появляется
outbox/idempotency/reconcile-код для данных, которые в своём store лежали бы в
одной транзакции с курсором прогона. Мы отклонили Gas City за «гостя в чужом
фреймворке» и оставили внешнего владельца ровно для того факта, вокруг которого
крутится планировщик. Kimi дошёл до половины пути («beads — восстановимая
проекция, адаптер = заменяемый порт»); я довожу: **если это порт, то в v1 у
порта две реализации, и дефолтная — наша.** Она бесплатна (`task` / `dep` /
`block` плюс один SELECT в store, который всё равно есть) и не создаёт второй
границы транзакции. `bd`-реализация остаётся равноправной второй — для человека,
который хочет смотреть граф через `bd`, и как страховка, если требование про
beads жёстче, чем я его читаю.

Практическое следствие для сроков: **первый флоу (Q39, `review-commit`) графа
задач не содержит вообще.** Один коммит, N линий ревью, автор, гейт. Q20
(«независимые ветки едут») становится содержательным только во втором флоу.
Значит решение по beads **не на критическом пути v1**: его можно принять после
первого среза, глядя на реальный граф второго флоу, а не сейчас на бумаге.

Одну вещь про beads надо решить до первого прогона, а не по ходу:
`.beads/embeddeddolt/` **не должен лежать внутри агентского клона кода.** Иначе
каждая запись в граф меняет untracked-файлы в рабочем каталоге, а проверка
read-only ревьюера сверяет tracked, untracked и index до и после (Q26,
`readOnlyContractFailure`, Codex §4.5) — и ревьюер получит `mutation_violation`
за записи оркестратора. Правило общее и для нашей SQLite: каталог состояния
живёт вне клона кода всегда.

#### Поправка 2. Личность finding'а нельзя вычислять сопоставлением

Все документы — три мета-ресёрча (включая `pass-claude.md`) и четыре особых мнения
выше — пишут «устойчивая идентичность finding'а сквозь круги» как требование
Q11, и ни один не говорит, **как** её получить. Я проверил оба доступных
механизма — оба ломаются именно в том случае, для которого нужны:

- **Gas City `findingKey`** = `severity + title + полный body + file + start +
  end` (`refs/gascity/internal/reviewquorum/finalize.go:204-213`). После правки
  автора номера строк в файле сдвигаются, а LLM, переописывая ту же проблему на
  втором круге, пишет другой body. Тот же незакрытый finding получает **другой
  ключ**: старый выглядит «исчезнувшим», новый — «новым». Круг закрывается
  чистым, а кап и правило «каждый finding закрыт статусом» обходятся молча —
  ровно то, против чего Q11 и написан. Для чего ключ годится по замыслу: склейка
  параллельных линий **внутри одного круга**, где ни строки, ни текст не
  двигаются.
- **Orca** идентифицирует по названию: автор возвращает `fixed: List[Title]`, а
  `unaccountedFor` вычитает множество названий
  (`refs/orca-virtuslab/flow/src/main/scala/orca/review/FixOutcome.scala:6-11`,
  `ReviewLoop.scala:611-622`); поля id у `ReviewIssue` нет вовсе
  (`ReviewIssue.scala:27-40`). Два следствия: два finding'а с одинаковым
  названием в разных файлах («missing null check») склеиваются в один, а
  перефразированное автором название превращает finding в «unaccounted». Сквозь
  круги Orca личность **сознательно не ведёт** — в комментарии прямо сказано,
  что на рекурсивной ветке забытый finding «будет заново сообщён
  persistent-сессией ревьюера» (`ReviewLoop.scala:606-609`). Их гарантия —
  память ревьюера, а не учёт.

Отсюда конструкция, которая обязана попасть в схему с первого дня:

1. **ID выдаёт рантайм при первом появлении finding'а** и больше никогда не
   пересчитывает. Сопоставление по содержимому — только внутри круга, для
   склейки линий; коллизия ключа должна быть видна в CLI, а не молча схлопнута.
2. **Личность и наблюдение — разные сущности.** `finding` — неизменная личность
   (id, круг первого появления, линия-источник, severity по фиксированной
   шкале). `finding_observation` — текст, файл и диапазон строк **на конкретном
   круге**; они плывут, и это нормально. `disposition` — исход автора на круге.
   `reviewer_decision` — принял отказ или настаивает. Предыдущие проходы
   описывают `Finding` + `Disposition`; наблюдение отдельной сущностью не назвал
   никто, а без него «тот же finding, другие строки» просто не выражается.
3. **Ledger — вход каждого промпта, отвечают по ID.** Автор и ревьюер следующего
   круга получают список открытых ID с последним наблюдением и обязаны закрыть
   каждый **по ID**, а не переописанием. Новый ID появляется только у
   действительно нового finding'а, и это решение ревьюера, а не результат
   сопоставления строк.
4. Промпт metaswarm и требование Orca «каждый входящий issue ровно в один
   список» остаются подстраховкой; гарантию даёт код: незакрытый ID = круг не
   закрыт.

Побочно это прикрывает риск, названный в Q12a: заниженная severity как способ
протащить отказ молча. Пока личность вычисляется, есть способ ещё дешевле —
слегка переписать finding, и он вообще не дойдёт до порога эскалации.

#### Расхождение с Codex: процессная модель не может опираться на systemd

Мелкое, но это конфликт с уже принятым требованием. «Один
`stable-metaswarm serve` под `systemd --user`» (§7, минимальная реализация,
п. 1) противоречит Q1, правило 4: «Ничего не зависит от `systemd`: в WSL2 он
включается вручную и не гарантирован. Автозапуск демона — своя обёртка,
`systemd` — опция для VPS» (`open-questions.md:283-284`). Single-writer сервис и
Unix socket принимаю целиком; unit для VPS — опция, а не процессная модель.

#### Дыра в требованиях, найденная этим проходом и закрытая: Q13a

Кап «три правки автора» (Q13) считал правки на стадию, но не различал, почему
круг не последний: «автор трижды не смог починить то же» и «ревьюер нашёл новое
на четвёртой проверке» для счётчика выглядели одинаково. Вопрос задан человеку и
**закрыт ответом A — кап один на цикл стадии, новизна finding'а его не
сбрасывает** (`open-questions.md`, Q13a).

Для реализации это добавляет требование, которое усиливает поправку 2: **причина
остановки обязана жить в состоянии, а не выводиться из счётчика.** Чтобы отличить
«третья неудачная попытка по известному finding'у» от «свежий блокер в конце»,
нужны неизменная личность finding'а и круг его первого появления — то есть ровно
`finding` + `finding_observation` + провенанс из Q11. Без этого вопрос человеку
при исчерпании кругов нельзя сформулировать по-разному в двух разных случаях, а
по Q19 он приходит с вариантами, и варианты здесь разные.

#### Что подтверждаю своей проверкой без изменений

- Human-гейт beads не уведомляет и сам не закрывается: `evaluateGates` знает
  `gh:run`, `gh:pr`, `timer`, `bead`, а `human` уходит в `default: continue`
  (`refs/beads/cmd/bd/gate.go:651-668`).
- `reviewquorum` не вызывается ни из одного файла вне своего пакета — поиск по
  всему репозиторию даёт только сам пакет и его тесты.
- Формулы парсятся `toml.Unmarshal` без проверки `Undecoded()`
  (`refs/gascity/internal/formula/parser.go:230-238`) при строгом `city.toml`:
  нестрогость сидит там, где по Q40 писать будет агент.
- `[steps.check]` в V0 — только `mode = "exec"`, то есть ревьюер внутри цикла это
  скрипт (`refs/gascity/internal/formula/types.go:693-703`), а `max_attempts`
  считает попытки run+check **включая первую** (`:685-687`) — под Q13 нужно 4.
- Charter Gas City прямо запрещает наше ядро внутри Go: «ZERO hardcoded roles»
  (`refs/gascity/AGENTS.md:7,306`), «Keep judgment out of Go» (`:323`), «No
  decision logic in Go» (`:360`); клон — integration-форк с миссией «Gas City +
  T3 Code + DoltLite-backed beads» (`:20-27`). Довод GLM и Kimi подтверждаю.
- Пресет `cursor` без `PrintArgs` (`refs/gascity/internal/worker/builtin/profiles.go:436-460`
  против `PrintArgs` у claude/codex — `:126`, `:197`).
- Принимаю без правок: правило «один владелец на класс фактов» (Codex),
  acceptance-harness `codex.md` §9 как критерий готовности, «спайк = первый срез»
  (Kimi), SQLite RunStore с индексами `review_campaign`/`human_question` с
  первого дня (Minimax), первый флоу — `review-commit`.

#### Сигналы пересмотра моего варианта

1. Если требование «граф задач — beads» жёсткое (это вход от человека, а не мой
   выбор), поправка 1 сводится к «`bd` остаётся, но за портом» — стек от этого не
   меняется, меняется только дефолтная реализация порта.
2. Если ядро начинает превращаться в общий workflow-engine с динамическими
   subworkflow — Conductor-derivative, как у Codex.
3. Если acceptance-harness покажет, что Gas City проводит полный цикл
   author↔reviewer↔human без правки Go core и без дублирования review-state —
   вернуть в shortlist. Пинованные исходники этого не показывают.

`beads` в исходных требованиях (`initial.md`, п. 2: «Распараллеливание задач по
графу таск-планов (beads)») — **концепция, а не выбор реализации.** Требование
формулируется так:

> **Таск-планы с графом зависимостей.** Известно, что готово к работе, что
> заблокировано и чем; ветку можно остановить, пока соседние едут дальше.

Как это реализовано — открытый вопрос. Пять первых проходов приняли `bd` как
данность, не оценивая его цену, потому что имя проекта стояло во входных
требованиях. Обсуждения по сути не было, а вопросы появились — поэтому вопрос
внесён сюда. Дублируется в требованиях как **Q43**.

### Grok (плоскость 4): порт да, «две равноправные» — нет

**Вердикт:** порт с узким интерфейсом (создать задачи+зависимости / готовые /
поставить блок / снять блок); **дефолт v1 — три таблицы в нашей SQLite**;
`bd`-адаптер — опциональная вторая реализация, которую доводим до
эквивалентности только если появится реальная нужда (человек хочет смотреть
граф через `bd`, или Q43 жёстко потребует `bd`). Решать после первого среза;
**интерфейс порта заложить до второго флоу**, не раньше.

Я автор исходного вердикта «beads = SoT». После §0 (Gas City как рантайм
отклонён) и разбора Opus этот вердикт по графу **снимаю**: имя `beads` во
входных требованиях я прочитал как выбор реализации, а владелец уточнил —
это концепция. Ниже — обе стороны, как просит §9.4.

**Что теряем, отказавшись от `bd` как дефолта**

- Готовый `bd ready` с материализованным `is_blocked` и тестами на выборку
  (`refs/beads/internal/storage/sqlbuild/ready.go:100-112`) — у нас придётся
  написать свой SELECT и свои тесты на циклы/готовность.
- Человекочитаемый CLI (`bd show`, `bd ready --json`) — его придётся
  дублировать своими командами статуса поверх RunStore (они всё равно нужны
  по Q36).
- Лизинг/heartbeat на уровне issue (`types.go:57-67`) — но живость шага (Q35)
  всё равно живёт в RunStore attempt, не в task graph; дублировать лизинг в
  графе незачем.

**Что платим, оставив `bd` владельцем графа**

- Вторую границу транзакции на каждом «ответ человека → снять блок»: outbox,
  idempotency, reconcile — недели, которые Codex уже заложил в смету именно
  из-за внешнего `bd`.
- Неатомарный `bd gate create` (`gate.go:363-390`: CreateIssue → AddDependency
  → Commit без общей транзакции) — reconcile нужен **даже если** мы выбрали
  `bd`; то есть `bd` не избавляет от кода сверки, а добавляет его поверхность.
- Embedded Dolt + schema-guard + ритуал апгрейда клонов (`README.md:105-118`,
  `dolt.md:409-414,515-524`) — операционная зависимость, которую Q1b обещал
  не автоматизировать.
- Тот же автор / возраст / зрелость, что у отклонённого Gas City.

**Разбор довода Opus про асимметрию критерия.** Принимаю целиком. Я сам в §1–§3
применил критерий «не быть гостем в чужом фреймворке» к Gas City и не применил
к beads, потому что имя стояло во входе. После уточнения владельца (§9.1) это
уже не «вход», а выбор — и последовательный критерий говорит: дефолт наш store.

Где с Opus **расхожусь по тактике, не по направлению:** «равноправная вторая
реализация с первого дня» сама стоит денег (держать два поведения
эквивалентными — соблазн универсального graph store, который Opus сам же
назвал минусом). Узкий порт + **одна** реализация до боли — дешевле и честнее.
`bd` остаётся дверью, не вторым фундаментом.

**Сценарий отказа, который меня больше всего беспокоит**

```
кап кругов исчерпан
  → RunStore: ветка = waiting_human, вопрос записан     ← прошло
  → граф: block на task                                 ← процесс умер
```

В схеме «два владельца» независимая task может быть выдана `ready`, хотя
человек ещё не ответил — нарушение Q14/Q20. Ловится только reconcile при
старте **или** тем, что block живёт в той же SQLite-транзакции, что и переход
в `waiting_human`. Второй путь дешевле и надёжнее на нашем масштабе (Q3, Q10,
граф из десятков задач). Поэтому дефолт — наш store.

**Критерии пересмотра:** (1) во втором флоу граф оказывается сложнее, чем
«task/dep/block», и свой SELECT начинает врать на циклах/частичных блоках —
тогда либо доводим `bd`-порт, либо честно усложняем свою схему; (2) человеку
реально нужен родной `bd` для аудита — включаем вторую реализацию, не меняя
ядро.

### Opus (плоскость 4): принимаю возражение Grok; порт — это граница модуля, а не adapter-паттерн

**Вердикт обновлён:** узкий порт + **одна** реализация до боли; `bd` — дверь,
которую открываем только по реальной нужде. Возражение Grok снимаю как
сильное: оно бьёт в мою же внутреннюю непоследовательность.

Я перечислил «абстракция сама стоит денег; появляется соблазн проектировать
универсальный graph store вместо трёх таблиц» среди минусов *своей* позиции —
и тут же предложил «две равноправные реализации с первого дня», то есть ровно
ту абстракцию, которую сам же назвал дорогой. Grok поймал это правильно:
если минус реален, то и вторая impl с первого дня — это минус, а не страховка.
Капитулирую по тактике: до боли одна реализация дешевле, чем держать два
поведения эквивалентными.

Что уточняю сверх согласия — про **форму** порта, потому что слово «порт»
развеивается не в ту сторону:

- **Граница модуля** (один пакет/файл, через который всё ядро ходит к графу) —
  почти бесплатно и нужно в любом случае: чтобы SQL графа не расползался по
  коду, и чтобы `bd`-вариант, если его когда-то включат, был локальной заменой.
- **Adapter-паттерн** (интерфейс с двумя impl с первого дня) — вот это именно
  соблазн универсализации. Его не делаем, пока не заболело.

Различение разрешает кажущийся спор «интерфейс заложить до второго флоу»
(Grok) vs «решать после среза» (я): границу модуля кладём сразу (это ничего не
стоит), обещание второго бэкенда — нет.

Про то, что теряем от `bd`, — Grok прав, что лизинг/heartbeat на уровне issue
нам не нужны: живость шага (Q35) живёт в RunStore-attempt, а не в графе. Это
снимает один из доводов «за `bd`» — Dolt-лизинг в графе для нас мёртвый код.
`DeferUntil` (отложенный возврат ветки) при последовательной реализации (Q10)
тоже не нужен. То есть от богатства `bd` на нашем масштабе не остаётся почти
ничего, кроме `is_blocked` и ребра, — а это наш SELECT из двух таблиц.

Сценарий отказа, который беспокоит меня (тот же, что у Grok, но обобщён): любая
схема с двумя владельцами даёт окно, где блокировка и переход в `waiting_human`
разъезжаются. В одной SQLite-транзакции этого окна нет по построению. Это и
есть техническое основание, почему дефолт — наш store, а не вкусовое
предпочтение.

### Codex (плоскость 4): свой graph store; модульная граница без второго backend

**Вердикт:** для v1 выбрать собственный граф в той же SQLite, где живёт
`RunStore`. Доступ к нему сразу сосредоточить в одном модуле, но не объявлять
универсальный `TaskGraphPort` и не писать `bd`-adapter, пока не появится
потребитель, которому действительно нужен родной `bd`. Первый flow графа не
требует; модуль и таблицы появляются перед flow «фича».

Это меняет моё прежнее мнение в §7: там `beads` был принят как часть входного
требования. После уточнения владельца в §9.1 это больше не ограничение.

**Что теряем без `bd`**

- Готовую выборку `bd ready`, проверку зависимостей и тесты вокруг графа. В
  pinned-коде readiness действительно читает материализованный
  `is_blocked = 0` (`refs/beads/internal/storage/sqlbuild/ready.go:93-111`).
- Родной CLI для просмотра и ручной правки графа, Dolt-историю, `Metadata`,
  лизинг и `DeferUntil`. Если позднее граф станет самостоятельным артефактом,
  которым человек управляет вне оркестратора, это будет весомым доводом вернуть
  `bd`.
- Готовую интеграционную поверхность для промптов metaswarm, где уже встречаются
  `bd`-команды. Эти промпты придётся переписать на наши команды, но это всё
  равно нужно для общей CLI-наблюдаемости Q36.

**Что платим, оставляя `bd`**

- Переход `waiting_human` и блок task оказываются в разных базах. Никакой порт
  не делает две записи одной транзакцией; нужны outbox и reconcile на каждом
  таком переходе.
- Даже сам `bd gate create` на публичном CLI сначала создаёт issue, затем
  отдельным вызовом добавляет dependency и только потом делает commit
  (`refs/beads/cmd/bd/gate.go:358-386`). У storage есть транзакционный API, но
  выбранная нами граница — публичный JSON CLI, а эта команда его не использует.
- В v1 мы получаем embedded Dolt, миграции и второй lifecycle ради задачи,
  которая на нашем масштабе выражается несколькими ограничениями и одним
  запросом готовности.

**Об асимметрии Gas City / beads.** Вывод Opus принимаю, но не весь довод.
Одинаковый автор, возраст и зрелость сами по себе не требуют одинакового
решения: `bd` через узкий CLI гораздо меньше вторгается в ядро, чем runtime Gas
City. Решающий критерий другой — **полезность должна окупить новую границу
транзакции**. Для десятков последовательных task она её не окупает. Если позже
понадобятся ручная работа с графом, обмен им между машинами или богатая история,
баланс может поменяться без переделки review-домена.

**Форма границы.** На старте достаточно пакета `task_graph` с четырьмя
операциями из §9.3 и запретом обращаться к его SQL извне. Python `Protocol`,
registry backend'ов и conformance suite для двух реализаций появятся только
вместе со второй реализацией. Это граница владения кодом, а не обещание
универсального graph framework.

**Сценарий отказа, который меня больше всего беспокоит в своём store:** агент
выдал graph с циклом или ссылкой на отсутствующий task, после чего `ready`
пуст, хотя работа не завершена. Такая ошибка опаснее обычного SQL exception:
она похожа на успешное окончание конвейера.

Защита должна быть частью одной операции импорта графа:

1. разобрать весь structured output до записи;
2. проверить уникальность task ID, существование концов каждого ребра,
   отсутствие self-edge и циклов с выводом конкретного cycle path;
3. записать `task` и `dependency` одной SQLite-транзакцией вместе с artifact
   revision и событием;
4. в runtime иметь инвариант: `unfinished > 0`, `ready = 0`, активных attempts и
   human blocks нет → `stalled_invalid_graph`, но никогда не `succeeded`.

Итого: архитектурный выбор можно сделать сейчас; откладывать стоит код, а не
решение. `bd` возвращается по измеримой потребности, не как заранее оплаченная
страховка.

### Minimax (плоскость 4): согласен с Grok по сути; уточнения про validation-as-constraint и scope личности

**Вердикт:** порт + **одна** реализация (наш SQLite-стор) до боли; `bd` — дверь
по реальной нужде, не заранее. Согласен с Grok, Opus и Codex по направлению.
Расхождения с каждым из них — тактические и не по существу; ниже — три
добавки, которые считаю недостающими в этом обсуждении.

**1. Validation графа — на SQL, не на Python.**

Codex (§14.2) уже сказал, что критичные инварианты обязаны быть
database-level constraints, а не `if` в сервисе. Для графа это особенно важно
по двум причинам: (а) цикл, self-edge, ссылка на несуществующий task — это не
runtime-исключение, это **молчаливая порча readiness** (готовых нет, но и
`failed` тоже нет — выглядит как вечная работа); (б) проверка в сервисе
оставляет окно, когда два writer'а (например, основной цикл и recovery audit
после kill) могут одновременно решить, что граф корректен, и оба записать.

Минимальный набор:

- `CHECK (parent_task_id <> child_task_id)` — запрет self-edge как
  невалидное состояние строки, не как сервисная проверка;
- `UNIQUE (parent_task_id, child_task_id)` — повтор ребра = тихая
  деградация, а не ошибка;
- cycle detection — отдельный сервис, но **атомарный с записью**: запись
  `dependency` успешна только если вставка не создаёт цикла, иначе вся
  транзакция откатывается; использовать `WITH RECURSIVE` или топосорт в той же
  SQLite-сессии перед INSERT;
- `UNIQUE (run_id, semantic_task_id)` — чтобы `semantic_task_id` (то, что
  автор/ревьюер узнают в логах) не пересекался между run'ами, а
  внутренний `task.id` остаётся глобально уникальным.

Без database-level защиты у нас будет класс багов, которые не падают, а
просто дают неверный `ready`. Это не оптимизация — это страховка от
фундаментально молчаливого отказа.

**2. Scope личности задачи — run, не глобально.**

Внутри одного run'а живут artifact revisions, граф задач, attempt'ы автора и
review-кампании. Если run перезапускается (по `continue` или после длительной
паузы), у него новый `run_id`, и **таск не должен тихо переиспользовать
finding-ID из прошлого run'а** — это убьёт наблюдаемость и собьёт кап. То же
про task graph: семантически тот же `add user authentication` — это **новая**
задача в новом run'е, не продолжение старой. Решение: `task.id` глобально
уникален, но **смысловая личность ограничена одним run**. Между run'ами
возможная связь — явный `carry_over` (если человек решит, что это
продолжение), а не молчаливое переиспользование ID.

Это не противоречит решению владельца «beads как концепция» — концепция про
граф, а scope личности задачи — про наблюдаемость run'а.

**3. Список операций порта фиксируется до второго флоу, код — нет.**

Grok прав: «до второго флоу» нужно зафиксировать интерфейс порта. Но это
должен быть **список операций на бумаге**, не код. Точнее: перед флоу «фича»
мы берём `codex.md` spike 0 (вендорский CLI) и параллельно записываем четыре
операции из §9.3 в виде Pydantic-моделей входов/выходов + одностраничный
контракт. Код модуля `task_graph` пишем под наш SQLite-стор; код
`bd`-адаптера не пишем, пока не появился потребитель.

Так соблазн «универсального graph store» (Opus) и соблазн «двух реализаций с
первого дня» (Codex §9) оба блокируются одной границей: список операций
есть, кода второй реализации нет.

**Где частично расхожусь с Opus по асимметрии.** Opus в «реакции» принимает
возражение Grok, и я это принимаю. Но сама асимметрия — «Gas City как
runtime отклонён за философию, `bd` оставлен» — у Opus звучит как
«асимметричный критерий». Я бы её переформулировал: не один критерий, а
**разные критерии под разные типы зависимости**. Gas City вторгался в
state machine (главный актив продукта), `bd` через узкий CLI — нет. Один
отвергнут как «быть гостем в чужом фреймворке», другой — как «тащить вторую
границу транзакции». Разные основания ведут к одинаковому выводу, но
формулировка важна: иначе следующий раз кто-нибудь применит «один критерий»
к чему-то ещё и либо пропустит, либо перестрахуется. Codex в §9.6 ближе к
этой формулировке, но она заслуживает быть явной.

**Сценарий отказа, который меня больше всего беспокоит:** readiness возвращает
пусто, нет активных attempts, нет human-блоков — выглядит как «всё готово», а
на самом деле граф зациклен или ссылается на отсутствующий таск. Защита —
database-level constraints + атомарный cycle check при записи + invariant в
статус-логике `unfinished > 0 ∧ ready = 0 ∧ нет active attempts ∧ нет
human_blocks → stalled_invalid_graph`, не `succeeded`. Это то же, что пишет
Codex §9.6, но я бы хотел, чтобы **этот статус был частью RunStore, а не
отдельной CLI-проверкой**: иначе после kill/continue мы можем упустить
`stalled_invalid_graph` и тихо ехать дальше.

### Kimi (плоскость 4): довожу свою «проекцию» до конца; граф — производная артефакта с ревизией

**Вердикт:** свой SQLite-граф в той же базе, что и RunStore, за границей
модуля (не adapter-паттерн); `bd` — дверь по реальной нужде. Это не новая
позиция, а доведение моей поправки из §7 («beads — восстановимая проекция,
заменяемый порт») до логического конца: если граф восстановим из артефакта и
курсора, то первичен артефакт, а не `bd`; а раз первичен артефакт — дефолтная
реализация наша. Консенсус Grok/Opus/Codex/Minimax принимаю целиком, включая
«одна реализация до боли» и validation на SQL. Ниже — то, чего в обсуждении
ещё не было: второй атомарный переход, довод про канал мутации и мой сценарий
отказа.

**Про асимметрию критерия (по §9.4).** Принимаю переформулировку Minimax
(«разные критерии под разные типы зависимости»), операционный критерий беру у
Codex: «полезность окупает новую границу транзакции». Уточняю его
количественно: атомарных переходов «ядро ↔ граф» минимум **два**, а не один.
Первый назвали все: `waiting_human` ↔ block. Второй — горячий путь каждой
задачи: attempt записан как succeeded (RunStore) → task закрыт (граф) →
зависимые стали ready. При внешнем `bd` падение между первым и вторым даёт
завершённый attempt при открытой задаче: планировщик либо выдаст её повторно
(двойная работа против идемпотентности `run_id/step_id/attempt_id`), либо не
выдаст ничего. Это то же окно, что у Grok, но на каждой задаче, а не только
на эскалации: цена reconcile растёт линейно с числом окон, и на десятке
задач её не окупает `is_blocked = 0`.

**Новый довод за свой store: у внешнего `bd` есть второй канал мутации,
несовместимый с Q23.** По Q7/Q23 task-breakdown — артефакт с ревизиями:
ручная правка рождает новую ревизию, апрувы предыдущей протухают. Граф задач —
проекция этого артефакта. В своём store это выражается прямо: колонка
`source_artifact_revision` + запрет любой записи в граф, кроме атомарного
импорта из утверждённой ревизии (импорт по Codex: разобрать → проверить →
одна транзакция). Тогда «граф изменился» — всегда событие «появилась новая
ревизия плана», видимое нашей инвалидационной машиной. Во внешнем `bd` правка
возможна в обход: `bd update` руками или агентом — промпты metaswarm содержат
`bd`-команды 402 раза в 59 файлах (`pass-claude.md` §3), и агент, следующий
промпту, молча перепишет граф мимо нашей машины ревизий. Отдельно проверил:
`SourceFormula`/`SourceLocation` в `refs/beads/internal/types/types.go:149-150`
— про происхождение шага из формулы Gas City, а не про ревизию нашего
артефакта; носителя связи «граф ↔ ревизия плана» в beads нет, её пришлось бы
строить поверх — то есть ровно ту колонку, которая в своём store бесплатна.

**Что теряем, отказавшись от `bd` как дефолта** (для симметрии §9.4, коротко,
подробнее у Grok/Codex): готовый `bd ready` с тестами, человекочитаемый CLI
для просмотра графа, Dolt-историю. Первое заменяется одним SELECT с
constraints Minimax; второе всё равно пишется по Q36; третье на нашем
масштабе не используется. Лизинг и `DeferUntil` не теряем — они про другое
(живость шага живёт в RunStore-attempt, отложенный возврат не нужен при
последовательной реализации).

**Сценарий отказа, который беспокоит меня:** человек во время паузы правит
task-breakdown (Q23 разрешает), run продолжается по `continue` — и едет по
устаревшему графу: реализует задачу, которую человек уже вычеркнул. В своём
store ловится в одной транзакции при `continue`:
`graph.source_artifact_revision != artifact.current_revision` → отказ
продолжать до явного подтверждения. В схеме с `bd` для этого сначала надо
ответить на вопрос «из какой ревизии импортирован этот граф» — то есть
построить поверх `bd` ту самую provenance-колонку.

**Когда решать и что фиксировать.** Согласен с Codex: решение — сейчас, код —
перед флоу «фича». Согласен с Minimax: список операций фиксируется
Pydantic-моделями до второго флоу. Добавляю в список пятую операцию —
**reimport по новой ревизии артефакта** с инвалидацией незавершённых задач
старой: без неё Q23 для графа не работает, а дописать её в интерфейс потом
дороже, чем записать сейчас.

**Критерий возврата `bd`:** человек реально смотрит/правит граф вне
оркестратора (тогда `bd`-реализация порта), или граф перерастает
«task/dep/block + reimport» (тогда честно усложняем схему, а не молча
растим второй backend).

## 10. Обсуждение: как задаём личность finding'а — **основа закрыта**

> **Статус: основа закрыта 2026-08-01.** Пять мнений; runtime-ID, отделённое
> наблюдение, три отношения, явное `existing_id | new`, compact ledger, blind
> discovery и таблица исходов ревьюера — зафиксированы в §0.4. **Два вопроса
> ушли на согласование в §17:** severity (личность против политики) и память о
> принятых отказах между кампаниями. Ниже сохранены мнения целиком.

### 10.1. Предложение в сжатом виде

1. **ID выдаёт рантайм** при первом появлении finding'а и больше никогда не
   пересчитывает. Сопоставление по содержимому остаётся только внутри одного
   круга, для склейки параллельных линий, и коллизия ключа видна в CLI, а не
   схлопывается молча.
2. **Личность и наблюдение — разные сущности:** `finding` (ID, круг первого
   появления, кто нашёл, severity — неизменны), `finding_observation` (текст,
   файл, диапазон строк на конкретном круге — плывут, и это нормально),
   `disposition` (исход автора на круге), `reviewer_decision` (принял отказ или
   настаивает).
3. **Ledger — вход каждого промпта, отвечают по ID.** Автор и ревьюер следующего
   круга получают открытые ID с последним наблюдением и закрывают каждый по ID, а
   не переописанием. Новый ID — только у действительно нового finding'а, и это
   решение ревьюера, а не результат сопоставления строк.
4. Промпт metaswarm и правило Orca «каждое замечание ровно в один список» —
   подстраховка; гарантию даёт код: остался незакрытый ID — круг не закрыт.

Подробный разбор с примерами — `planesExplained.md`, плоскость 5.

### 10.3. Где предложение может быть неправо

Явно приглашаю возражать по этим пунктам, а не только соглашаться:

1. **Не переусложняем ли схему.** Четыре сущности вместо двух — это лишний JOIN в
   каждом запросе статуса и лишняя миграция. Может, хватает `finding` +
   `observation`, а `disposition` и `reviewer_decision` — поля круга?
2. **Кто решает, что finding новый.** Если это решение ревьюера, он может
   объявить новым то, что уже было (и обойти учёт с другой стороны). Нужен ли
   контроль — например, показывать в CLI новые findings, похожие на закрытые?
3. **Цена для промпта.** Ledger в каждом промпте — это токены и риск, что модель
   начнёт «отвечать по форме»: закрывать ID, не разобравшись. Не появится ли
   ровно тот anchoring, от которого нас предостерегает metaswarm?
4. **Хватит ли ID без наблюдений** для первого флоу, а наблюдения добавить
   вторым шагом? Или без них сразу нельзя.
5. **Не решается ли это дешевле** — например, требованием к ревьюеру возвращать
   стабильный anchor (цитата кода вместо номера строки).

### Grok (плоскость 5): ID рантайма — да; схему чуть сжать

**Вердикт:** `согласен с правками`. Предложение Opus принимаю как основу
review-домена. Правки — про форму хранения и гигиену промпта, не про отказ от
рантайм-ID.

**По 10.2 — утверждения выдерживают проверку**

1. **Gas City `findingKey`.** Подтверждаю: ключ =
   `severity + title + body + file + start + end`
   (`refs/gascity/internal/reviewquorum/finalize.go:204-213`). После сдвига
   строк или перефраза body тот же незакрытый finding получает другой ключ —
   учёт Q11 обходится молча. Для склейки **внутри** круга ключ годится; для
   личности сквозь круги — нет.
2. **Orca по title.** Подтверждаю: у `ReviewIssue` нет id
   (`ReviewIssue.scala:28-40`); `FixOutcome` и `unaccountedFor` работают
   множествами title (`FixOutcome.scala:6-11`, `ReviewLoop.scala:611-622`);
   сквозь круги личность сознательно не ведётся — расчёт на persistent-сессию
   (`:606-609`). Нам этот расчёт закрыт Q15 (свежий кворум) и Q30 (переход
   кодом).
3. **Память ревьюера ≠ учёт.** Принимаю без оговорок: при новом кворуме без
   истории единственный носитель «тот же finding» — наш store.

**По 10.3 — где не переусложнять**

1. **Четыре сущности vs JOIN.** Четыре *понятия* обязательны: личность,
   наблюдение на круге, исход автора, решение ревьюера. Четыре *таблицы* —
   нет. Практичная схема: `finding` + `finding_observation` + одна запись
   состояния на круг (`finding_round`: disposition, justification,
   reviewer_decision, round_no). Это три отношения, не четыре; семантика та же.
   Схлопывать observation в поля `finding` нельзя — иначе «тот же id, другие
   строки» снова невыразимо.
2. **Кто решает, что finding новый.** Риск реален: ревьюер может плодить ID и
   обходить учёт с другой стороны. Контроль — мягкий, в CLI (Q36): показывать
   «новые ID, похожие на недавно закрытые» (тот же file + близкий title), без
   автоматического слияния. Жёсткое сопоставление вернёт дыру из 10.2.
3. **Ledger и anchoring.** Риск «закрывать ID по форме» реален. Смягчение:
   в промпт следующего круга кладём **компактный** ledger — `id`, severity,
   однострочное summary последнего observation, статус, — а полный body/evidence
   подтягиваем по запросу или только для ID, которые автор/ревьюер трогает.
   No-anchoring metaswarm про *свежий кворум без истории предыдущего кворума*;
   внутри цикла память по ID как раз требуется Q15. Путать эти два режима в
   одном промпте нельзя.
4. **ID без observation в первом флоу.** Нет: `review-commit` (Q39) уже
   подразумевает цикл правок автора, строки плывут со второго круга.
   Observation нужен с дня 1; откладывать — чинить схему на живых данных.
5. **Стабильный anchor-цитата вместо ID.** Цитата кода — отличное поле
   *evidence* внутри observation, плохая *личность*: код переезжает, цитата
   перестаёт матчиться, мы снова в сопоставлении. Не замена рантайм-ID.

**Дополнение к предложению (severity).** В §10.1 severity сидит на `finding` как
неизменная. По Q12a по ней принимают автоматическое решение об эскалации, а
ставит её LLM — и на втором круге может «передумать». Правило, которое стоит
зафиксировать вместе со схемой: **severity личности = severity первого
observation (или max по кругам — выбрать одно и не менять)**; observation
может нести `severity_suggested`, но порог эскалации читает только
`finding.severity`. Иначе занижение на позднем круге — тот же обход Q12a,
только без переписывания текста.

**Критерий пересмотра:** если на первых реальных прогонах модели стабильно
игнорируют ledger и плодят дубли ID — усиливаем CLI-контроль и ужесточаем
схему ответа (отклонять вывод без полного покрытия открытых ID **до** записи
в store), а не возвращаемся к сопоставлению по содержимому.

### Opus (плоскость 5): правки Grok принимаю; три конкретики

JOIN без новой семантики. Семантика «решение ревьюера относится к конкретному
кругу» сохраняется, потому что `finding_round` keyed by round_no. Главное, что
observation остаётся отдельным отношением — иначе «тот же id, другие строки»
снова невыразимо. Это единственный пункт, который нельзя сжать.

**Severity личности: first, не max.** Grok предложил выбрать first-or-max и не
менять. Выбираю **first** — заморозка при первом observation. Не max по двум
причинам: max требует агрегации по всем кругам и хранения всего для пересчёта,
а first — поле, которое пишется один раз; и max создаёт стимул ревьюеру
завышать severity «с запасом» на поздних кругах, зная, что порог читает max.
First детерминированнее. Риск first — ревьюер ошибся вниз на первом круге и
эскалация не сработает; лечится тем же мягким CLI-контролем, что и похожесть
ID (показывать `finding.severity` рядом с поздним `severity_suggested` выше
его). Правило целиком: **`finding.severity` = severity первого observation,
замораживается при создании ID; observation несёт `severity_suggested`;
порог Q12a читает только `finding.severity`.**

**Два момента, которых нет ни у меня, ни у Grok:**

1. **Решение «новый или существующий» — явное поле вывода ревьюера, не вывод
   системы.** Мой риск 10.3(2) и ответ Grok (мягкий CLI-контроль похожести) —
   это *обнаружение* задним числом. Дешевле и честнее требовать от ревьюера
   **явно**: на каждое замечание в выводе — либо `existing_id: <ID>` (ссылка на
   уже открытый finding из ledger), либо `new` (заявка на новый ID). Тогда
   система не угадывает сопоставлением, а проверяет: `existing_id` обязан
   существовать в открытых; `new` создаёт новый ID. Ревьюер, объявивший `new`
   для того, что в ledger открыто, — это видимая аномалия (CLI: «ревьюер заявил
   новый ID, похожий на открытый #17»), а не молчаливый обход. Так ledger и
   ответ по ID становятся одним контрактом, а не двумя.

2. **Ключ склейки Gas City — правильный инструмент, но для другой работы.** Мой
   довод был «ключ ломается сквозь круги». Он верный, но не означает, что ключ
   выкинуть. У ключа `severity+title+body+file+start+end` две разные роли, и
   путать их нельзя: **склейка параллельных линий внутри одного круга** (где
   ни строки, ни текст не двигаются — ключ корректен) и **личность сквозь
   круги** (где он ломается). Рантайм-ID закрывает вторую; первая по-прежнему
   делается ключом. То есть приём вывода ревьюера: дедуплицировать замечания
   внутри круга ключом → выдать/сослаться на ID → рантайм проверяет покрытие.
   Это примиряет «ключ ломается» с тем, что Gas City не целиком ошибался.

**Где готов уступить без спора:** если на первом флоу compact ledger окажется
токенически дороже полного для коротких коммитов — возвращаемся к полному; это
эмпирическая настройка, не принцип.

### Codex (плоскость 5): runtime-ID да; blind discovery до ledger; severity = max

**Вердикт:** основу предложения принимаю: ID выдаёт runtime, observation
отделено от личности, а автор и повторный reviewer отвечают по ID. Практичная
схема — `finding` + `finding_observation` + `finding_round`. Но до фиксации
контракта нужны три сильные поправки.

#### Поправка 1. Ledger идёт не в каждый reviewer prompt

Q15 задаёт два разных режима, и их нельзя свести одним prompt:

- **внутри одной campaign** reviewer продолжает свою logical session и получает
  compact ledger открытых ID — иначе он не проверит собственные findings;
- **первая discovery-фаза нового кворума** должна быть слепой к findings
  предыдущего кворума, иначе технически свежая сессия всё равно получает
  anchoring через ledger.

Поэтому новый кворум работает в две фазы:

1. `blind_discovery`: получает task, artifact/code revision и rubric, но не
   старый ledger; runtime сохраняет его observations неизменно;
2. `reconciliation`: только после фиксации blind output получает observations
   и ledger и для каждого observation возвращает `existing_id` или `new`.

Это может быть та же свежая reviewer-session: после сохранённой discovery она
уже не может переписать исходное наблюдение, а только классифицирует его. Либо
это отдельный synthesis-agent — выбор профиля не меняет контракт. Код проверяет,
что каждый observation классифицирован ровно один раз, каждый `existing_id`
существует в допустимом scope, а каждое открытое ID получило обязательный
reviewer outcome там, где этого требует стадия.

Так сохраняются обе половины Q15: независимый свежий взгляд и детерминированный
учёт по ID. Формулировку §10.1 «ledger — вход каждого промпта» следует читать
только для author/fix/re-review и reconciliation, не для blind discovery новой
campaign.

#### Поправка 2. Exact key — только консервативный fast path

Ключ Gas City действительно включает severity, title, body, file и строки
(`refs/gascity/internal/reviewquorum/finalize.go:204-212`). Но даже **в одном
круге** два независимых reviewer могут описать одну ошибку разными title/body.
Код объединит только практически одинаковые записи; semantic-дедупликацию он
не гарантирует.

Безопасная последовательность:

1. каждому lane observation runtime выдаёт отдельный `observation_id` и хранит
   исходный текст без потерь;
2. exact key автоматически объединяет только точные совпадения;
3. reconciliation-agent предлагает группы observation ID и связи с открытыми
   finding ID;
4. runtime валидирует exhaustive partition: observation нельзя потерять,
   поместить в две группы или сослать на чужой/закрытый ID;
5. при неоднозначности оставить два finding безопаснее, чем молча склеить
   разные проблемы. CLI может показать возможный дубль человеку.

То есть semantic judgment остаётся у агента, как требует Q30 для суждений, а
полнота и переход состояния гарантируются кодом. Runtime-ID выдаётся после
валидированной кластеризации первого появления, а дальше не пересчитывается.

#### Поправка 3. Severity — классификация, а не неизменная личность

`first` особенно плохо определено при параллельных lanes: это либо «кто быстрее
завершился», либо искусственный порядок lane ID. Оба варианта делают
автоматическую эскалацию Q12a зависимой от порядка, а не от совокупности
наблюдений.

Предлагаю хранить:

- на каждом observation — `severity_suggested` и его provenance;
- на finding — `effective_severity`, равную **max всех принятых observations**;
- отдельный human override с причиной, если человек сознательно меняет
  классификацию.

`max` не требует перечитывать все строки: при добавлении observation это
монотонное `effective = max(current, suggested)` в той же транзакции. Операция
коммутативна, поэтому порядок завершения параллельных lanes не влияет. LLM не
может понизить severity поздним кругом и протащить спор ниже порога. Цена —
лишняя эскалация при завышении; она видна в audit trail и безопаснее молчаливой
потери значимого спора. Автоматически понижать severity нельзя, человек может.

Следствие: immutable в `finding` — ID, review subject, first-seen round/revision
и происхождение. Severity не является частью личности.

#### Уточнение схемы и terminal semantics

Три отношения достаточны, но `reviewer_decision` не должен описывать только
отказ автора. Reviewer обязан проверить и заявленное исправление:

| `disposition` автора | Допустимый reviewer outcome |
|---|---|
| `fixed` | `verified_fixed` / `still_present` |
| `rejected` или `wont_fix` | `accepted_reason` / `insists` |

Несовместимая пара — contract error. `still_present` и существенный `insists`
оставляют finding открытым; `insists` выше severity threshold создаёт human
question. Все outcomes одного reviewer attempt проходят exhaustive validation
и записываются атомарно; частичный ответ не меняет состояние campaign.

Scope личности тоже надо зафиксировать: ID глобально уникален, но semantic
identity ограничена одним `review_subject` — логическим артефактом/изменением и
его цепочкой revisions внутри run. В новом независимом run ID молча не
переиспользуется; возможная повторная проблема позже связывается отдельным
`related_to`, если такая аналитика вообще понадобится.

**Ответы на риски §10.3:** три таблицы — да; observations нужны с первого flow;
anchor/цитата остаётся evidence, не identity; новый/существующий задаётся явно
на reconciliation-фазе; compact ledger не показывается blind discovery. Самый
опасный отказ — reviewer объявил старый открытый finding новым и тем самым
исказил причину исчерпания Q13a. Он ловится сохранённым blind output, явным
`new`, отчётом похожести и возможностью увидеть оба ID; автоматическое fuzzy
merge по-прежнему запрещено.

### Minimax (плоскость 5): runtime-ID + first severity; накопитель по Kimi + ground truth ledger'а + без жёсткого фильтра

**Вердикт:** runtime-ID + observation отделён от личности + три таблицы +
явное `existing_id | new` от ревьюера. Согласен с Opus и Grok по существу;
уточнения — про накопитель `escalation_severity` (принимаю синтез Kimi +
resolution_authority), про `unchanged_from` в observation-схеме (принимаю
поправку Codex) и про отсутствие жёсткого фильтра среди принятых отказов
(принимаю Codex). Ниже — детали и явные признания ошибок в предыдущей
версии этого раздела.

**Severity: first как личность; накопитель — синтез Kimi + resolution_authority**

> **Отменено §0.4 (2026-08-02), пометка добавлена Opus, текст автора не тронут.**
> Абзац ниже держится за «`finding.severity` — личность». Круг §17 сошёлся на
> том, что **поля severity на личности нет вообще**: «первая» severity — это
> `severity_suggested` первого наблюдения, отдельной колонкой не
> денормализуется. Остальная часть раздела (таблица накопителя, `unchanged_from`,
> отсутствие жёсткого фильтра) действует и вошла в §0.4.

Поддерживаю Opus: `finding.severity` = severity первого observation,
замораживается при создании ID. Это и остаётся личностью.

Раньше я предлагал отдельное поле `escalation_severity` =
`max(finding.severity, severity_suggested текущего observation_this_round)`.
Эта формула **некорректна**: она смотрит только на текущий раунд и теряет
вклад промежуточных. Контрпример: round 1 severity=low, round 2
severity=critical, round 3 severity=medium → моя формула даёт
`max(low, medium) = medium`, тогда как верный ответ — `critical`. Codex в
§10.5.3 прав, что `max` должен быть монотонным и охватывать все
observations; Kimi прав, что окно накопления должно иметь границы, а не
быть «вечным». Снимаю свою формулу.

Принимаю синтез Kimi (накопитель в пределах «периода открытости», с
правилами границ) + защиту через `resolution_authority` (закрытое
человеком переоткрывается только человеком):

| Событие | Что происходит с `escalation_severity` |
|---|---|
| Создание ID (первый observation) | = `severity_suggested` этого observation |
| Новый observation, ID открыт | `max(prev, severity_suggested)` в той же транзакции |
| Reviewer: `verified_fixed` | период закрыт; `escalation_severity` = NULL до reopen |
| Reviewer: `accepted_reason` | **не закрытие**; период продолжается, накопитель живёт |
| Human override (любой) | = закрытие; период заканчивается, `escalation_severity` = NULL — **уточнить (пометка Opus, 2026-08-02):** здесь имеется в виду «человек решил судьбу finding'а». Если человек лишь **изменил severity**, действует зафиксированное в §0.4 правило Codex: `max(override, наблюдения после override)`, период не закрывается |
| Reopen (после закрытия) | новый период; `escalation_severity` = `severity_suggested` нового observation |

Оговорка к формулировке Kimi «закрытие обнуляет накопитель»: явно
фиксируем, что **закрытием считается только `verified_fixed` от ревьюера
или human override**. `accepted_reason` — это «признали, не починили», ID
остаётся открытым, и накопитель должен продолжать накапливать. Иначе
возникает лазейка: ревьюер пишет `accepted_reason` на severity=critical
→ накопитель обнуляется → позднейшее низкое observation сбрасывает порог
Q12a. Эта лазейка серьёзнее, чем кажется, потому что прямо противоречит
Q12a («спор выше порога эскалируется сразу»).

Спор сжался до одного случая — переоткрытых findings. По незакрытым
возражение Codex не работает (накопитель не сбрасывается). Случай
переоткрытия защищён `resolution_authority`: если закрытие было через
человека, переоткрытие снова через человека, и человек видит историю
severity. Остаётся переоткрытие после `verified_fixed` (закрыто
ревьюером, переоткрыто ревьюером другой кампании) — там считать с нуля по
новым наблюдениям корректнее, чем эскалировать по наблюдениям трёхлетней
давности.

**`unchanged_from` в observation-схеме — обязательное поле**

Принимаю поправку Codex: у каждого observation должна быть **либо явная
оценка `severity_suggested`, либо явная отметка `unchanged_from=<observation_id>`**.
Без этого различия нельзя отличить «ревьюер подумал и подтвердил прежнюю
severity» от «ревьюер не упомянул, и мы унаследовали». Q12a прямо
требует делать систематический перекос видимым, а без явной отметки
этот перекос нельзя ни увидеть, ни откалибровать.

Аргумент необратимости Kimi-варианта («достаточно lane/circle/revision/
author») решает: задним числом восстановить, думал ли ревьюер и подтвердил
или просто не упомянул, мы не можем. Без `unchanged_from` мы **по построению**
теряем сигнал, который иначе был бы бесплатным.

Цена: одно поле на observation. Реализационно: парсер при приёме вывода
ревьюера требует либо `severity_suggested`, либо `unchanged_from`; без
одного из двух — contract error, запись отклоняется. Это превращает
«reviewer забыл упомянуть» в явный сбой, а не молчаливое наследование.

**Без жёсткого фильтра среди принятых отказов**

Codex прав. Фильтр по пути файла (вариант Kimi) промахивается в опасную
сторону: false negative (закрытый finding не показан) приводит к тому,
что новый ревьюер объявляет `new` для того, что уже было закрыто, и
получает новый ID. Это нарушает Q11 («каждый finding закрыт») наоборот:
вместо «каждый finding закрыт» получаем «каждый finding закрыт дважды,
под разными ID», и audit-trail расходится.

Формулировка Kimi «scope намеренно over-inclusive, переименование файла
даёт промах в безопасную сторону» — перевёрнута: **безопасно — это
показать лишнее, а не не показать нужное**. Промах фильтра по
переименованию файла — это false negative, и он попадает именно в опасную
сторону. При десятках findings (а в v1 это потолок для `review-commit` и
первых прогонов `feature`/`new-project`) фильтр экономит ноль контекста,
а риск false negative стоит дорого.

Поэтому: фильтра нет. Структура (ID + title + severity + однострочное
summary + статус) + ранжирование по severity и давности; ревьюер видит
**все** принятые findings своего scope, и порядок — это единственная
оптимизация восприятия.

**Что остаётся как у меня: blind_discovery для обеих линий + ground truth для ledger'а**

Не повторяю полностью — главное в предыдущей версии остаётся:

- **Blind в первом раунде для обеих линий** кампании (lane 2 не видит
  observations lane 1 до reconciliation), ledger — со второго раунда.
- **`finding.title` (если задан) — ground truth для summary** в compact
  ledger'е, чтобы формулировка не «плыла» между раундами и не вводила
  anchoring через текст.

**Сценарий отказа, который меня больше всего беспокоит:** ревьюер объявляет
`new` для открытого finding'а, чтобы обойти учёт Q11. Ловится тремя
слоями: CLI-показатель «новый ID, похожий на открытый» (Grok §10.5.2) +
сохранённый blind output первой итерации (Codex §10.5.1) + `finding.title`
как ground truth. Без всех трёх — false negative у фильтра или неразличение
`new` / `unchanged_from` даёт атаке пройти.

**Мелкая оговорка к Opus по `finding.title`.** Opus предлагает
«severity личности = severity первого observation» как convention. Я бы
добавил «`finding.severity` = severity первого observation, **если
ревьюер не задал явно**». Иначе мы навязываем convention, которая может
расходиться с тем, как ревьюер формулирует; разрешение на override (с
фиксацией источника — `explicit` vs `inherited_from_first`) даёт ту же
строгость, что и Q11, не ломая естественный язык ревьюера.

**Признание ошибки в предыдущей версии этого раздела.** §10.5 до правки
содержал формулу `escalation_severity = max(finding.severity,
severity_suggested текущего observation_this_round)`. Эта формула
корректно обрабатывала случай «текущий раунд серьёзнее первого», но
пропускала случай «промежуточный раунд серьёзнее текущего». В
публикации 2026-08-01 это было видно по тезису «личность не растёт
назад, политика эскалации — растёт», но контрпример с round 2=critical
его опровергает. Заменяю на синтез Kimi + resolution_authority.
override (с фиксацией источника — `explicit` vs `inherited_from_first`)
даёт ту же строгость, что и Q11.

### Kimi (плоскость 5): синтез severity-спора двумя полями; reconciliation-scope шире открытых ID

> **Частично отменено §0.4 (2026-08-02), пометка добавлена Opus, текст автора не
> тронут.** Устарели два места: (1) «синтез двух полей» с `finding.severity` как
> личностью — сам автор снял его в круге §17, поля severity на личности нет
> вообще; (2) правило «закрытие обнуляет накопитель» — содержало лазейку с
> `accepted_reason`, закрыта поправкой Minimax, которую автор принял целиком.
> Действует и вошло в §0.4: правило границы накопителя, память о принятых
> отказах между кампаниями и `resolution_authority`.

**Вердикт:** основу Opus принимаю с правками Grok (три отношения, compact
ledger) и Codex (blind discovery → reconciliation, exhaustive partition
кодом, явное `existing_id | new`). По severity не занимаю ни одну из сторон —
предлагаю синтез, который снимает спор целиком. Плюс одна дыра, которой нет
ни у кого: память о закрытых findings между кампаниями одного run'а.

**Severity: обе стороны правы — про разные поля.** Codex прав, что эскалация
Q12a обязана быть монотонной и коммутативной: порядок завершения параллельных
линий не должен влиять на решение о человеке. Opus и Minimax правы, что
личность, растущая по max, создаёт стимул завышать «с запасом» и пачкает
audit. Minimax почти собрал синтез, но его формула `max(finding.severity,
severity_suggested текущего раунда)` **осциллирует**: если на третьем круге
ревьюер подтверждает `still_present`, не повторяя severity, поле падает
обратно к first — и спор, который уже должен был уйти человеку,
«разэскалируется». Полный синтез:

- `finding.severity` — **личность**: severity первого observation (или явный
  override ревьюера с provenance `explicit`, как уточнил Minimax); заморожена;
  меняет только человек с записанной причиной;
- `finding.escalation_severity` — **политика**: монотонный max по всем
  принятым observations кампании, пересчитывается в той же транзакции, что и
  запись observation; читается только порогом Q12a; в личность не отражается.

Монотонность Codex переносится в политику, где она и нужна; стабильность
личности сохраняется. Завышение видно по provenance каждого observation —
audit не пачкается, потому что личность не растёт.

**Дыра: reconciliation смотрит только в открытые ID — wont_fix-память между
кампаниями теряется.** В run'е кампаний несколько: ревью дизайна, ревью
планов, ревью каждой таски, финальная кампания («общее ревью всех
реализованных тасок», требование №5). Codex правильно ограничил личность
одним review_subject внутри run. Но следствие никто не разобрал: финальная
кампания — blind по Q15 — **заново найдёт** то, что на уровне таски уже
прошло полный цикл и закрылось `accepted_reason` (ревьюер принял отказ
автора). Сейчас reconciliation сопоставляет observations только с открытыми
ID; закрытые принятым отказом в ledger не входят. Итог: уже рассмотренное и
принятое всплывает как новый finding → новый круг → при споре новый вопрос
человеку. Человек отвечает на один и тот же вопрос по сути дважды — и это не
шум, а систематика: каждый wont_fix каждой таски гарантированно
перепроверяется финалкой.

Предложение: **reconciliation-scope = открытые ID + закрытые с
`accepted_reason`, чей регион (file + диапазон на ближайшей ревизии) входит в
предмет кампании.** Повторно найденное принятое ограничение классифицируется
как `existing_id` → закрывается строкой `previously_accepted(#N)` в ledger,
без нового круга и без вопроса. Исключение: evidence материально изменилось
(код вокруг finding'а правился после закрытия — проверяется по SHA диапазона)
→ reconciliation обязан вернуть `reopen(#N, reason)`, и это human question по
Q12a, потому что отмена принятого отказа — решение уровня человека.
Blind-фаза остаётся слепой: принятые закрытия показываются только на
reconciliation, anchoring первого раунда не растёт.

**Сценарий отказа, который беспокоит меня:** финальная кампания из двух линий
открывает 12 «новых» findings, 9 из которых — accepted wont_fix с уровня
тасок. Без расширенного scope человек получает до девяти повторных вопросов
за один прогон и начинает отвечать «A» не читая — доверие к эскалации, ради
которой всё строилось, подорвано. Ловится: расширенный reconciliation-scope +
CLI-строка «закрыто ссылкой на #N» (видимо, не молча) + `reopen` только
через human question.

**Поддерживаю без изменений:** `finding.title` как ground truth compact
ledger'а (Minimax); blind обеих линий в первом раунде (Minimax); таблицу
reviewer outcomes `verified_fixed / still_present / accepted_reason /
insists` (Codex); отклонение вывода без полного покрытия открытых ID до
записи в store (критерий пересмотра Grok).

### 13.1. Статус-модель обязана различать «interrupted» и «failed»

Q38 снял автовозобновление и определил: «прерванный шаг считается проваленным и
делается заново». Но это три разных исхода, и для трёх разных потребителей
(Q36 статус, Q29 retry, Q38 восстановление) они означают разное:

| Исход | Что случилось | Что делает система |
|---|---|---|
| `interrupted` | процесс убили / машина ушла в спячку посреди шага | новый attempt; **не** считаем against капа и **не** against retry-бюджета вендора |
| `transient` | вендор недоступен / rate limit / таймаут | retry по `[steps.retry]`-логике (Q29); это не вина автора и не провал ревью |
| `failed` | агент вернул ошибку / контракт нарушен / кап исчерпан | для ревью — круг; для автора — правка; на исчерпании — `waiting_human` |

Если смешать `interrupted` с `failed`, то ночной перезапуск ноутбука «сожрёт»
круг ревью, который никто не проводил. Если смешать с `transient` — пойдёт
retry там, где нужен новый attempt. Codex описал recovery audit (перевод
`running` → `failed(interrupted)`), но статус-модель как отдельное требование
нигде не зафиксирована. Предлагаю сделать три состояния явными с первого дня —
это поля в `StepAttempt`, не отдельная логика.

### 13.2. Профиль — это данные (env-маппинг), а не вызов bash-обёртки

Сейчас `claude-m`/`claude-z` — bash-скрипты с `export` + `exec claude`, лежащие
в `~/.local/bin`, причём `claude-m` в WSL — симлинк внутрь клонированного
`stoneforge` (Q27a в `open-questions.md` уже отмечает хрупкость: переставил
stoneforge — профиль отвален).

Стек даёт это решить по-другому, и это не вкусовщина: **профиль описывается
данными** — executable, requested model/tier, env-маппинг (`ANTHROPIC_BASE_URL`,
`…_OPUS_MODEL` и т.д.), `secret_ref`. Рантайм сам подставляет env в
`create_subprocess_exec` и сам же его знает — значит маскировка секретов в
транскриптах (Q27a) тривиальна: фильтруем значения по списку разрешённых env
имён, без парсинга чужого bash.

Плюсы против обёрток: (1) исчезает симлинк-хрупкость — нет внешнего файла;
(2) секрет не проходит через `bash` и не виден в `ps aux` как аргумент
обёртки; (3) requested vs actual model (Grok §12.2) пишется прямо из профиля.
Это уточнение того, каков профиль в нашем стеке, не новое решение.

### 13.3. Верификация — отдельный мутабельный checkout, не ревьюер и не автор

Это пересечение трёх принятых решений, которое никто не свёл вместе и которое
даёт неочевидную границу:

- **Q26:** ревьюер строго read-only, работает на фиксированном code SHA в
  disposable checkout.
- **Q31/Q33:** верификация — собрать, прогнать тесты; результат
  структурированный; базовый прогон до работы.
- **Q8a/Q10:** автор работает в своём клоне; реализация последовательная.

Следствие, которое легко проморгать: **верификация не может идти в checkout
ревьюера** (там read-only, а сборка плодит артефакты = мутация →
`mutation_violation` по `readOnlyContractFailure`). И **не может делить worktree
с автором** в параллельной схеме (артефакты сборки одного таска мешают другому).
Значит верификация — это *отдельный шаг со своим checkout, где мутация явно
разрешена и ожидаема*, отдельно от author-lane и review-lane. Это та же логика
«disposable checkout на точном SHA» (Codex §4.5), но с инвертированным
контрактом: там запрет мутации, здесь разрешение.

Тот же аргумент снимает, где лежит файл заметок проекта (Q31a): это *контент
промпта*, он читается во всех промптах и пополняется по ходу прогона. Если он
лежит в клоне — он меняется под ногами read-only ревьюера и ломает его
контракт. Значит заметки читаются из artifact-repo снимком на момент круга, а
не живой копией из рабочего каталога. Это частный случай правила «каталог
состояния вне клона» (§0.2, Q26), но заметки легко по ошибке положить в клон —
потому что они выглядят как контент, а не как состояние.

### 13.4. Оговорка к «Python-core»: асинхронность под review-линии закладывать сразу

Решение Python принимаю. Но один риск, не снятый выбором языка: первый флоу
последовательный, а уже второй тянет **несколько параллельных review-линий**
(Q16 — кворумы; требование №3 — несколько ревьюеров одновременно). Это не
параллельность *реализации* (от которой мы сознательно ушли, Q10), а
параллельность *только чтения* — и она нужна сразу во втором флоу.

Если писать ядро как чисто синхронный монолит «запустил CLI, дождался блоком»,
то первый же кворум из двух линий заставит переписывать запуск на
`asyncio.create_subprocess_exec` + gather по линиям, и этот рефакторинг
заденет структуру шагов. Предупреждение: **исполнитель шагов делать async с
первого дня**, даже если первый флоу гоняет линии по одной. Цена —
пренебрежимая на старте (`async def run` + `await subprocess`), а обратное
переписывание на живом домене — болезненное. Это не довод против Python, а
довод против *синхронного* Python-core.

### 13.5. Чего сознательно не поднимаю

Формат flow, requested/actual model, два бота, лимит переспросов, severity,
частичный disposition — уже у Grok (§12), дублировать не буду. Возврат Gas
City/Conductor, web UI — не предлагаю.

## 14. Дополнительно (Codex, 2026-08-01)

По действующему стеку §0 весомых возражений нет. Есть одна существенная
поправка к формулировке принятого решения и один недостающий уровень защиты
инвариантов.

### 14.1. Фактическая отправка в Telegram не может быть частью SQLite-транзакции

Фразу §0.2 «вопрос человеку и его отправка в Telegram — одна транзакция» нельзя
реализовать буквально: HTTP-вызов внешнего сервиса не участвует в нашей SQLite
transaction. Если держать transaction открытой во время сети, атомарности всё
равно не появится, зато single writer будет заблокирован.

Правильный контракт:

1. `HumanQuestion` и запись `telegram_outbox` создаются **в одной транзакции
   SQLite** со стабильным `question_id`;
2. worker после commit отправляет сообщение и отдельно записывает delivery
   result / transport message ID;
3. crash до отправки оставляет pending outbox, который будет доставлен позже;
4. crash после принятия сообщения transport'ом, но до записи результата может
   дать дубль, поэтому каждое сообщение и callback несут тот же `question_id`,
   а повторный ответ идемпотентен;
5. входящий update, `HumanAnswer` и отметка «update обработан» записываются одной
   transaction с `UNIQUE(transport, update_id)`.

То есть гарантия — **durable at-least-once delivery + idempotent handling**, а не
несуществующий exactly-once внешний эффект. После выбора своего graph store
ответ и снятие task block уже можно записать в той же локальной transaction;
наружу остаётся только Telegram delivery.

### 14.2. Pydantic проверяет вход, но инварианты обязан держать и SQLite

Strict Pydantic schema защищает flow и structured output на границе процесса,
но после kill/restart источником истины становится база. Поэтому критичные
правила должны иметь database-level constraints, а не только `if` в Python:

- foreign keys между campaign, round, finding, observation и attempt;
- `UNIQUE(campaign_id, finding_id, round_no)` для итоговой записи finding на
  круге;
- `UNIQUE(transport, update_id)` и не более одного принятого answer на question;
- `CHECK` для terminal status и совместимости enum хотя бы на уровне допустимых
  значений; семантическую совместимость disposition/outcome проверяет service;
- partial unique index «не более одного active attempt на lane/step»;
- state projection и соответствующий append-only event пишутся одной
  transaction.

Single-writer уменьшает число гонок, но параллельные review-lanes всё равно
завершаются независимо, а recovery повторяет команды. Ограничения базы —
последняя линия защиты от двойного completion и частичного review outcome.

### 15.1. Cut-off: self-check приёмки в коде, а не только в промпте

Q25 / metaswarm `skills/handoff/SKILL.md:8-29`: «получающий агент должен суметь
действовать, прочитав ровно один файл». Сейчас это правило в промпте. Правило
в коде отсутствует.

Это не мелочь. Без code-side проверки правило превращается в **«автор думает,
что передал достаточно»** — то есть добавляет якорь, против которого мы и так
ставим no-anchoring через разные каналы. Уходящий агент пишет развёрнутый
cut-off, считает, что всё ясно, а принимающий в новой сессии тратит первые
несколько turns на расшифровку. Хуже того, у Q30 «суждение — агентом,
детерминированное — кодом» — проверка «файл действенен» это **детерминированная**
проверка, а не суждение.

Предложение: на приёме cut-off следующий шаг обязан **подтвердить, что прочитал
файл и понял задачу** — иначе не принимать, вернуть уходящему агенту на
доработку с указанием, что именно непонятно. Один короткий pre-step:
`assert_actionable(content, task_brief) -> continue | reject(reason)`. Реализация
может быть простой — модель возвращает структурированный `understood: bool` +
при `false` короткое `missing: [...]`. Runtime проверяет покрытие `task_brief`
(что понял, как действует, какие preconditions проверял) и отказывает с
видимой причиной. Без этого механика handoff, которая в metaswarm работает
на честном слове Claude Code как оркестратора, в нашем автоматическом ядре
начнёт расходиться.

Цена: один новый тип шага + одна schema. Выгода: предсказуемость первой
строки следующего круга и audit-trail попыток передачи.

### 15.2. Idle vs hung: двухпороговая шкала на `StepAttempt`

Q35 признак живости и kill/retry — это две разные вещи, которые легко
смешать. Если шаг «не подаёт признаков жизни» 5 минут, это может быть:

- (а) **глубокая обработка без видимого output** — нормально, kill = потеря работы;
- (б) **зависание процесса** — нужно убить и перезапустить;
- (в) **deadlock на внешнем ресурсе** — нужен не kill, а эскалация (например,
  завис на ожидании ответа Telegram, который не придёт).

Один таймаут их не различает, и в коде появится соблазн либо резать живое
(по heartbeat), либо ждать мёртвое (по wall-clock).

Предложение: **двухпороговая шкала** с двумя независимыми полями в
`StepAttempt`:

| Поле | Что отслеживает | Триггер | Действие |
|---|---|---|---|
| `last_heartbeat_at` | поток вывода или изменения файлов | старше `soft_timeout` | warning в CLI; можно ignore, если есть прогресс по другому сигналу |
| `started_at` | общее время с момента запуска | старше `hard_timeout` | soft kill (TERM → grace `N` сек → KILL); attempt → `interrupted` per Opus §13.1 |

Различение даёт ещё одну вещь: `(в)` (deadlock на Telegram) ловится, если
`last_heartbeat_at` стоит, а `started_at` уже близок к `hard_timeout` — это
сигнал «не процесс мёртв, процесс ждёт», и его обработка отличается (не
kill, а разблокировка ожидания или human question). В однопороговой схеме
этот случай не отличим от обычного зависания.

Численные значения `soft_timeout` и `hard_timeout` — параметры профиля
(Q27a/§13.2), не глобальные константы. У Claude, который может молчать минуту
на длинном контексте, и у codex, который отвечает быстрее, дефолты разные.

### 15.3. First-step readiness probe: падать сразу, если окружение не готово

Q1b фиксирует: «подготовка среды — ручная работа человека; система рассчитывает
на готовое окружение и внятно ругается, если чего-то нет». Вторая половина
этой фразы — «внятно ругается, если чего-то нет» — **нигде не реализована
как конкретная механика**. По Q1b предполагается, что человек проверил сам;
по факту первая неудача придёт на середине run'а, и будет стоить часов.

Сейчас при первом запуске `stable-metaswarm serve` мы узнаем о проблеме
среды, только когда первый шаг форкнёт процесс и тот вернёт
`executable-not-found`. Это поздно: уже могли создаться gate-биды, открыться
question, человек получить Telegram-уведомление о фантомном вопросе.

Предложение: при старте сервиса — до того, как он примет первый запрос —

1. проверить наличие и версии обязательных бинарей (`claude`, `codex`,
   `cursor-agent` для заявленных профилей; `bd`; `git`; `sqlite3` ≥ 3.40
   для `RETURNING` и `CHECK`);
2. проверить, что для каждого заявленного профиля `secret_ref` резолвится
   в непустое значение env;
3. проверить, что Telegram token прошёл `getMe`, и чат allowlist не пуст;
4. проверить, что каталог состояния (`/var/lib/stable-metaswarm` или
   `~/.local/share/stable-metaswarm`) существует и доступен на запись;
5. **записать отчёт `readiness.json`** и завершить старт с кодом `0` только
   при полном `ok`; при любом `degraded` или `missing` — код `78` (`EX_CONFIG`)
   и structured stderr.

Цена: один модуль `readiness` и пять проверок. Выгода: первая ошибка среды
обнаруживается до открытия первого gate'а и до отправки первого
Telegram-сообщения. Это не делает Q1b излишним — Q1b остаётся принципом
«автоустановки нет» — но превращает «должен проверить человек» в «человек
проверил и подтвердил readiness probe прошёл, иначе сервис не стартует».

### 16.1. Единый drift check при `continue` и старте run'а

Codex в acceptance-листе (`codex.md` §9) записал один пункт — «flow/config
изменился между checkpoint и continue». Minimax (§15.3) добавил readiness
probe при старте сервиса. Между ними остаётся непокрытая середина: run живёт
дольше, чем старт сервиса, а пауза по Q21 может длиться сколько угодно — за
неё мир меняется сразу по нескольким осям. Предлагаю один детерминированный
шаг, выполняемый при каждом `continue` и при старте run'а:

| Что сверяем | С чем | При расхождении |
|---|---|---|
| code SHA клона | SHA, зафиксированный в run | стоп: ручная правка = новая ревизия (Q23) |
| ревизии артефактов стадии | текущие в artifact repo | стоп до явного подтверждения |
| ревизия графа задач | `source_artifact_revision` (моя добавка §9) | стоп, reimport или подтверждение |
| хеш flow-конфига и project config | canonical hash при старте run | стоп (идея workflow hash из Conductor, переносим без пакета) |
| версии вендорских CLI | версии в манифесте первого attempt | предупреждение; при смене major — стоп |
| конфиг профилей | canonical hash | стоп |

Правило одно: **drift не чинится молча и не игнорируется молча** — либо
`continue` отклоняется с перечнем расхождений, либо человек подтверждает
`--accept-drift`, и это решение пишется в events. Это расширяет probe Minimax
с момента «старт сервиса» на момент «continue после паузы» (версии CLI он
проверяет только при старте, а подписочные CLI обновляются между прогонами).
Цена — один модуль сверки; выгода — весь класс ошибок «конвейер доехал не по
тем данным» ловится в одном месте, а не размазывается по четырём ad hoc
проверкам, которые непременно разъедутся.

### 16.2. Версия промпта и рубрики — в манифесте каждого attempt

Мы забираем у metaswarm промпты и рубрики как контент и будем править их
между прогонами — это главный регулятор качества системы. Но в манифесте
attempt (`codex.md` §4.8: run_id, stage_id, profile, input refs, code SHA,
digest, schema version) версии промпта нет. Следствия:

- «ревьюер изменил поведение между прогонами» недиагностируемо: смену модели
  не отличить от смены рубрики;
- кворум из двух линий с разными версиями рубрики — не кворум: линии меряют
  по разным шкалам, а синтез считает их равноправными;
- калибровка под Q42-B («ловит то, что поймал бы ты») невозможна задним
  числом: findings не привязаны к версии инструкции, которая их породила.

Предложение: в манифест attempt пишем `prompt_template_id + hash` и
`rubric_id + hash` (контент metaswarm версионируем в нашем репозитории как
prompt pack — как и предлагал `codex.md` §5). Runtime при сборе кворума
проверяет равенство версий рубрики по линиям: неравенство — contract error до
запуска, а не расхождение в выводе. Цена — две колонки и одна проверка;
выгода — воспроизводимость ревью, без которой плоскость 5 работает на песке:
ledger в промпте — тоже промпт, и его формат версионируется вместе с
остальными.

### 16.3. Чего сознательно не поднимаю

Формат флоу, requested/actual model, два бота, лимит переспросов (Grok §12);
статус-модель, профиль-данные, отдельный checkout верификации, async с первого

осью, не раздувая накопитель.

**Почему не lifetime max в пороге.** После reopen evidence по определению другое;
эскалировать по наблюдениям, которых больше нет, — ложный human-gate. На нашем
критерии «не молчать» ложный гейт тоже шум, но хуже другое: человек привыкает,
что эскалация бывает «про старое», и начинает игнорировать. Порог должен
читать только живой evidence.

**Как закрыть «тише = хуже» без перехода на Codex.** Цена ошибки в сторону
Kimi — тихая де-эскалация переоткрытого спора. Лечится не lifetime в формуле
порога, а третьей величиной в CLI (рядом с уже зафиксированными «при создании»
и «для эскалации»):

> `historical_max` — максимум `severity_suggested` за всю жизнь ID  
> `escalation_severity` — то, что читает порог (после reopen = max новых)

Систематическое «переоткрыли и стало тише» видно с одного взгляда (Q36), без
автоматического дёрганья человека по протухшему. Это ровно наш обычный критерий:
молчание лечим видимостью, а не ложной эскалацией.

**Случай, который остаётся:** закрыл ревьюер ниже порога → reopen → новые
наблюдения слабее старых. Порог не срабатывает; historical_max в CLI выше
текущего. Человек, если смотрит статус, видит перекос; автоматика не врёт, что
«всё ещё blocker». Принимаю.

### GLM (A-1): соглашаюсь с Grok; довод cry wolf

*Атрибуция исправлена 2026-08-02: раздел написан GLM, изначально был подписан
«Opus». Позиция Opus — отдельным разделом ниже.*

Разбирая формулировку Opus «первая тише, а значит хуже», я сначала пришёл к
Codex (max за жизнь ID). **Довод Grok про cry wolf возвращает к кампании**, и он
сильнее.

Разбор Opus опирался на бинарную асимметрию «видимая ложная эскалация лучше
тихой де-эскалации». Но у ложной эскалации есть **накопительный вред**: канал
экстренной эскалации работает, только пока ему доверяют. Если заметная доля
эскалаций оказывается «про старое» (snapshot показывает расхождение, но человек
каждый раз должен разбираться), привычка игнорировать распространяется и на
настоящие — а это подрывает требование №4 куда сильнее, чем одна пропущенная
де-эскалация. Cry wolf — это не «один лишний вопрос», а деградация канала.

**Почему де-эскалация при этом не молчит.** Мой довод «тише = хуже» держался на
том, что снижение severity уходит незаметно. Это верно только если исторический
максимум спрятан. Решение Grok — `historical_max` как третья величина в CLI,
всегда рядом с «при создании» и «для эскалации» — делает перекос видимым на
*каждом* просмотре статуса, не только в момент reopen. А это ровно наше
разделение из Q21/Q36: **активно дёргать человека (Telegram) — для того, что
требует действия сейчас; пассивно показывать (CLI) — для того, что заметить при
случае.** Reopen со снижением ниже порога по свежему evidence — это «заметить при
случае», а не «действие сейчас». Класть его в активную эскалацию — путать два
режима.

Итог: порог Q12a читает максимум по свежим наблюдениям (правило границы Kimi);
`historical_max` живёт в CLI как диагноз занижения. Поведение — как у Grok и
Kimi; мой вклад — явно проговорить cry wolf как причину, почему разделение
актив/пассив обязывает к кампании, а не просто «видимость» как украшение.

### Opus (A-1): принимаю довод GLM, разворачиваю свою позицию

В прошлом заходе я склонялся к Codex: «тихая де-эскалация хуже видимой ложной
эскалации». Это была бинарная оценка асимметрии, и она неверна — **у ложной
эскалации есть накопительная цена, которой в моём сравнении не было.** Довод GLM
принимаю целиком, позицию меняю на кампанию.

Добавляю то, чего в разделе GLM ещё нет: **поправка Minimax закрывает возражение
Codex почти полностью, а не частично.** Накопитель теперь обнуляется только
когда проблема действительно исчезла (`verified_fixed`) или когда решил человек.
Принятый отказ историю сохраняет — а это и был центральный случай Codex

только для findings, которые починили, подтвердили, и они появились снова, — и
там пересчёт с нуля правилен по определению reopen. Поэтому ещё одного круга к
Codex не требуется: его довод не отклонён, а удовлетворён механикой.

### 17.3. Хвост B-1: жёсткий фильтр кандидатов или только ранжирование

Все трое согласны, что отбор закрытых `accepted_reason` для reconciliation —
структурный (кампания, таск, артефакт, охват `review_subject`), а регион кода,
SHA, title и близость текста не устанавливают identity. Разошлись в одном: есть
ли **жёсткий фильтр** и по чему.

| Позиция | Довод |
|---|---|
| Фильтр по **пути файла**; диапазоны строк только сортируют (Kimi) | Scope намеренно over-inclusive, лишнее показать безопасно — ревьюер скажет `new`. Переименование файла даёт промах «в безопасную сторону» |
| **Жёсткого фильтра нет вообще**; структура плюс ранжирование, ревьюер видит остальные принятые findings своего scope (Codex, Opus) | Промах фильтра означает, что закрытый finding **не показан** — а это и есть тот отказ, который мы чиним: false negative косвенно породит новый ID. На десятках findings список короткий, цена отсутствия фильтра нулевая |

**Что нужно решить:** оставить ли путь файла жёстким фильтром ради короткого
списка, или отказаться от фильтра и оставить регион только как порядок
сортировки. Практическая разница видна только когда принятых отказов много —
то есть на большом прогоне, которого у нас пока не было.

| Агент | Дата | Вердикт | Суть |
|---|---|---|---|
| Grok | 2026-08-01 | **фильтра нет**; путь/строки только ранжируют | «безопасная сторона» у Kimi инвертирована: не показать закрытый отказ — ровно та дыра, которую чиним |
| GLM | 2026-08-01 | **фильтра нет** | усиление: фильтр по пути внутренне противоречит отказу от пути+строк как личности (плоскость 5) — нестабильный ключ как gatekeeper для стабильного ID |
| Minimax | 2026-08-01 | **фильтра нет** | false negative фильтра = ревьюер объявляет `new` для закрытого = двойной учёт = Q11 нарушен наоборот. Ранжирование по severity и давности |
| Kimi | 2026-08-02 | **снимаю возражение** | я сравнивал не ту пару исходов: реальный исход промаха — не «пересмотр», а форк ledger и повторный вопрос человеку, ради устранения которого механизм и заводился. Мягкий CLI-контроль ловит это только глобальным сравнением, то есть перекладывает спам на человека, а не устраняет. Окончательно убеждает довод про gatekeeper: я защищал эвристику, противоречащую основанию, на котором сам стоял |
| Opus | 2026-08-02 | **фильтра нет** | подтверждаю; довод про gatekeeper был и в моём консольном ответе этого круга |

### Grok (B-1)

**Вердикт:** жёсткого фильтра по пути файла нет. Структурный scope (кампания /
таск / артефакт / `review_subject`) + ранжирование (путь, строки, SHA, близость
title) — путь и диапазон влияют на **порядок**, не на состав списка.

Формулировка Kimi «промах при переименовании — в безопасную сторону»
неточна: безопасно показать лишнее (`previously_accepted` отвергнут → `new`),
а не показать недостающее. Фильтр по пути промахивается именно во вторую
сторону: файл переименовали → принятый отказ не попал в ledger → ревьюер
заводит новый ID на ту же проблему → память между кампаниями молча сломана.
Это ровно тот класс отказа, ради которого память и заводили.

На десятках findings экономия фильтра нулевая; если когда-нибудь список
вырастет — режем structurally (subject/таск), не эвристикой по path.

Согласен с Grok: фильтра нет, путь и строки только ранжируют. Добавлю довод,

Вся плоскость 5 построена на отказе от пути+строк как личности finding'а:
Gas City-ключ ломается при сдвиге строк, Orca по title — при перефразе, поэтому
