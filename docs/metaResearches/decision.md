## 1. Что строим

Оркестратор CLI-агентов от разных вендоров. Ведёт задачу по конвейеру
**тех-дизайн → граф задач → таск-планы → реализация → верификация → финальное
ревью**, с циклами проверки «А сделал — Б проверил — А поправил или обоснованно
отказался» и с остановкой ветки на открытых вопросах до ответа человека.

Три флоу, в порядке реализации:

1. **Ревью коммита** — параллельные линии ревью, сведение findings, цикл правок.
2. **Фича в существующий проект** — полный конвейер.
3. **Новый проект с нуля** — то же плюс bootstrap-стадии.

Главная ценность и главная сложность — **протокол разрешения findings**: каждое
замечание закрывается явным статусом, отказ автора рассматривает ревьюер, спор
не ниже порога уходит человеку, число кругов ограничено кодом. Готового такого
протокола нет ни у одного из изученных проектов; всё остальное — обвязка вокруг
него.

## 2. Стек

| Слой | Выбор | Форма |
|---|---|---|
| Ядро | **Собственное, Python 3.12+** | Один процесс-сервис, асинхронный исполнитель шагов |
| Состояние | **SQLite** (WAL, single writer) + append-only события | Одна база на инстанс |
| Граф задач | **Свой**, в той же базе, за границей модуля | `task` / `dependency` / `block`; `bd` — вторая реализация по возникшей нужде |
| Запуск агентов | **`asyncio.create_subprocess_exec`** | Без shell-интерполяции, process groups |
| Адаптеры CLI | **Свои, три семейства** | `claude`, `codex`, `cursor` |
| Конфиг флоу | **YAML + Pydantic `extra="forbid"`** | Канонический JSON с хешем показывается до запуска |
| Канал с человеком | **Свой Telegram-бот, long polling** | Через transactional outbox |
| CLI | Typer + Rich (или эквивалент) | `run / status / continue / pause / cancel / answer / validate` |
| Packaging и dev-tooling | **`setuptools`, `uv` + `uv.lock`, `src/metaswarm`** | Зависимость меняется вместе с lockfile; единая локальная проверка — `./scripts/check.sh`; `uv` не является runtime-зависимостью |

`pyproject.toml` объявляет project/dev dependencies, `uv.lock` фиксирует их
точную резолюцию, а `uv run --locked` запрещает проверке молча переписать
устаревший lockfile. Если `uv` отсутствует, `scripts/check.sh` завершается как
обычный POSIX command-not-found с кодом 127. Сам сервис не запускает `uv` и не
проверяет его в production readiness.

**Ничего из чужого не является зависимостью рантайма.** Доноры:

| Донор | Что берём | Чего не берём |
|---|---|---|
| **Gas City** | Спецификация поведения и эталон сверки: пятиосевая модель профиля, семантика read-only контракта, ключ склейки findings внутри круга | Рантайм, формулы, control-биды, Go-код |
| **Conductor** | Референс архитектуры: словарь режимов контекста (`accumulate` / `last_only` / `explicit`), идея строгой схемы и канонического вида, каталог fault-cases | Пакет, движок, provider registry, checkpoint, dashboard-gate |
| **Orca** | Инварианты review-домена: исчерпывающий `FixOutcome`, «каждое замечание ровно в один список», непрерывность сессии автора | Lifecycle: их исчерпание кругов сворачивает findings в `ignored` и едет дальше — прямо против нашего требования |
| **bernstein** | Механика адаптеров: argv, коды выхода, разбор stream-json, read-only флаги, Telegram long polling | Пакет и его небезопасные умолчания (`bypassPermissions`, автоподмена вендора) |
| **metaswarm** | Контент: промпты, 9 рубрик, роли, шаблон handoff, правило свежего ревьюера | State machine — она у них живёт в контексте LLM |
| **beads** | Модель графа как образец | Как хранилище — не в v1 |

Лицензии доноров permissive (MIT / Apache-2.0). При переносе фрагментов
сохраняем copyright и отмечаем происхождение.

**Правило, разрешающее споры при реализации:** *детерминированное делает код,
суждение делает агент, голый API вендора не нужен.* Жёстче всего это работает в
одном месте — **переход состояния review/fix обязан быть кодом**, иначе кап
кругов остаётся рекомендацией, которую модель может обойти, а на нём стоит весь
контракт findings. Кодом делаются: переходы состояния, склейка наблюдений внутри
круга, проверка полноты покрытия открытых ID, снятие блокировок, запуск
верификации, работа с git и артефактами. Агентом — поиск замечаний, оценка
severity, решение «то же самое или новое», обоснование отказа и его
рассмотрение. Когда при реализации возникает спор «а не проще ли поручить это
модели» — ответ даёт это правило.

**И запрет на универсализацию «на вырост»:** абстракции, у которых сегодня одна
реализация, пишутся как один модуль, а не как интерфейс с реестром. Это касается
прежде всего графа задач: `Protocol`, registry бэкендов и conformance-suite
появляются **только вместе со второй реализацией**, не раньше. То же для
адаптеров: три конкретных, а не фреймворк адаптеров.

**Инструменты — не самоцель, и это решение владельца.** Выбор стека, библиотек и
конкретных механизмов сделан по лучшему пониманию на момент выбора, а не как
обязательство. Если при проектировании или в коде выясняется, что другой
инструмент или другая форма заметно проще, — **менять можно и нужно**, записав,
что именно отменено и почему.

То же относится к самим требованиям: **поправку к требованию предлагать
разрешено**, если она существенно упрощает реализацию. Не молча обходить, а
выносить на решение — с ценой, которую требование стоит, и с тем, что теряется
при его смягчении. Требования в `../requirements/` фиксируют задачу, а не способ
её решения.

Единственное, что не двигается без явного разговора, — **контракт разрешения
findings и правила остановки ветки**: в них смысл системы, и «упростить» их
означает построить другую систему.

**Отклонено, чтобы не возвращаться:** Gas City и Forge как рантайм, форк
Conductor, Orca как control plane, CAO и AgentAPI (управление через regex по
экрану), Temporal / DBOS / LangGraph / ControlFlow (покупают durability, которая
отменена решениями по восстановлению), Tutti и Stably Orca (десктопные
продукты), vibe-kanban и humanlayer (закрыты или deprecated).

## 3. Границы v1

**В v1 входит:** три флоу (по одному за раз, в указанном порядке), пять
профилей, полный протокол ревью, вопросы человеку через Telegram, верификация,
CLI-наблюдаемость, восстановление состояния после перезапуска.

**Не входит, с критерием возврата:**

| Не делаем | Вернёмся, если |
|---|---|
| Параллельная реализация через worktree | Слияние конфликтов перестанет требовать отдельной стадии конвейера |
| Веб-интерфейс, сводки в Telegram | После MVP, по желанию |
| Контейнеры и песочницы | Понадобятся жёсткие запреты вместо промптовых |
| PTY-эмуляция | У конкретного вендора не окажется стабильного headless — тогда только для этого адаптера |
| `bd` как реализация графа | Человек реально начнёт смотреть или править граф вне оркестратора |
| Голый API вендора | Не потребуется: профили покрывают всё, где нужно суждение |
| Несколько прогонов, очередь, приоритеты | Один прогон за раз — принятое ограничение |
| Бюджеты и учёт токенов | Подписки, цена фиксирована |
| Автовозобновление после падения | Продолжение только явной командой |
| Таймауты и напоминания на вопросах человеку | Ждём сколько угодно |
| Самопроверка приёмки cut-off моделью | Реальные прогоны покажут провалы передачи |
| Универсальный конструктор флоу | Три флоу руками; дальше агент пишет по образцу |

## 4. Топология и процессная модель

**Два независимых инстанса**, без общего состояния и без связи между собой:

| Инстанс | Среда | Проекты | Особенности |
|---|---|---|---|
| **РабОрк** | WSL2 на ноутбуке | Рабочие | Артефакты только во вспомогательный репозиторий; наружу отдаётся только ветка задачи, PR выставляет человек |
| **СвойОрк** | Linux VPS | Личные | Артефакты рядом с кодом; полный цикл вплоть до PR допустим |

Windows — только рабочая копия человека с IDE. Компонентов системы там нет,
обмен с агентским клоном идёт ветками через git remote.

**Одна кодовая база, два instance profile.** Различия допустимы только на
периферии ввода-вывода; попытка развести поведение внутри цикла проверки или
контракта findings — сигнал ошибки проектирования.

**Правила переносимости между WSL2 и VPS** (закладываются сразу):

1. Никаких абсолютных путей и предположений про домашний каталог.
2. Рантайм агентов — `subprocess`, не `tmux`.
3. Telegram — long polling, не webhook.
4. **Ничего не зависит от `systemd`:** в WSL2 он не гарантирован. Демон
   поднимается своей обёрткой; unit — опция для VPS.
5. Файлы проектов — в нативной ФС Linux, не в `/mnt/c`.

**Процессная модель.** Один сервис на инстанс — единственный writer базы и
владелец дочерних процессов агентов. Локальный CLI общается с ним через Unix
domain socket; наружу TCP не открывается. Перезапуск сервиса выполняет recovery
audit и возобновляет Telegram polling, но **не продолжает прогон**: прерванная
попытка становится `interrupted`, прогон ждёт явного `continue`.

**Защита от второго демона и осиротевших процессов.** «Single writer» — это
требование, которое надо обеспечить, а не свойство, которое возникает само:

- **instance lock** на каталоге состояния с lease и heartbeat; второй экземпляр
  сервиса не стартует, а внятно сообщает, кто держит замок;
- у каждой попытки пишутся **PID, start-time и process group id** — PID сам по
  себе переиспользуется ОС, и без start-time проверка «жив ли ещё тот процесс»
  ошибается;
- правило recovery: **новая попытка не запускается, пока прежняя группа не
  подтверждена мёртвой.** Если группа жива — сначала гасим её (TERM → grace →
  KILL), и только потом создаём новую попытку. Иначе после падения сервиса
  осиротевший агент продолжит писать в тот же рабочий каталог параллельно с его
  заменой.

**Окружение готовит человек, система его не чинит.** Установка CLI, логины по
подпискам, тулчейн проекта, доступы к git — ручная работа, один раз на среду.
Система вправе рассчитывать на готовое окружение и обязана внятно ругаться, если
чего-то нет. Автоустановщиков, мастеров настройки, автологина и попыток
самолечения не пишем — ни сейчас, ни потом. Readiness probe ниже **проверяет и
отказывается стартовать**, но ничего не доустанавливает.

**Readiness probe при старте сервиса** — до приёма первого запроса:

1. наличие и версии бинарей заявленных профилей, `git`, `sqlite3`;
2. каждый `secret_ref` резолвится в непустое значение;
3. Telegram-токен проходит `getMe`, allowlist непуст;
4. каталог состояния существует и доступен на запись;
5. отчёт `readiness.json`; при любом `missing` сервис не стартует.

Смысл: первая ошибка среды обнаруживается до того, как создан первый гейт и
человеку ушло уведомление о фантомном вопросе.

**Drift check при `continue` и при старте прогона** — одним детерминированным
шагом, по семи осям:

| Сверяем | С чем |
|---|---|
| code SHA клона | SHA, зафиксированный в прогоне |
| Ревизии артефактов стадии | Текущие в artifact repo |
| Ревизия графа задач | `source_artifact_revision` |
| Canonical hash flow и project config | Значение при старте прогона |
| Версии вендорских CLI | Версии в манифесте первой попытки |
| Canonical hash конфига профилей | Значение при старте прогона |
| **Версия ядра оркестратора** | Версия, записанная в манифест прогона |

Правило: **дрейф не чинится и не игнорируется молча.** Либо `continue`
отклоняется со списком расхождений, либо человек подтверждает `--accept-drift`,
и это решение пишется в события. Смена major-версии CLI — стоп, минорная —
предупреждение.

**Принятие дрейфа — не просто отметка в журнале: у каждой оси своё последствие.**
Одного события «человек согласился» недостаточно, иначе прогон поедет с
одобрениями, выданными на другое состояние мира:

| Ось дрейфа | Что происходит при `--accept-drift` |
|---|---|
| Code SHA клона | Прежние результаты ревью и верификации на старом SHA признаются устаревшими; открытые findings сохраняются, но требуют нового круга |
| Ревизия артефакта стадии | Апрувы предыдущей ревизии протухают (как при ручной правке) |
| Ревизия графа | Переимпорт с инвалидацией незавершённых задач прежней ревизии |
| Hash flow или project config | Стадии, ещё не начатые, идут по новому конфигу; уже завершённые не переигрываются, но их манифесты помечаются другой версией |
| Версия вендорского CLI | Minor — запись в манифест попытки, поведение не меняется. **Major этим флагом принять нельзя:** прогон останавливается, пока человек не подтвердит отдельным решением, что фикстуры адаптера перепроверены |
| Версия ядра оркестратора | Запись в события и продолжение. **Смена major — стоп без права принять флагом:** семантика стадий могла измениться при том же hash конфига, и «тот же флоу» больше не означает «то же поведение» |
| Hash конфига профилей | Проверяется, что роли всех незавершённых стадий по-прежнему резолвятся; если профиль исчез — стоп независимо от `--accept-drift` |

## 5. Хранилища: один владелец на класс фактов

Двусторонней синхронизации одинакового состояния нет нигде.

| Класс фактов | Владелец |
|---|---|
| Задачи, зависимости, готовность, блокировки | Модуль `task_graph` в основной SQLite |
| Курсор прогона, стадии, попытки, сессии, heartbeat | SQLite `RunStore` |
| Кампании ревью, круги, findings, наблюдения, dispositions | SQLite `RunStore` |
| Вопросы человеку, ответы, Telegram offset, outbox | SQLite `RunStore` |
| История переходов | `run_event`, append-only, в той же транзакции, что и переход |
| Код и его ревизии | git-репозиторий агентского клона |
| Дизайн, планы, cut-off, результаты верификации, заметки проекта | Artifact repo по правилам инстанса |
| Сырые транскрипты | Каталог на диске; в базе только путь, digest и redacted summary |

**Каталог состояния лежит вне агентского клона кода — всегда.** Иначе записи
оркестратора выглядят как изменения untracked-файлов в workspace ревьюера и
валят его read-only контракт: виноватым окажется тот, кто ничего не делал.

**Индексы под `review_campaign` и `human_question` — с первого дня.** Запрос «что
сейчас ждёт человека» не должен сканировать журнал событий: раз напоминаний нет,
эта команда — единственная защита от потерянной задачи, и она обязана быть
быстрой.

Ретенция транскриптов — по числу завершённых прогонов, не по времени. Активные,
приостановленные и ждущие человека прогоны сборщик не трогает.

**Схема базы версионируется нумерованными миграциями.** База переживает
обновления ядра между прогонами, поэтому: миграции применяются при старте
сервиса, **до** recovery audit — иначе audit будет читать записи схемой, которой
они не соответствуют; версия схемы хранится в самой базе; откат вниз не
поддерживается, старое ядро на новой базе не стартует, а внятно сообщает о
несовместимости. Версия ядра пишется в манифест прогона и участвует в drift check
(§4).

**Время: хранение и сравнение — разные вещи.** Все timestamps хранятся в UTC. Но
живость шага, таймауты и retry-задержки считаются по **монотонным часам**, а не
по настенным: ноутбук уходит в спячку, переезжает между часовыми поясами и
получает поправку от NTP — на настенных часах это даёт то мгновенные ложные
таймауты, то вечное ожидание. Дешевле записать сейчас, чем отлаживать потом.

## 6. Модель данных

### 6.1. Прогон, стадии, попытки

Минимальный набор сущностей: `Run`, `StageExecution`, `Branch`, `StepAttempt`,
`AgentInvocation`, `LogicalSession` с vendor-native session ID, `ArtifactRef` с
digest и SHA, `VerificationRun`, `Blocker`, `RunEvent`.

**Что именно неизменяемо у попытки:** вход (профиль, промпт и его версия,
входные ссылки, SHA) и терминальный результат. Изменяемые по ходу поля —
`status` до терминального и `last_heartbeat_at` — живут отдельной runtime-строкой
`attempt_liveness`, а не правят запись результата. Формулировка «попытка
неизменяема» без этого разделения ложна: heartbeat пишется каждые несколько
секунд.

**Исход попытки и результат ревью — разные вещи, и смешивать их нельзя.**
Ревьюер, который сказал «не починено», отработал успешно: неуспешен результат
проверки, а не вызов агента.

*Исход `StepAttempt` — про технику вызова:*

| Исход | Что случилось | Бюджет |
|---|---|---|
| `succeeded` | Процесс завершился, вывод прошёл схему. Каким был вердикт по существу — не его дело | — |
| `interrupted` | Рестарт сервиса, машина ушла в спячку, человек убил | Никакой |
| `hung` | Не было признаков жизни дольше `hard_timeout`, процесс убит нами | `hang_retry_budget` |
| `transient` | Вендор недоступен, rate limit, сетевой сбой | `vendor_retry_budget` |
| `contract_error` | Агент ответил, но вывод не проходит схему: нет покрытия открытых ID, нет ни `severity_suggested`, ни `unchanged_from`, несовместимая пара disposition/outcome | `contract_retry_budget` |
| `failed` | Вызов не состоялся по неретраибельной причине: ненулевой код возврата, отсутствующий бинарь, отказ в правах | — |

*Результат круга ревью — про существо:*

| Результат | Что означает |
|---|---|
| `clean` | Открытых замечаний не осталось, круг завершает кампанию |
| `needs_revision` | Есть открытые замечания, автору идёт следующая правка |
| `escalated` | Спор не ниже порога либо правки исчерпаны, а проверка требует ещё одной — вопрос человеку |

Отказ автора, с которым ревьюер не согласен, **ниже** порога — не отдельный
результат круга. Finding закрывается записью `policy_closed`, после чего
применяются обычные приоритеты: `clean`, если открытых замечаний нет;
`escalated`, если есть спор не ниже порога или исчерпан кап; иначе
`needs_revision`. Факт автоматически принятого отказа остаётся в
`finding_resolution` и отдельно виден в CLI. Подтверждающий круг без новой
авторской ревизии не создаётся.

Три следствия, каждое обязательное:

1. **Счётчики двигает завершённая валидная работа, а не статус попытки.**
   Их два и они независимы: `author_revision_count` растёт на состоявшейся
   правке автора (попытка `succeeded`, давшая новую ревизию),
   `review_check_count` — на состоявшейся проверке (попытка `succeeded` с
   валидным выводом). `interrupted`, `hung`, `transient`, `contract_error` и
   `failed` не двигают ни один. Иначе ночной перезапуск ноутбука «съедает» круг
   ревью, которого никто не проводил.
2. **Вечно зависающий CLI не крутится бесконечно.** Раньше `hard_timeout`
   давал `interrupted`, а `interrupted` не тратил бюджет — получалась петля.
   Теперь зависание — отдельный исход со своим бюджетом, и по его исчерпании
   ветка уходит к человеку.
3. **Битый структурированный вывод — не круг ревью.** Модель, которая трижды
   вернула невалидный JSON, не «трижды не согласилась»; по исчерпании
   `contract_retry_budget` это тоже вопрос человеку, но с другой формулировкой.

**Состояния разнесены по уровням** — плоский общий enum невозможен, потому что
одна ветка ждёт человека, пока другие работают:

| Уровень | Состояния |
|---|---|
| `Run` (вычисляемый агрегат) | `running` — есть хоть одна активная ветка; `paused` — человек поставил на паузу; `waiting_human` — активных веток нет, все либо завершены, либо ждут; `cancelling` — отмена запрошена, но ветки ещё не приведены к терминалу; `idle` — диагностическая ошибка «нет активности, блокировки и терминала»; терминальные `cancelled`, `failed`, `succeeded` |
| `Branch` / `StageExecution` | `ready`, `running`, `retry_wait`, `blocked`, `done`, `failed`, `cancelled` |
| `Blocker` (отдельная сущность) | тип (`human_question`, `awaiting_continue`, `dependency`, `drift`, `invalid_graph`), на что навешен, чем снимается, кто создал |

«Ждёт человека» — это не состояние ветки, а **наличие блокировки** типа
`human_question`; так CLI показывает не только факт, но и причину, а инвариант
«ветка стоит не просто так» проверяется одним запросом.

Состояние `Run` **вычисляется** из веток и блокировок, а не выставляется руками:
иначе оно неизбежно разъедется с реальностью. `stalled_invalid_graph` — это
блокировка, а не состояние прогона.

**Живость шага — две независимые шкалы:**

| Поле | Что отслеживает | Триггер | Действие |
|---|---|---|---|
| `last_heartbeat_at` | Поток вывода или изменения файлов | Старше `soft_timeout` | Предупреждение в CLI |
| `started_at` | Общее время с запуска | Старше `hard_timeout` | TERM → grace → KILL; попытка = `hung` |

Пороги — параметры профиля, не глобальные константы: у разных CLI разная норма
молчания. Различение двух шкал заодно ловит третий случай — «процесс не мёртв,
процесс ждёт»: heartbeat стоит, но общее время ещё не вышло.

**Границы попытки автора в git.** Утверждение «diff попытки берём из git» само по
себе границ не задаёт. Поэтому у каждой авторской попытки пишутся `input_sha`
(состояние ветки до запуска) и `output_sha` (после), а рантайм делает
checkpoint-коммит на завершении попытки, если агент не закоммитил сам. Без этого
после двух подряд правок нельзя показать diff именно второй.

**В манифесте каждой попытки:** `run_id`, `stage_id`, профиль (requested и
actual model/provider), входные ссылки, точный code SHA, digest артефактов,
версия схемы, версия ядра, **`prompt_template_id + hash` и `rubric_id + hash`**. Без версий
промпта и рубрики «ревьюер изменил поведение между прогонами» недиагностируемо,
а кворум из линий с разными версиями рубрики меряет по разным шкалам — рантайм
проверяет их равенство **до** запуска и падает contract error при расхождении.

### 6.2. Граф задач

Три таблицы в основной базе, весь SQL — внутри модуля `task_graph`. Пять
операций: создать задачи с зависимостями, спросить готовые, поставить блок,
снять блок, **переимпортировать по новой ревизии артефакта**.

Это **граница владения кодом, а не обещание сменного бэкенда**: пока реализация
одна, никакого `Protocol`, реестра и conformance-suite не пишется (см. правило в
§2). Пять операций фиксируются как список на бумаге до второго флоу — этого
достаточно, чтобы `bd`-реализацию можно было добавить позже локальной заменой.

**Граф — проекция утверждённого task-breakdown, а не самостоятельное
состояние.** У него есть `source_artifact_revision`; писать в него можно только
атомарным импортом:

1. разобрать весь вывод агента до записи;
2. проверить уникальность ID, существование концов каждого ребра, отсутствие
   self-edge и циклов — с выводом конкретного пути цикла;
3. записать задачи, рёбра, ревизию артефакта и событие **одной транзакцией**.

Без этого правка плана человеком (новая ревизия, протухшие апрувы) для графа не
работает.

**Инварианты — на уровне БД, а не проверками в сервисе:**

- `CHECK (parent_task_id <> child_task_id)`;
- `UNIQUE (parent_task_id, child_task_id)`;
- `UNIQUE (import_id, semantic_task_id)` — внутри одного импорта ID уникален —
  плюс партиальный уникальный индекс по `(run_id, semantic_task_id)` среди
  **активных** задач. Первоначально здесь стояло просто
  `UNIQUE (run_id, semantic_task_id)`; в паре с требованием «задачи прежней
  ревизии инвалидируются, а не удаляются» это несовместимо — старая и новая `T3`
  не могут сосуществовать. Две гарантии вместе дают то же, что задумывалось, и
  при этом допускают историю;
- проверка цикла атомарна со вставкой ребра.

Причина: цикл — не исключение, а **молчаливая порча готовности**, и проверка в
сервисе оставляет окно между основным циклом и recovery audit.

**Защита от ложного успеха:** незакрытые задачи есть ∧ готовых нет ∧ активных
попыток нет ∧ **нет ни одной легитимной блокировки, объясняющей простой** (не
только `human_question`, но и `awaiting_continue`, `dependency`, `drift`) →
блокировка `invalid_graph`, **никогда не `succeeded`**. Она живёт в базе, а не в
CLI-проверке, иначе после kill/continue её пропустят.

**Смысловая личность задачи ограничена одним прогоном.** Тот же по формулировке
таск в новом прогоне — новая задача; связь между прогонами только явным
`carry_over`.

### 6.3. Review-домен

Четыре отношения. Ключевая тонкость — **наблюдение существует раньше, чем
личность**: слепая фаза сохраняет вывод ревьюера неизменяемо, а привязка к
`finding` появляется только на reconciliation. Поэтому наблюдение и его связь с
личностью — разные записи.

| Сущность | Что несёт | Изменяемость |
|---|---|---|
| `review_observation` | Что ревьюер увидел: текст, файл, диапазон строк, evidence, `severity_suggested` или `unchanged_from`, линия, круг, ревизия, автор наблюдения | **Immutable**, пишется в слепой фазе до всякой классификации |
| `finding` | Личность: ID, `review_subject`, круг и ревизия первого появления, `title`, `first_owner_lane_id` | Не меняется (кроме `title` человеком) |
| `finding_observation_link` | Связь наблюдения с личностью и её тип: `first_seen`, `recurrence`, `reaffirmation`, `reopening` | Пишется reconciliation, одна связь на наблюдение |
| `finding_round` | `disposition` автора, обоснование, `reviewer_decision`, номер круга | Одна запись на круг |

Такая форма сохраняет слепой вывод буквально — а он нужен как доказательство при
разборе «ревьюер объявил новым то, что было открыто».

**Типов связи ровно четыре, по одному на каждый исход reconciliation** (§7.2).
Первоначально здесь было перечислено три — `reopening` пропущен по недосмотру, и
без него переоткрытие неотличимо от повтора, а период открытости severity
вычислить нечем. Исправлено при проектировании схемы; соответствие
исход ↔ тип связи и остальные уточнения — `../design/db-schema.md` §14.

**«Кто нашёл» живёт на наблюдении, а не на личности:** один finding может
объединить наблюдения двух линий, и singular-поле на личности было бы ложью.

**Владелец finding'а назначается детерминированно, но он свой в каждой
кампании.** Линия с наименьшим индексом среди тех, чьи наблюдения вошли в группу
**этой кампании**, становится владельцем и на следующем круге проверяет
исправление и рассматривает отказ:

- ей это по силам — внутри кампании она продолжает свою логическую сессию и
  помнит свои findings, чего требует правило памяти ревьюера;
- отдельный consolidation-ревьюер был бы свежим агентом без этой памяти;
- «все линии-источники со сведением решений» умножает стоимость и всё равно
  требует правила разрешения ничьей.

**Владение хранится на уровне кампании, а не личности.** На `finding` лежит
`first_owner_lane_id` — это provenance, «кто вёл его в самом начале». Актуальный
владелец живёт в `finding_round.owner_lane_id`. Причина: переоткрытие может
случиться в более поздней кампании, где прежней линии и её сессии уже нет, а
новый кворум обязан быть свежим — неизменяемый владелец ссылался бы на
участника прошлой кампании. При переоткрытии владелец выбирается заново, по тому
же правилу минимального индекса, среди линий текущей кампании.

`finding_round.reviewer_decision` — решение владельца этого круга, и оно
единственное. Остальные линии в этом круге замечание не судят.

**Севериты на личности нет.** Оценка живёт только на наблюдении; «первая
severity» — это `severity_suggested` первого наблюдения, отдельной колонкой не
денормализуется.

**`finding.title`** фиксируется при первом наблюдении (или задаётся ревьюером
явно) и дальше меняется только человеком с записанной причиной. Это ground truth
для короткой строки в ledger: если summary плывёт между кругами, модель видит
«то же, но другими словами» — тот же anchoring, от которого мы защищаемся.

**Каждое наблюдение несёт ровно одно из двух:** собственную `severity_suggested`
(переоценил) или `unchanged_from=<observation_id>` (подтвердил прежнюю).
Отсутствие обоих — contract error, вывод ревьюера отклоняется до записи.
Иначе «ревьюер подумал и подтвердил» задним числом не отличить от «не упомянул,
и мы унаследовали», а без этого различия систематический перекос severity нечем
измерить.

**Шкала severity — фиксированный упорядоченный enum, один на всех ревьюеров и
все профили:**

```
low  <  medium  <  high  <  critical
```

- **Сравнение с порогом — `>=`:** эскалируется спор, чья `escalation_severity`
  **не ниже** порога.
- **Дефолтный порог — `high`** (то есть автоматически к человеку уходят споры
  `high` и `critical`; `low` и `medium` закрываются принятием отказа автора).
  Порог — параметр конфига стадии, чтобы подвинуть его, увидев реальную картину.
- **Значение вне enum — contract error** на приёме вывода ревьюера. Никаких
  приведений «похоже на high» и никаких дефолтов по умолчанию: молчаливая
  подстановка здесь означает молчаливое изменение решения об эскалации.

**Три величины severity, и путать их нельзя:**

| Величина | Что это | Кто читает |
|---|---|---|
| `severity_suggested` | Оценка на конкретном наблюдении | Аудит, диагностика перекоса |
| `escalation_severity` | Вычисляемый монотонный максимум по принятым наблюдениям **за период открытости** | Только порог эскалации |
| `historical_max` | Максимум за всю жизнь ID | Только CLI, как диагноз занижения |

`escalation_severity` — **вычисляемое представление, а не хранимое поле**:
хранимое даёт второй путь записи, который расходится при падении между эффектом
и коммитом. Материализация позже допустима только как восстановимая проекция.

**Границы периода накопления:**

| Событие | Что с накопителем |
|---|---|
| Создание ID | Начальное значение = `severity_suggested` первого наблюдения |
| Новое наблюдение при открытом ID | `max(prev, severity_suggested)` в той же транзакции |
| `verified_fixed` от ревьюера | Период закрыт |
| Решение человека по судьбе finding'а | Период закрыт |
| **Принятый отказ** — `accepted_reason` от ревьюера **или** policy-closure (спор ниже порога закрыла система) | **Период не закрывается, накопитель живёт** |
| Человек изменил severity | Период не закрывается; дальше `max(override, наблюдения после override)` |
| Переоткрытие после `verified_fixed` или решения человека | **Новый** период, счёт с нуля по новым наблюдениям |
| Переоткрытие после принятого отказа | **Прежний** период продолжается |

Строка про принятый отказ закрывает лазейку: иначе ревьюер пишет
`accepted_reason` на критичном finding'е, накопитель обнуляется, и позднее мягкое
наблюдение опускает спор ниже порога. Подстроить это проще, чем занизить severity
напрямую. Policy-closure отнесён туда же намеренно: спор, задавленный порогом
автоматически, ничем не отличается от принятого ревьюером — иначе лазейка
переезжает на него.

**Две тонкости, без которых правило противоречит само себе:**

1. **Оси разные.** Правило про накопитель не отменяет того, что для state machine
   круга принятый отказ — терминальный исход. Замечание закрыто, круг завершён,
   а период накопления severity живёт дальше. Это не противоречие, а два разных
   жизненных цикла у одной записи.
2. **Поэтому переоткрытие ведёт себя по-разному.** Переоткрыли то, что было
   принято как отказ, — накопитель никуда не девался, и прежняя серьёзность
   по-прежнему в силе (иначе лазейка обходится через reopen). Переоткрыли то, что
   было починено и подтверждено или решено человеком, — evidence действительно
   другое, счёт начинается заново.

**Следствие, зафиксированное намеренно:** раз накопитель переживает принятый
отказ, то когда более поздняя кампания связывает новое наблюдение с тем же
finding'ом и оно несёт высокую оценку — эскалация срабатывает. «Риск приняли, но
по свежему evidence он вырос» доходит до человека. Это цель, а не побочный
эффект.

**Период открытости — не поле, а выводимый интервал.** Он определяется событиями
в `run_event`: открывающее — создание ID или переоткрытие **после** закрывающего
события; закрывающее — `verified_fixed` либо решение человека по судьбе
finding'а. Принятый отказ (ревьюером или политикой) в число закрывающих не
входит, поэтому переоткрытие после него нового периода не начинает. `escalation_severity` считается по наблюдениям, попавшим
в текущий открытый интервал. Отдельная таблица периодов не нужна и была бы ещё
одним расходящимся путём записи; события уже append-only и уже пишутся в одной
транзакции с переходом.

**Инварианты `unchanged_from`:**

- ссылка только **назад по времени** — на наблюдение с меньшим порядковым
  номером;
- только на наблюдение **того же finding'а** и **того же периода открытости**:
  через переоткрытие наследовать оценку нельзя, там счёт с нуля;
- цепочки без циклов; разрешение цепочки обязано заканчиваться наблюдением с
  явной `severity_suggested`;
- нарушение любого пункта — contract error на приёме, а не отложенная поломка.

**Автоматически понижать severity нельзя.** Человек может — отдельным событием
`severity_override` с provenance: кто, когда, старое → новое, причина. Событие —
единственная мутация severity, не рождённая из наблюдения.

**В событие решения об эскалации пишется snapshot:** значение severity, порог и
версия политики на момент решения. Это делает вопрос «почему это ушло человеку»
отвечаемым без пересчёта.

### 6.4. Review subject

Предмет кампании — не строка и не название, а типизированная запись: по нему
проверяется допустимость `existing_id` и по нему же отбираются старые принятые
отказы. Без структуры «структурный отбор» вырождается в эвристику.

| Поле | Значение |
|---|---|
| `kind` | одно из: `code`, `artifact`, `task`, `stage` |
| `run_id` | Прогон, которому принадлежит |
| `target_ref` | Ссылка на задачу, артефакт или диапазон коммитов |
| `revision` | Ревизия артефакта или code SHA |
| `parent_subject_id` | Отношение вложенности |

Вложенность задаётся **при создании кампании самим флоу**, а не вычисляется по
содержимому: предмет финальной кампании создаётся как родитель предметов всех
таск-кампаний прогона. Отсюда детерминированно следует, какие принятые отказы
попадают в её reconciliation и какие `existing_id` для неё допустимы.

Личность finding'а ограничена одним `review_subject` и его цепочкой ревизий
внутри прогона. В новом прогоне ID молча не переиспользуется; при необходимости
связь выражается явным `related_to`.

### 6.5. Вопросы человеку

Сущности: `HumanQuestion`, `HumanAnswer`, `notification_outbox`.

Вопрос и запись в outbox создаются **одной транзакцией** со стабильным
`question_id`. Отправка идёт после commit; результат доставки и transport message
ID пишутся отдельно. Входящий update, ответ и отметка «обработано» — одной
транзакцией с `UNIQUE(transport, update_id)`.

**Outbox транспортно-нейтрален** (уточнение при проектировании): у записи есть
поле `transport`, и Telegram — лишь один из отправителей, наравне с `cli`. Иначе
домен, создающий вопрос, обязан знать `chat_id`, и правило «домен не выполняет
внешних эффектов» ломается на первом же атомарном переходе. Побочная выгода — в
первой фазе весь протокол вопросов проходится через CLI, без Telegram.

Гарантия — **durable at-least-once + идемпотентная обработка**, а не
несуществующий exactly-once внешнего эффекта.

### 6.6. Атомарные переходы

Ради этого и выбрана одна база: границы, где раньше пришлось бы городить outbox и
сверку между двумя владельцами состояния, теперь одна транзакция. Их надо
перечислить явно, иначе реализация разнесёт их по разным вызовам.

| Переход | Что входит в одну транзакцию |
|---|---|
| Задан вопрос человеку | `HumanQuestion` + запись в `notification_outbox` + `Blocker` на ветке или задаче + событие |
| Получен ответ | `HumanAnswer` + отметка update как обработанного + снятие блокировки + новое состояние ветки + review-следствие (`max_author_revisions += 1` и прежний `fix_cycle` либо терминальный `closed_escalated`) + событие |
| Задача выполнена | Терминальный результат попытки + закрытие задачи в графе + пересчёт готовности зависимых + событие |
| Круг ревью закрыт | Все `finding_round` этого круга + `review_round.result` + состояние кампании (`closed_clean` либо прежний `fix_cycle` при human gate) + событие |
| Импорт или переимпорт графа | Задачи + рёбра + `source_artifact_revision` + инвалидация незавершённых задач прежней ревизии + событие |
| Эскалация | `review_round.result = escalated` + snapshot решения (значение, порог, версия политики) + `HumanQuestion` + outbox + блокировка; кампания остаётся `fix_cycle` + событие |

**Чего транзакция не покрывает — и это надо называть честно.** SQLite атомарно
фиксирует только локальное состояние и **намерение**. Наружу остаётся не один
эффект, а пять:

| Внешний эффект | Как обеспечивается корректность |
|---|---|
| Запуск и убийство процесса агента | PID + start-time + process group в записи попытки; recovery гасит группу, прежде чем создать новую попытку |
| Checkpoint-коммит в агентском клоне | Сообщение коммита несёт `attempt_id`; recovery **приводит ветку к `input_sha` прерванной попытки** и повторяет работу — найденный коммит не принимается за результат |
| Запись и коммит в artifact repo | Тот же приём: `run_id/stage_id/attempt_id` в сообщении коммита плюс digest содержимого; повторная запись того же digest — no-op |
| Push ветки задачи | Идемпотентен по построению: тот же SHA на том же ref |
| Отправка в Telegram | Outbox: намерение в транзакции, доставка после commit, `UNIQUE(transport, update_id)` на входящих |

Общий приём один и тот же — **intent → effect → reconcile**: намерение
записывается в транзакции, эффект выполняется после commit и несёт в себе
идентификатор намерения, а при старте сверка проверяет, был ли эффект выполнен,
вместо того чтобы вслепую повторять. Это не деталь реализации: без
идентификатора в коммите после падения между `git commit` и фиксацией состояния
появится второй коммит с тем же содержимым.

**Сверка бывает двух видов, и для checkpoint выбран второй.** Там, где найденный
эффект можно принять за результат, сверка идемпотентная: тот же digest артефакта
уже записан — no-op, тот же SHA на том же ref — no-op. Но checkpoint-коммит
прерванной попытки фиксирует **незаконченную** работу, и принимать её за
результат нельзя: следующий шаг оказался бы построен на середине оборванной
мысли. Поэтому здесь **intent → effect → compensate**: ветка возвращается к
`input_sha`, коммит остаётся достижим только через reflog, работа повторяется с
начала. Цена названа прямо — можно повторно оплатить работу, которая фактически
успела завершиться до падения. Взамен незавершённый результат никогда не
становится основанием следующего шага.

**Носитель намерения для checkpoint — запись `StepAttempt`, а не запись правки.**
Запись правки автора служит счётчиком капа и обязана появляться только по факту
состоявшейся правки; совместить в ней намерение и факт нельзя, не сломав счёт.

### 6.7. Артефакты и ревизии

Артефакт всегда несёт явный **code SHA**: когда дизайн и код лежат в разных
репозиториях, соседство больше ничего не доказывает.

Правка артефакта человеком — **новая ревизия**, апрувы предыдущей протухают.
Перезапуск стадии выражается новой веткой цепочки попыток
(`design:A1 → review:A1 → revision:A2 → …`), а не удалением старой.

## 7. Протокол ревью

Сердце продукта. Один и тот же контракт на всех циклах, включая финальную
кампанию, где цикл начинается с проверяющего.

### 7.1. Цикл

1. Автор создаёт ревизию артефакта или кода; фиксируется точный SHA.
2. Настроенное число линий ревью проверяет **одну и ту же ревизию** параллельно.
3. Каждое замечание получает ID от рантайма, severity, evidence и линию-источник.
   После завершения reconciliation первичный круг закрывается здесь же:
   отсутствие открытых findings даёт `clean`, их наличие — `needs_revision` и
   первую правку автора. Это исход первичного круга, а не решение капа после
   проверки правки; `author_revision_count` в этот момент ещё равен нулю.
4. Автор обязан отнести каждое открытое замечание ровно к одному исходу:
   `fixed`, `rejected`, `wont_fix` — с обоснованием при отказе.
5. Ревьюер проверяет и исправление, и аргумент отказа:

   | `disposition` автора | Допустимый исход ревьюера |
   |---|---|
   | `fixed` | `verified_fixed` или `still_present` |
   | `rejected` / `wont_fix` | `accepted_reason` или `insists` |

   Несовместимая пара — contract error. Все исходы одной попытки ревьюера
   проходят исчерпывающую валидацию и пишутся атомарно; частичный ответ не меняет
   состояние кампании. Вместе с решениями ревьюер может вернуть
   `new_observations` — проблемы, которые он впервые заметил, проверяя правку.
   Они не привязываются к текущему finding автоматически: после валидных
   решений все новые observations этого `fix_check` проходят обычный
   reconciliation по четырём исходам §7.2. Только там им выдаётся новая
   личность либо находится существующая. Новый finding получает
   `first_round_id` текущего `fix_check` и входит в тот же open set до решения
   о продолжении цикла.
6. `still_present` и `insists` оставляют замечание открытым. `insists` при
   `escalation_severity` не ниже порога **сразу** создаёт вопрос человеку, не
   дожидаясь исчерпания кругов. Спор ниже порога закрывается принятием отказа
   автора с записью в audit trail.
7. **Кап проверяется только тогда, когда цикл собирается продолжиться, и
   ограничивает он правки автора.** Настраивается один параметр —
   `max_author_revisions`, дефолт 3; число проверок из него выводится:
   `max_review_checks = max_author_revisions + 1`. Отдельно крутить второй лимит
   нельзя, иначе можно сконфигурировать «три правки при двух проверках».

   Правило перехода на границе:

   | Ситуация | Что происходит |
   |---|---|
   | Проверка вернула `clean` | **Успех**, независимо от счётчиков. Даже если это была четвёртая проверка |
   | Проверка вернула `needs_revision` и `author_revision_count < max_author_revisions` | Автор получает следующую правку |
   | Проверка вернула `needs_revision` и правки исчерпаны | Вопрос человеку |
   | Автор завершил правку | Проверка запускается **всегда** — в том числе после третьей правки. Именно она и есть четвёртая |

   То есть кап нельзя проверять «по достижении счётчика»: третья правка не
   блокирует ветку до того, как её проверят, а четвёртая проверка не блокирует
   ветку, если она чистая. Оба эти прочтения дают ошибку на единицу с разных
   сторон.

   Кап один на цикл стадии: новое замечание на последнем круге его не
   сбрасывает. Возможность такого замечания обеспечивается
   `new_observations` в `review.decisions.v1`; без неё отдельная причина
   `cap_exhausted_new` была бы недостижима.
8. Если продолжать нельзя, текущий круг закрывается с `result = escalated`, на
   ветку ставится блокировка `human_question`, и она стоит. **Сама кампания в
   ожидании ответа остаётся в `fix_cycle`:** `closed_escalated` — терминальное
   состояние, а человек ещё может разрешить дополнительную правку в том же
   цикле с теми же счётчиками. Соседние независимые ветки продолжают работу;
   состояние `Run` становится `waiting_human`, только если активных веток не
   осталось вовсе.
9. Прогон успешен, только когда все задачи закрыты, финальная кампания без
   неразрешённых findings и верификация зелёная.

**Причина остановки живёт в состоянии, а не выводится из счётчика.** «Автор
трижды не смог починить одно и то же» и «ревьюер нашёл новое на четвёртой
проверке» требуют от человека разного, и вопрос ему формулируется по-разному.
Различить их можно только зная круг первого появления каждого открытого
замечания.

**Dispositions круга — всё или ничего.** Либо все открытые ID закрыты одной
транзакцией, либо не засчитывается ни один. Как именно попытка провалилась,
зависит от того, где оборвалось: процесс убит на середине — `interrupted`;
процесс закончил, но выдал частичный или невалидный набор dispositions —
`contract_error`. В обоих случаях круг не состоялся и кап не двигается.

### 7.2. Личность замечания

Личность **выдаёт рантайм** при первом появлении и больше никогда не
пересчитывает. Сопоставление по содержимому используется только внутри одного
круга, для склейки параллельных линий, и коллизия ключа видна в CLI, а не
схлопывается молча.

Почему не сопоставлением: после правки автора номера строк сдвигаются, а модель
переописывает ту же проблему другими словами — контентный ключ ломается именно
во втором круге, ради которого он и нужен, и незакрытое замечание «исчезает».
Опираться на память ревьюера тоже нельзя: новый кворум по требованию свежести
ведёт агент без истории.

**Reconciliation обязан классифицировать каждое наблюдение ровно одним исходом
из четырёх.** Он выполняется после первичного blind discovery и повторно для
`new_observations`, найденных в `fix_check`; это единственное место выдачи новой
личности в любом круге. Система не угадывает, а проверяет:

| Исход | Что означает | Ссылка на ID |
|---|---|---|
| `new` | Другая проблема либо связь с прежним ID недостаточно уверена | Создаётся новый ID |
| `existing_open(id)` | То же, что уже открыто | Только на **открытый** ID допустимого scope |
| `reaffirmed_closed(id)` | Прежний принятый отказ всё ещё применим; нового круга нет, вопроса человеку нет | Только на закрытый с `accepted_reason` |
| `reopen_closed(id, reason)` | Прежнее закрытие больше не держится | Только на закрытый; дальше по `resolution_authority` |

Граница `reaffirmed_closed` подтверждена владельцем в Q44. Если reconciler
считает проблему другой либо не может безопасно связать её с прежним ID, он
выбирает `new`. Если это тот же finding, тихо оставить его закрытым можно только
после `accepted_reason` и только пока прежнее обоснование остаётся применимым.
После `verified_fixed`, `policy_closed` или `human_decision` тот же finding
проходит через `reopen_closed`; human-закрытие при этом снова уходит человеку.
Так регресс не маскируется новым ID и не теряется через автоматическое
подтверждение прежнего закрытия.

Что делает с кругом каждый исход:

- `new` и `existing_open` — наблюдение входит в **текущий круг**, замечание
  остаётся открытым и требует ответа автора;
- `reaffirmed_closed` — круга не порождает вовсе: прежнее решение в силе, автору
  ничего не идёт, человеку тоже;
- `reopen_closed` — переводит закрытое замечание в текущий круг, дальше по
  `resolution_authority`.

Ссылка на закрытый ID разрешена **только** в `reaffirmed_closed` и
`reopen_closed` — в `existing_open` она запрещена. Без этого перечня требование
«не ссылаться на закрытый ID» и механика памяти о принятых отказах прямо
противоречат друг другу.

«Заявил `new` для того, что открыто» — видимая аномалия в CLI, а не молчаливый
обход. Мягкий контроль: CLI показывает новые ID, похожие на недавно закрытые
(тот же файл, близкий title), **без** автоматического слияния.

**Список открытых замечаний идёт входом в промпт компактным:** ID, severity,
однострочное summary из `finding.title`, статус. Полный текст и evidence
подтягиваются только для тех ID, которые автор или ревьюер трогает.

### 7.3. Свежесть ревьюера и две фазы кворума

Внутри одной кампании линия продолжает свою логическую сессию и помнит свои
findings. Новая кампания получает **заведомо свежего** участника: система знает,
кто уже видел предмет, и назначить его снова невозможно технически.
Разнообразие считается по фактической паре provider+model, а не по имени бинаря.

**Область свежести — параметр стадии, `freshness_scope`.** Двух формулировок
здесь недостаточно, и они расходятся: «не видел эту ревизию» и «не участвовал в
предыдущих кругах» — разные правила. На чистом пути без правок ревизия не
менялась, и по первому правилу финальную свежую кампанию некем закрыть, если
участников ровно столько же, сколько было линий.

| `freshness_scope` | Ключ | Где |
|---|---|---|
| `revision` | предмет + ревизия + provider + model | Обычные кампании |
| `subject` | предмет + provider + model | Финальная кампания, второй кворум |

Практическое следствие, которое надо знать до начала: **два профиля,
резолвящиеся в одну фактическую модель, — один участник.** Проверяется до
первого прогона, а не после.

**Экспозиция записывается в момент передачи входа модели, а не по успешному
ответу.** Ревьюер, вернувший невалидный вывод, ревизию уже видел; считать его
свежим значило бы дать способ обойти правило — достаточно один раз ответить
мусором. Отсюда требование: фактическая пара provider+model резолвится заранее,
при старте прогона, а расхождение с ответом трактуется как дрейф.

**Автор ревизии не может быть её ревьюером — отдельное правило, а не следствие
свежести.** Свежесть говорит про тех, кто уже проверял; про того, кто писал, она
молчит, и без явного запрета ту же модель можно назначить проверять собственную
работу. Это прямо требование «А сделал — Б проверил», поэтому держится так же
технически, в двух местах: при отборе линий круга проверки исключается пара,
авторившая проверяемую ревизию, и при валидации конфига флоу профили автора и
ревьюера одной стадии не должны резолвиться в одну фактическую пару. Второе
важно из-за того, что `claude`, `claude-m` и `claude-z` — один бинарь: по именам
профилей совпадение бэкендов неотличимо.

Новый кворум работает в две фазы:

1. **`blind_discovery`** — получает задачу, ревизию и рубрику, но **не** прежний
   ledger; наблюдения сохраняются неизменяемо.
2. **`reconciliation`** — после фиксации слепого вывода получает ledger и
   классифицирует каждое наблюдение одним из четырёх исходов §7.2.

**В первом раунде кампании обе линии слепы друг к другу** — иначе anchoring идёт
через параллельную сессию. Со второго раунда доступен ledger обеих линий.

**Склейка внутри круга:** каждому наблюдению — свой `observation_id` с
сохранением исходного текста; точные совпадения объединяет код; группы предлагает
reconciliation; рантайм валидирует исчерпывающее разбиение — наблюдение нельзя
потерять, положить в две группы или сослать на ID вне допустимого scope либо с
исходом, которому такая ссылка не разрешена. **При неоднозначности оставить два
замечания безопаснее, чем молча склеить разные проблемы.**

### 7.4. Память о принятых отказах между кампаниями

В прогоне кампаний несколько, и финальная смотрит тот же код, что таск-уровневые.
Без памяти она заново поднимет всё, что уже закрылось принятым отказом: причина,
по которой отказ приняли, в коде не записана, а слепой ревьюер найдёт проблему
снова. Это систематика, а не шум — и повторные вопросы человеку по уже решённому
подрывают доверие к эскалации.

Поэтому в reconciliation попадают **открытые ID плюс все закрытые** замечания тех
кампаний, чей предмет входит в предмет текущей — не только принятые отказы, но и
`verified_fixed`. Причина: починенная и подтверждённая проблема может появиться
снова, и это законный `reopen_closed`, а не новое замечание; если показывать
только принятые отказы, такой reopen недостижим, и регресс каждый раз получает
новый ID с потерей истории. Внутри одного прогона закрытых немного, так что
список остаётся обозримым; порядок задаётся ранжированием.

Отбор **структурный** — по связи кампания / таск / артефакт и охвату review
subject.
Регион кода, SHA, близость title и текста — **только evidence и порядок показа**:
жёсткого фильтра нет, в том числе по пути файла. Фильтр по нестабильному ключу
сторожил бы стабильный ID — ровно та конструкция, которую мы отвергли для
личности, а автор между кругами файлы переименовывает и перемещает.

`reaffirmed_closed(id)` — **явный результат ревьюера**, а не автоматическое
закрытие по совпадению. Наблюдение связывается со старым замечанием
(`finding_observation_link` типа `reaffirmation`) даже когда прежний отказ
подтверждён: иначе не отличить «перепроверили и подтвердили» от «не смотрели».
По решению Q44 этот исход допустим только при
`last_resolution = accepted_reason`; остальные виды закрытия того же finding
проходят через `reopen_closed`.

**Переоткрытие следует каналу, который закрыл замечание.** У каждого закрытия
записывается `resolution_authority` — кто именно его принял:

| `resolution_authority` | Когда возникает | Что делает `reopen_closed` |
|---|---|---|
| `reviewer` | Ревьюер принял отказ автора (`accepted_reason`) или подтвердил починку | Обычный круг и обычный порог эскалации |
| `human` | Человек ответил на вопрос, принял риск, решил `wont_fix` | **Всегда возвращается человеку**, независимо от severity: отмена явного решения человека не полномочие системы |
| `policy` | Спор был ниже порога, и система закрыла его автоматически принятием отказа — ревьюер при этом настаивал | Обычный круг и обычный порог. Если новое наблюдение подняло `escalation_severity` до порога, вопрос человеку возникает штатно — впервые |

Третье значение обязательно: без него случай «ревьюер настаивал, но порог не
пройден» не имеет владельца закрытия, и правило «следуй каналу» для него не
определено. Заодно это ровно тот случай, ради которого накопитель переживает
принятый отказ: спор, задавленный порогом сегодня, всплывает сам, если завтра
evidence станет серьёзнее.

Изменившийся код создал **другую** проблему → это `new`, а не переоткрытие.

Порог при этом не трогается ни для чего, что человек не решал лично.

## 8. Человек в контуре

**Канал один — Telegram-бот, двусторонний, long polling.** У каждого инстанса
свой токен и свой allowlist: общий update stream означал бы, что ответ одному
инстансу закрывает гейт другого. В каждом сообщении — короткий
instance/run/question ID.

**Формат вопроса** (требование к вопросу, не к ответу): суть в двух фразах, чем
вызван и на что влияет, варианты с оценкой уверенности там, где они уместны.
Вопрос без вариантов законен — бывают вопросы вида «расскажи, как надо».

**У вопроса об исчерпании кругов варианты стандартные**, и это контракт промпта и
бота, а не свободное сочинение агента:

| Вариант | Что делает система |
|---|---|
| Разрешить ещё одну правку | `max_author_revisions` для этой стадии увеличивается на 1, та же кампания остаётся в `fix_cycle`, цикл продолжается с прежними счётчиками |
| Принять как есть | Открытые замечания закрываются с `resolution_authority = human`, кампания переходит в `closed_escalated`, стадия завершается |
| Остановить ветку | Кампания переходит в `closed_escalated`, ветка помечается неуспешной, соседние продолжают |
| Свой текст | Интерпретирует агент, с обычным лимитом в один переспрос |

`closed_escalated` означает окончательно завершённую после вмешательства
человека кампанию, а не само ожидание человека. Пока вопрос открыт,
`review_campaign.closed_at` остаётся `NULL`; остановка выражена blocker'ом
ветки и durable-записью `human_question`. Это позволяет ответу «ещё одна
правка» продолжить **ту же** кампанию без сброса `author_revision_count` и
`review_check_count`.

В самом вопросе обязательно различаются два случая, ради которых причина
остановки хранится в состоянии: «автор трижды не смог починить одно и то же» и
«ревьюер нашёл новое на последней проверке». Это разные ситуации, и варианты
человек выбирает в них разные.

**Ответ** — свободный текст. Короткий «A» закрывает гейт детерминированно, без
участия модели; свободный текст интерпретирует агент и обязан переспросить, если
не понял. **Переспрос ограничен**, дефолт — один: дальше бот просит ответить
вариантом или reply с ID вопроса, без новой интерпретации.

**Порядок закрытия и что именно останавливается.** Ответ сначала
durable-записывается, затем снимается блокировка `human_question` — и на её место
ставится блокировка `awaiting_continue`, которую снимает только явная команда.
Останавливается при этом **только эта ветка**: соседние независимые ветки всё
время работали и продолжают работать, а состояние прогона по-прежнему
вычисляется из веток. Глобальный `paused` бывает ровно один — когда человек сам
поставил прогон на паузу.

Иначе получается противоречие: требование «ветка встала, остальные едут» и
одновременно «после ответа весь прогон стоит».

**Молчание человека** — ждём сколько угодно. Ни таймаутов, ни решений за
человека, ни закрытия прогона. Взамен «ждёт ответа» обязано отличаться от
«работает» и «завис» с одного взгляда.

**Обязательные точки утверждения** задаются конфигом; по умолчанию одна —
тех-дизайн. Механика та же, что у открытых вопросов.

**Ручное управление** (в порядке возрастания цены): отмена прогона, пауза и
снятие, ручная правка артефакта с продолжением, перезапуск стадии. Последние две
делаются только после того, как заработают ревизии артефактов.

## 9. Агенты: адаптеры, профили, контекст

### 9.1. Три адаптера, четыре обязательных профиля и один желательный

Адаптер пишется на CLI-семейство и описывает механику: проверить установку,
собрать argv без shell-интерполяции, передать промпт и рабочий каталог, включить
структурированный вывод, получить и возобновить сессию, определить активность и
завершение, применить read-only, мягко и затем жёстко остановить группу
процессов, классифицировать исход.

| Профиль | Адаптер | Бэкенд |
|---|---|---|
| `claude` | claude | Anthropic, подписка |
| `claude-m` | claude | MiniMax через `ANTHROPIC_BASE_URL` |
| `claude-z` | claude | Z.AI GLM через `ANTHROPIC_BASE_URL` |
| `codex` | codex | OpenAI, подписка |
| `cursor-agent` | cursor | Cursor, свой аккаунт |

M0-проверка 2026-08-03 на Linux VPS подтвердила headless для четырёх
обязательных профилей: Anthropic `claude-opus-5`, MiniMax `MiniMax-M3`, Z.AI
`glm-5.2`, OpenAI `gpt-5.6-sol`. `cursor-agent` на этом VPS не установлен и
зафиксирован как недоступный желательный профиль. Полный наблюдённый контракт и
версии — в `../design/vendor-cli-contracts.md`.

После ревью Claude fixtures перезаписаны с `--safe-mode
--disable-slash-commands --strict-mcp-config` и явным role-specific `--tools`.
Это сохраняет `HOME` для подписочной auth, но не наследует операторские MCP,
skills и memory. Structured init проверяется до допуска результата в кворум.

**Обязательны четыре первых профиля** — они дают четыре независимых мнения
(Anthropic, MiniMax, Z.AI, OpenAI), чего хватает на два кворума и на правило
свежести. **`cursor-agent` очень желателен, но не блокирует v1**: readiness probe
проверяет только профили, объявленные в конфиге инстанса, а критерий готовности
не требует пятого.

**Профиль — это данные, а не bash-обёртка:** executable, requested model/tier,
env-маппинг, `secret_ref`, флаги, allowlist переменных. Рантайм сам подставляет
окружение в запуск процесса. Плюсы против нынешних скриптов в `~/.local/bin`:
исчезает симлинк-хрупкость, секрет не проходит через `bash` и не виден в
`ps aux` как аргумент обёртки.

**Requested и actual модель пишутся обе.** У `claude-z` запрос `opus` даёт
`glm-5.2`; без второго поля правило свежести ревьюера технически не обеспечить.

**Вендор недоступен** — ждём и повторяем, после N попыток к человеку. Подмены
вендора нет: расстановка ролей из конфига сохраняется, иначе «ревьюер другого
вендора» втихую становится тем же, что автор.

**Секреты: что гарантируем и чего не гарантируем — честно.** Профиль-обёртка по
своему устройству передаёт токен бэкенда через окружение дочернего процесса.
Значит агент, у которого есть shell, технически может его прочитать: запрет
«не читать секреты» держится промптом, как и остальные три запрета, и hard
guarantee здесь нет. Что гарантируется на самом деле:

- в конфиге лежит только `secret_ref`, никогда само значение;
- **redaction выполняется до записи** транскрипта, а не при просмотре: значения
  всех переменных из allowlist профиля заменяются маркером. Формулировка «храним
  полностью сырой транскрипт» уточняется — сырой относительно формата CLI, но с
  обязательной заменой известных секретов;
- секрет не попадает в промпт, событие, манифест и артефакт;
- где вендор поддерживает собственное хранилище учётных данных вместо env, оно
  предпочтительнее — тогда токен не проходит через окружение вовсе.

### 9.2. Ревьюер строго read-only — три слоя

1. Native-режим вендора: `--sandbox read-only` у codex; у claude изолирующие
   `--safe-mode --disable-slash-commands --strict-mcp-config` и **замена**
   toolset через `--tools Read,Grep,Glob`. `--allowedTools` только выдаёт
   разрешение и границу не создаёт. `--permission-mode plan` для этой цели
   запрещён: probe показал запись plan-файла вне checkout. `--mode ask` у cursor
   остаётся гипотезой до появления бинаря.
2. Работа в disposable checkout на зафиксированном SHA; результат возвращается
   через stdout, в artifact repo пишет рантайм.
3. Сверка tracked, untracked и index до и после. Любая мутация ревьюера —
   `mutation_violation`: результат не участвует в кворуме, checkout удаляется,
   вызов повторяется или эскалируется.

### 9.3. Контекст и передача

Политика контекста задаётся конфигом стадии; агент себе контекст не выбирает.
Четыре режима: только задача / задача плюс объявленные артефакты / cut-off /
продолжить свою сессию.

**Cut-off пишет уходящий агент** по жёсткому шаблону. Критерий приёмки —
принимающий должен суметь действовать, прочитав ровно один файл.

Проверяется **структурно и кодом**: обязательные секции (задача, текущее
состояние, следующее действие, затронутые файлы, открытые вопросы), непустые
критерии приёмки, резолвимость упомянутых файлов и SHA, digest. Это ловит пустые
и шаблонные передачи без единого вызова модели.

Модельная самопроверка приёмки в v1 **не делается**: принимающий склонен
отвечать «понял», а обычный механизм вопроса человеку уже покрывает реальную
блокировку — и срабатывает там, где непонимание проявилось, с конкретным
контекстом. Если реальные прогоны покажут провалы передачи, механизм добавляется
так: проверяет **будущий исполнитель**, продолжая свою сессию; одна доработка;
при исчерпании в артефакт пишется отметка «приёмка отклонена, причина,
продолжаем как есть»; доработка возможна, только пока сессия уходящего агента
резюмируется, иначе сразу отметка, а на критичной границе — вопрос человеку.
Обязательным имеет смысл делать только на дорогих границах, прежде всего
«дизайн → разбивка на таски».

### 9.4. Запреты

Четыре, держатся промптом и обёртками, не изоляцией: прод и чужие среды, файлы
вне рабочего каталога, чтение секретов, `git push --force`. Детерминированный
git-сервис просто не предоставляет запрещённых операций. Мы не называем это
песочницей: контейнеров нет, и security-claim из этого не делается.

Ограничений по конфиденциальности нет: код рабочих проектов можно отправлять
всем профилям.

## 10. Верификация, git, артефакты

**Рецепты верификации** — свободный текст в конфиге проекта, допустимо «проверь
сам». Где инструкция есть, агент следует ей буквально; где нет — решает сам, но:

- результат фиксируется структурированно: что запускали, код возврата, вывод;
- выбранный способ пишется в артефакт прогона, иначе следующий прогон придумает
  иначе и результаты станут несравнимы;
- по возможности тот же план прогоняется **до** изменений как baseline, чтобы
  отличить «было сломано» от «мы сломали».

**Кто исполняет придуманные агентом команды — это граница, и её надо задать
явно.** Агент-планировщик возвращает **структурированный `VerificationPlan`**
(список команд с рабочим каталогом и аргументами), а **исполняет его
детерминированный сервис**, предварительно проверив каждую команду против
политики: рабочий каталог внутри агентского клона или checkout верификации, argv
без shell-интерполяции, никаких обращений к прод-средам и путям с секретами.
План и результат сохраняются оба.

Это единственное место во всей системе, где команды, придуманные моделью,
исполняются кодом, — и потому единственное, где **пять проверок политики команд
выполняются кодом, а не промптом:** `cwd`, shell-синтаксис, исполняемый файл,
denylist путей и адреса прод-сред. Это не то же самое, что четыре общих запрета
агентам из §9.4. Если отдать исполнение самому агенту, граница исчезает и
проверки снова держатся на честном слове. При реализации это забывается первым,
поэтому записано отдельным абзацем; механика — `architecture.md` §10.

**Красные тесты — блокер:** пока не зелёные, задача не сделана. Критерий
объективный и обсуждению с моделью не подлежит. Но baseline разводит два случая,
и второй — отдельный переход, а не отказ:

| Baseline | Сейчас | Что делает система |
|---|---|---|
| Зелёный | Красный | Обычный отказ, следующий круг правок автора |
| Красный | Красный по той же причине | **Вопрос человеку:** чиним чужое или выносим отдельной задачей. Не наш провал, но и «сделано» не получается |
| Красный | Красный по другой причине | Обычный отказ: мы добавили новую поломку поверх старой |

Агент не имеет права ни молча чинить чужое, ни тихо списывать падение на
предшественников — обе развязки решаются вопросом человеку, а не моделью.

**Верификация идёт в отдельном checkout с явно разрешённой мутацией.** Не в
checkout ревьюера — сборка плодит артефакты и это нарушение read-only; не в
worktree автора. Тот же принцип «disposable checkout на точном SHA», но с
инвертированным контрактом.

**Файл заметок по проекту** читается во всех промптах и пополняется по ходу
прогона; для шага верификации пополнение обязательно. Подаётся агентам
**снимком из artifact repo**, а не живой копией из клона: иначе он меняется под
ногами read-only ревьюера.

Прореживание — **отдельный шаг в конце прогона**, с тремя ограничениями: он идёт
**отдельным коммитом**, чтобы в истории было видно, что именно вычистили; он
имеет право менять **только этот файл**; у файла есть потолок размера, по
достижении которого прореживание обязательно. Начинаем с одного файла на проект;
разбивать по темам — только если он вырастет настолько, что целиком в промпт
класть станет дорого.

**Git-политика:** агенты работают в отдельном клоне и локально могут всё. Наружу
у РабОрка отдаётся только ветка задачи, запушенная в рабочий remote; PR в master
выставляет человек. У СвойОрка допустим полный цикл. Право на push — параметр
проекта, раздельный для веток задач и всего остального.

**Артефакты пишет детерминированный сервис**, а не произвольный шаг агента. В
манифесте: `run_id`, `stage_id`, попытка и профиль, входные ссылки, точный code
SHA, digest содержимого, версия схемы.

## 11. Конфигурация флоу

**YAML + Pydantic `extra="forbid"`.** Неизвестное поле — ошибка загрузки, а не
тихое игнорирование: по принятому решению четвёртый и последующие флоу пишет
агент, и он не удивится, что его правка ничего не изменила.

**Канонический вид с хешем показывается до запуска** и он же участвует в drift
check. Валидация «что понял парсер» — обязательный шаг, а не удобство.

**Длинные промпты и рубрики живут отдельными файлами** и подключаются по
`id + hash`. Это снимает многострочные строки — самое хрупкое место YAML — и
одновременно даёт версионирование промптов для манифеста попытки.

Против ловушек YAML: строгие типы, запрет неявных булевых (`on`/`yes`),
обязательные кавычки у версий. Проверяется теми же golden-тестами, что и
канонический вид.

Каждый флоу явно задаёт: роль → профиль, размер кворума, число кворумов на
стадию, retry-бюджеты, `max_author_revisions`, политику контекста и обязательные
точки утверждения. Всё это вычисляет парсер, а не выбирает агент по ходу. Число
проверок в конфиге не задаётся — оно выводится из `max_author_revisions`.

**Вход прогона:** текст задачи в аргументе команды или Markdown-файл. Запуск
всегда явный, руками. Интеграций с трекерами нет, вебхуков нет, обратной записи в
тикет нет.

## 11a. Топология трёх флоу

Стадии перечислены полностью — при сжатии их легко потерять, а именно они и есть
конвейер из требований. «Кворумы» — сколько независимых кампаний ревью подряд
проходит стадия; «линии» — сколько параллельных ревьюеров внутри одной кампании.
Все цифры — умолчания конфига, а не константы кода.

| # | Стадия | Кто | Линии / кворумы | Контекст | Гейт |
|---|---|---|---|---|---|
| 1 | Baseline-верификация | код | — | — | — |
| 2 | Кампания ревью | ревьюеры | 2 линии, 1 кворум | только задача + диапазон коммитов | — |

молча превратить в допущение, особенно если он касается findings или остановки
ветки.

**Два кворума** стоят у стадий 3 и 8 не случайно: дизайн и границы задач — те
места, где ошибка стоит всего прогона, и второй кворум ведёт заведомо свежий
участник. Два кворума — это две последовательные кампании, а не две параллельные
линии внутри одной: линии проверяют одновременно и не видят выводов друг друга,
кампании идут одна за другой и вторая работает по результату первой.

## 12. Наблюдаемость

CLI-команды. Минимум, который обязан быть виден:

- дерево прогона: стадии, что идёт, что готово, что ждёт;
- **«ждёт ответа человека» отдельно от «работает» и «завис»** — раз напоминаний
  нет, это единственная защита от потерянной задачи;
- незакрытые findings и споры, с `escalation_severity` и `historical_max` рядом;
- автоматически принятые отказы — чтобы систематический перекос severity был
  заметен;
- какой круг проверки идёт и сколько осталось;
- какой профиль исполняет шаг, requested и actual модель.

Хранятся транскрипты сессий в формате, как их отдаёт CLI, с обязательной
redaction известных секретов до записи, плюс метаданные шага. Diff попыток
берётся из git агентского клона по `input_sha` / `output_sha` — отдельно не
хранится.

## 13. Инварианты, которые обязан держать код

Проверяемый список. Каждый пункт — либо транзакция, либо констрейнт, либо
валидация до записи.

**Про findings:**

1. Каждое открытое замечание закрыто явным статусом; незакрытый ID = круг не
   закрыт.
2. Каждое наблюдение классифицировано **ровно одним** исходом reconciliation, не
   потеряно и не попало в две группы.
3. `existing_open` допустим только для открытого ID нужного scope;
   `reaffirmed_closed` — только для закрытого ID с последним resolution
   `accepted_reason`; `reopen_closed` — для любого закрытого ID нужного scope.
4. **Счётчиков два, и они независимы:** `author_revision_count` и
   `review_check_count`. Общего счётчика, который растёт дважды за цикл, не
   существует. Настраивается только `max_author_revisions` (дефолт 3);
   `max_review_checks = max_author_revisions + 1` — производная, а не отдельная
   ручка.
5. **Оба растут только после `StepAttempt.succeeded`** соответствующей роли:
   правка засчитывается, когда автор довёл попытку до валидного результата,
   проверка — когда ревьюер выдал валидный вывод. `interrupted`, `hung`,
   `transient`, `contract_error` и `failed` не двигают ни один из них.
6. **Кап проверяется в момент решения «продолжать ли», а не по достижении
   числа.** `clean` даёт успех при любых счётчиках; после последней разрешённой
   правки проверка всё равно выполняется; блокировка `human_question` ставится
   только когда проверка требует ещё одной правки, а правки исчерпаны.
   `review_check_count` никогда не превышает `max_author_revisions + 1` — это
   утверждение для проверки, а не второй гейт.
7. Личность выдаётся один раз и не пересчитывается.
8. Каждое наблюдение несёт `severity_suggested` либо `unchanged_from`; значение
   severity принадлежит фиксированному enum; `unchanged_from` ссылается только
   назад, в пределах того же finding'а и того же периода открытости, без циклов.
9. `escalation_severity` монотонна вверх в пределах периода; автоматического
   понижения не существует.
10. Исход ревьюера совместим с disposition автора.
11. Решение по finding'у выносит владелец этого круга, и оно единственное.
12. Новая кампания не получает сессию прежнего кворума; линия внутри кампании
    свою сохраняет.
13. У каждого закрытия записан `resolution_authority`; `reopen_closed` следует
    ему.

**Про состояние:**

14. Переход состояния и его событие пишутся одной транзакцией.
15. Все переходы из §6.6 атомарны целиком, включая блокировку графа вместе с
    вопросом человеку и закрытие задачи вместе с результатом попытки.
16. Ответ человека записан до снятия блокировки.
17. После перезапуска нет двойного перехода и нет двойной работы: оставшиеся
    `running` попытки становятся `interrupted`, а новая попытка не стартует, пока
    прежняя process group не подтверждена мёртвой.
18. Активен ровно один экземпляр сервиса на каталог состояния (instance lock).
19. Не более одной активной попытки на линию или шаг (partial unique index).
20. Не более одного принятого ответа на вопрос; `UNIQUE(transport, update_id)`.
21. FK между кампанией, кругом, замечанием, наблюдением и попыткой;
    `UNIQUE(campaign_id, finding_id, round_no)`.
22. Состояние `Run` вычисляется из веток и блокировок, а не выставляется
    напрямую. «Ждёт человека» на уровне ветки — это наличие блокировки, а не её
    состояние.

**Про граф:**

23. Нет self-edge, нет дублей рёбер, нет циклов — проверено атомарно со
    вставкой.
24. Пустая готовность при незакрытых задачах и отсутствии любой легитимной
    блокировки — `invalid_graph`, не `succeeded`.
25. Запись в граф возможна только атомарным импортом утверждённой ревизии.

**Про безопасность и гигиену:**

26. Секрет не появляется в промпте, событии, манифесте и артефакте, а в
    транскрипт попадает только после redaction.
27. РабОрк не создаёт ни одного служебного файла или коммита в репозитории кода.
28. Мутация ревьюера аннулирует его результат.
29. Шаг прореживания заметок меняет только файл заметок.

**Про согласованность завершения:**

30. У review-кампании `closed_at` заполнен тогда и только тогда, когда её
    состояние терминально: `closed_clean`, `closed_escalated` или
    `closed_cancelled`.

## 14. Приёмочные сценарии

Happy path недостаточно. До объявления версии готовой должны проходить:

- убийство процесса на каждой границе: до запуска CLI, во время, после
  завершения до фиксации состояния, после фиксации до следующего шага;
- дублирующийся Telegram update и повторная доставка из outbox;
- ответ на старый, чужой или уже закрытый вопрос;
- блокировка поставлена, а вопрос не записан, и наоборот;
- вендор: rate limit, протухший логин, отсутствующий бинарь, битый JSON,
  процесс без вывода, живой вывод без завершения, игнорирование SIGTERM;
- ревьюер изменил tracked, untracked, index или файл артефакта;
- одна линия кворума упала, вторая закончила — частичный результат не
  засчитывается как консенсус;
- автор потерял замечание или поместил его в две disposition;
- отказ автора не принят ревьюером;
- ровно три правки дают четыре проверки; **четвёртая проверка выполняется** и,
  если она `clean`, стадия завершается успехом, а если требует ещё правки — на
  ветку встаёт блокировка `human_question`. Проверяются обе границы: третья
  правка не блокирует ветку до своей проверки, и чистая четвёртая проверка не
  блокирует ветку вовсе. Пока вопрос открыт, кампания остаётся `fix_cycle` с
  `closed_at = NULL`; разрешённая человеком дополнительная правка продолжает ту
  же кампанию и прежние счётчики, а окончательный ответ переводит её в
  `closed_escalated`. Соседняя независимая ветка в это время реально работает,
  и `Run` остаётся `running`;
- новое замечание на последнем круге не сбрасывает кап, и причина остановки
  читается как «новое», а не как «трижды не смог»;
- ревьюер объявил `new` для открытого замечания — ловится сохранённым слепым
  выводом и отчётом похожести;
- принятый отказ всплыл в финальной кампании — закрывается ссылкой, без нового
  круга и без вопроса; переоткрытие человеком-закрытого уходит человеку;
- baseline уже красный, новая проверка красная по той же причине — уходит
  вопросом человеку, а не отказом автору; по другой причине — обычный отказ;
- flow или конфиг изменились между остановкой и `continue`; принятый дрейф по
  code SHA обесценивает прежнее ревью, по ревизии плана — переимпортирует граф;
- неизвестное поле в YAML ломает валидацию; канонический вид совпадает с тем,
  что реально исполнено;
- граф с циклом или ссылкой на несуществующую задачу не даёт ложного успеха;
- **CLI зависает раз за разом** — по исчерпании `hang_retry_budget` ветка уходит
  к человеку, а не перезапускается бесконечно;
- **агент трижды вернул невалидный вывод** — это не три круга ревью, и вопрос
  человеку формулируется как контрактная проблема, а не как несогласие;
- **второй экземпляр сервиса** не стартует на том же каталоге состояния;
- **осиротевший процесс агента** после падения сервиса погашен до создания новой
  попытки;
- **ревьюер сослался на закрытый ID** в `existing_open` — contract error;
- **severity вне enum** или `unchanged_from` через границу периода — contract
  error на приёме, а не позже.

Тесты идут на фейковых CLI-исполняемых с golden-фикстурами; реальные vendor smoke
tests — отдельным opt-in набором.

## 15. Допущения и риски

**M0 проверен запуском 2026-08-03.** Headless-контракты Claude Code 2.1.220 и
Codex CLI 0.146.0 сняты на Linux VPS для Anthropic, MiniMax, Z.AI и OpenAI;
фикстуры и fake CLI сохранены. Проверка подтвердила четыре разные фактические
пары provider+model и не изменила стек, но уточнила механику адаптеров: Claude
read-only делается изолированным explicit toolset, Codex требует protocol
completion marker даже при exit 0, а старые предполагаемые коды ошибок нельзя
считать фактом. Fake CLI отдельно моделирует невалидный доменный result и
синтаксически повреждённый vendor stream, чтобы не смешивать два класса ошибок.
`cursor-agent` остаётся непроверенным по формату, потому что бинаря на VPS нет;
для желательного профиля это принятый неблокирующий исход. WSL2-специфичное
допущение recovery также не проверено, поскольку probe шёл на обычном VPS.

**Явные допущения:**

| Допущение | Что если неверно |
|---|---|
| Четырёх обязательных профилей хватает на два кворума и на правило свежести | Уменьшить число кворумов, довести `cursor-agent` до обязательного или завести пятый бэкенд — конфиг, не код |
| Граф задач останется в пределах десятков задач на прогон | Свой SELECT перестанет быть тривиальным; тогда либо усложняем схему честно, либо включаем `bd`-реализацию модуля |
| Лимиты подписок выдержат параллельные линии ревью | Разводить линии по разным подпискам при настройке кворумов |
| Модели будут дисциплинированно отвечать по ID | Ужесточить схему ответа: отклонять вывод без полного покрытия открытых ID до записи. Возврат к сопоставлению по содержимому запрещён |
| Компактный ledger дешевле полного | Эмпирическая настройка, меняется без последствий для схемы |
| **Окружение готовит человек**, и оно остаётся готовым между прогонами: CLI установлены, логины живы, тулчейн на месте | Система не чинит, а отказывается стартовать с внятным отчётом. Если ручная подготовка окажется слишком частой рутиной — это повод к скрипту-помощнику **рядом** с системой, но не к автоустановке внутри неё |
| **Состояние прогона живёт в одной локальной SQLite и не реплицируется** | Смерть диска = потеря прогона целиком. Код и артефакты переживают в git, состояние — нет. Для личного инструмента принято осознанно; частично смягчается тем, что граф задач восстановим из утверждённой ревизии task-breakdown, а артефакты и код лежат в репозиториях. Если цена окажется неприемлемой — дешёвая мера первой очереди это периодический `VACUUM INTO` рядом с транскриптами, а не репликация |

**Зафиксированное особое мнение.** По области накопления `escalation_severity`
остаётся несогласный: считать максимум не за период открытости, а за всю жизнь
ID. Довод — новая кампания не должна иметь возможности неявно понизить уже
обнаруженную серьёзность. Он удовлетворён механикой (`resolution_authority` плюс
правило про `accepted_reason` плюс `historical_max` в CLI), но записан, потому
что расхождение остаётся для случая «починили, подтвердили, появилось снова».

**Критерии пересмотра стека:**

- ядро начинает превращаться в общий workflow-engine с динамическими
  subworkflow и произвольным routing → рассмотреть Conductor-derivative;
- параллельная реализация, merge queue и веб становятся центральными →
  пересмотреть Forge;
- десятки постоянно живущих агентов → это другой продукт, смотреть Gas Town;
- у конкретного CLI нет стабильного headless → PTY только для этого адаптера,
  основной путь не менять.

## 16. Порядок работ

**Шаг 0. Проверка вендорских CLI, 2–3 дня.** Принимает ли каждый профиль
неинтерактивный промпт, есть ли машинно выделяемый финальный вывод, продолжается
ли сессия, работает ли print-режим `cursor-agent` по подписке без браузера.
Выход — не демо, а зафиксированные argv/output-фикстуры, из которых сразу
получаются фейковые CLI для тестов.

**Шаг 1. Первый срез: `review-commit`.** Принять repo/ref/base ref и конфиг
проекта; зафиксировать SHA и baseline-верификацию; запустить кворум в disposable
read-only checkout; сохранить структурированные findings; дать автору
исправить, получить dispositions, повторить ревью с капом; при споре или
исчерпании задать вопрос человеку; пережить kill/restart и продолжиться только
по `continue`; завершиться на чистом финальном ревью и зелёной верификации.

На этом срезе стабилизируется схема домена. Не начинать одновременно DSL для
дизайна и таск-планов: иначе ошибки state machine смешаются с ошибками
декомпозиции.

**Шаг 2. Фича в существующий проект.** Добавить дизайн, кворум по дизайну, граф
задач, последовательные таск-планы, реализацию и ревью по каждой задаче,
финальную кампанию, поддержание файла заметок. Первым делать РабОрк: он строже по
артефактам и git, и тем самым задаёт безопасные умолчания.

**Шаг 3. Новый проект.** Research/bootstrap-стадии и настраиваемые точки
утверждения. Только после трёх работающих флоу агенту разрешается генерировать
новый флоу по образцу — и сгенерированный YAML всегда проходит строгую валидацию
с показом канонического вида до запуска.

**Критерий MVP:** одна реальная задача проходит конвейер до конца, и результат не
стыдно показать.

Ориентир по объёму: дешёвая обвязка — недели, дорогое ядро (протокол ревью,
вопросы человеку, ревизии, живость) — основная часть работы. Первый срез
реалистично получить заметно раньше остального.
