# Нормативный шаблон таск-плана

Этот файл — единственный шаблон детального таск-плана в проекте. Для нового
плана копируется блок ниже; параллельные сокращённые шаблоны не заводятся.
Правила жизненного цикла планов и пакетов заданы в
[`../design/task-plans.md`](../design/task-plans.md) §3.1 и §9.

Планы хранятся как `docs/task-plans/<пакет>/<ID>.md`, например
`docs/task-plans/p1-a/t1.1.md`. В содержимом ID и пакет должны точно совпадать с
графом в `docs/design/task-plans.md`; в пути они нормализуются в нижний регистр.

Перед передачей на содержательное ревью автор удаляет все подсказки в
`<!-- комментариях -->` и заменяет все `<плейсхолдеры>`. Вопрос допустимо
записать в остановленном черновике, который передаётся человеку, но не
ревьюеру. После ответа план обновляется, и в прошедшем структурную приёмку плане
нет `TBD`, открытых вопросов или ссылок только на ветку без точного commit SHA.

## Структурная приёмка плана

План можно передавать на содержательное ревью, только если:

1. все 12 разделов присутствуют и заполнены; для отсутствующих рисков,
   допущений или non-goals явно написано «нет», а раздел не удалён;
2. снимки репозитория и проектных документов указаны точными достижимыми commit
   SHA; planning baseline пакета и implementation parent не подменяются этими
   историческими SHA;
3. каждая зависимость названа вместе с потребляемым результатом, а не только ID;
4. у каждой публичной границы есть один владелец и перечислены потребители;
   для программного API приведены точные public-типы и сигнатуры, immutable
   input/output DTO, модель ошибок и владелец транзакции — HTML-подсказка §5
   сама по себе этим требованием не считается;
5. каждый `AC-*`, `INV-*` и `FAIL-*` связан хотя бы с одной проверкой `V-*`;
6. команды `test`/`lint` записаны argv-массивами без `&&`, `|`, перенаправлений
   и подстановок; у строк `inspection` вместо argv записаны точное действие и
   ожидаемое свидетельство;
7. в плане нет открытых вопросов, скрытых будущих зависимостей и работы,
   принадлежащей другому плану;
8. оценка укладывается в границы задачи из графа либо расхождение объяснено и
   граф обновлён до ревью.

## Git-границы реализации

После принятия всего пакета создаётся один planning baseline marker commit. До
первой правки каждой задачи на чистом линейном `main` фиксируется текущий полный
SHA — её `implementation parent`. Он не обязан совпадать ни со снимком паспорта,
ни с closing commit прямого предшественника: между ними уже могут находиться
принятые независимые задачи.

Closing commit задачи обязан содержать trailers:

```text
Planning-Baseline: <full SHA marker commit пакета>
Implementation-Parent: <full SHA перед первой правкой задачи>
```

Все inspection-проверки scope используют только
`implementation_parent..closing_commit`. Если работа переходит между сессиями,
оба SHA до первой новой правки повторяются в именованном `implementation_scope`
cut-off и его `referenced_shas`; exclusive sibling/merge ranges для линейного
`main` не применяются.

Между фиксацией implementation parent и closing commit `main` зарезервирован за
этой задачей: коммиты других задач не вклиниваются. Скрипт
`python3 scripts/checks/check-task-git-scope.py <closing SHA>` проверяет
trailers, full SHA, ancestry, first-parent range и отсутствие merge; inspection
из §10 отдельно доказывает, что все файлы range принадлежат текущей задаче.

Если во время реализации меняются публичный контракт, владелец данных,
транзакционная граница, зависимость между задачами или критерий приёмки,
затронутые планы возвращаются на ревью по `docs/design/task-plans.md` §3.1.
