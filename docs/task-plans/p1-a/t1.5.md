## 2. Цель и наблюдаемый результат

**Цель.** Реализовать чистый домен reconciliation, который сводит первичные
слепые observations и новые observations последующих `fix_check` в устойчивые
личности findings, не теряет и не дублирует ни одно наблюдение и не отменяет
решение человека автоматически.

Reconciliation выполняется после слепого первичного ревью и повторно, если
проверяющие авторскую правку вернули `review.decisions.v1.new_observations`.
Его агент видит новые observations текущего круга и допустимый ledger,
предлагает группы и для каждой выбирает один из четырёх исходов. После этого
рантайм, а не модель, проверяет полноту и допустимость ссылок и выдаёт новым
группам личности. В первичном круге T1.5 дополнительно определяет его исход; в
`fix_check` — дополняет open set до решения T1.4.

«Новые» здесь означает observations без известной личности: все blind
observations первичного круга и только `new_observations` из `fix_check`.
Follow-up observation внутри `decisions[*]` уже имеет target во внешнем
`finding_id`; по решению Q45 при `still_present`/`insists` его проверяют
T1.6/T1.7b и механически связывают как `recurrence`, не передавая T1.5.
Сочетание follow-up с `verified_fixed`/`accepted_reason` отвергает T1.7 до этой
границы.

**Наблюдаемый результат.** Для полного immutable snapshot наблюдений, ledger и
предложения reconciler'а функция `reconcile()` детерминированно возвращает
либо готовый набор intent'ов `finding`/`finding_observation_link` для текущего
круга, либо ожидание решения человека по переоткрытию human-закрытого finding.
Для context `discovery` отдельная чистая функция выводит `clean` или
`needs_revision`; для `fix_check_new` intents входят в `CheckFacts` T1.4 и
делают `cap_exhausted_new` достижимым. Любое из восьми нарушений
`agent-contracts.md` §4
отклоняет результат целиком как `contract_error` со структурированной
диагностикой. При исчерпании `contract_retry_budget` отдельная функция строит
вопрос с полным сырым набором наблюдений и ledger, не выдавая механически новые
ID. Всё проверяется unit-тестами без SQLite, asyncio и процессов агентов.

## 3. Границы

**Входит:**

- устойчивый `dedup_key` по нормализованным полям observation и группировка
  точных совпадений только внутри одного круга;
- immutable domain types для context `discovery`/`fix_check_new`, наблюдений,
  допустимого ledger, предложения reconciler'а, intent'ов личности/связи,
  human gate и исхода первичного круга;
- `build_reconciliation_units()` для безопасного автоматического сведения
  дословных совпадений до обращения к reconciler'у;
- `reconcile()` с восемью семантическими проверками контракта до формирования
  любого persistence intent;
- четыре исхода `new`, `existing_open`, `reaffirmed_closed`, `reopen_closed` и
  точное отображение в `first_seen`, `recurrence`, `reaffirmation`, `reopening`;
- строгая граница Q44: `reaffirmed_closed` только после `accepted_reason`; для
  того же finding после остальных закрытий используется `reopen_closed`, а
  другая или неуверенно связанная проблема получает `new`;
- создание `NewFindingIntent` для каждой новой группы, выбор владельца как
  линии с наименьшим индексом среди observation этой группы и сохранение
  ground-truth title первого появления;
- двухшаговый путь `reopen_closed` для human-закрытого finding: ожидание без
  результата круга, затем ответ `reopen` или `keep_closed`;
- исход первичного `discovery`-круга: `clean`, если после полного
  reconciliation в текущем круге нет работы для автора, иначе
  `needs_revision`;
- contribution `fix_check_new`: новая identity получает
  `first_round_id=current_round_id`, а author-work findings входят в open set
  текущего check до `decide_after_check()`;
- payload вопроса `reconcile_failed` после исчерпания retry budget: сырые
  observations, ledger и последние ошибки без автоматической классификации;
- табличные unit-тесты точной склейки, восьми нарушений, четырёх исходов,
  human-пути и обоих исходов первичного круга.

**Не входит:**

- JSON/Pydantic-схема `review.reconciliation.v1`, транспортные маркеры и
  rendering сообщения о повторной попытке — `T1.7`; T1.5 получает уже
  разобранные значения, но повторно проверяет несущую семантику;
- чтение/запись SQLite, выдача конкретного публичного `F-*`, создание
  `finding_round`, событий, вопросов, outbox и blocker — `T1.3`/`T1.7b`;
- валидация и direct link follow-up observation внутри `decisions[*]`: проверка
  сочетания только со `still_present`/`insists` принадлежит T1.7, проверка того
  же finding/периода — T1.6, атомарная запись observation + `recurrence` +
  решения — T1.7b; такой input не проходит T1.5;
- переходы campaign и cap: T1.5 не импортирует типы T1.4, а T1.7b отображает
  его независимый исход первичного круга в `RoundResult`/`CampaignEvent` либо
  contribution `fix_check_new` в `CheckFacts` перед вызовом T1.4;
- вычисление периодов и severity, применение порога и вывод authority/closes-
  period из resolution — `T1.6`; T1.5 использует уже подготовленный status и
  authority из ledger и владеет выбором обычного либо human reopen-пути;
- подсчёт retry budget, запуск свежей сессии `reconciler`, профили, runner и
  планирование параллельных веток — `T1.9`, `T1.17`, `T1.18`; T1.5 задаёт
  обязательный invocation-контракт и payload на границе исчерпания бюджета;
- отправка и интерпретация свободного ответа человека — `T1.15`/`T1.16`;
  T1.5 принимает типизированный выбор и отображает его в link intent;
- similarity-поиск, автоматическое объединение похожих title/file и
  переиспользование `dedup_key` между кругами или кампаниями;
- изменение контракта findings либо правила остановки ветки.

Human gate T1.5 блокирует только текущую ветку: пока хотя бы один
`reopen_human_closed` не разрешён, текущий круг остаётся без result, а
частичный набор не уходит автору. Campaign сохраняет текущее состояние:
`reconciliation` для первичного круга, `fix_cycle` для `fix_check_new`. T1.5
выражает остановку отсутствием готового completion; фактическое состояние
ветки и продолжение соседних независимых веток обеспечивают T1.7b и T1.18.

`ReconciliationUnit` сохраняет все raw observation IDs. Её `unit_id` — public
ID observation с минимальным `seq`, то есть это не новый namespace. В prompt
unit показывается один раз с representative ID и списком exact aliases; после
парсинга T1.7 механически раскрывает любое упоминание representative во все raw
IDs до вызова `reconcile()`. Evidence не уничтожается и в persistence остаётся
по исходным immutable observations. Members не являются отдельными входными
единицами для reconciler'а, поэтому pre-grouping не добавляет отдельной
проверки. Восьмая проверка относится к identity: `new` обязана дать непустой
title, а три исхода существующего ID title не принимают. Разные units
автоматически не объединяются: semantic grouping остаётся явным предложением
агента.

## 9. Критерии приёмки

- **AC-1.** При одинаковых immutable inputs в любом порядке, когда функции
  T1.5 вызываются повторно, тогда получаются равные keys, units, issues и
  decisions; время, БД, env и I/O не читаются.
- **AC-2.** Когда две линии возвращают наблюдения с одинаковыми шестью полями
  после NFC/newline canonicalization в одном round, тогда они образуют одну
  exact unit и одну semantic identity; когда отличается хотя бы case, пробел,
  body, file, range или severity либо меняется round, автоматической склейки
  нет.
- **AC-3.** Когда валидный proposal содержит все четыре outcome,
  `reaffirmed_closed` ссылается на закрытый через `accepted_reason` finding, а
  `reopen_closed` — на закрытый через `verified_fixed`/`policy_closed`, тогда
  каждый raw observation текущего T1.5 input получает ровно один link:
  `new→first_seen`,
  `existing_open→recurrence`, `reaffirmed_closed→reaffirmation`,
  `reopen_closed→reopening`; new group создаёт одну identity intent.
- **AC-4.** Для каждой из восьми строк `agent-contracts.md` §4, включая оба
  подслучая строки 5, когда построен минимальный нарушающий proposal, тогда весь
  вызов завершается
  `ReconciliationContractError` с точным code, group/ID context и сообщением,
  достаточным для исправления полного ответа; intents/outcome отсутствуют.
- **AC-5.** Когда proposal ссылается на finding, тогда `existing_open`
  принимается только для open ID scoped ledger, `reopen_closed` — для любого
  closed ID scoped ledger, а `reaffirmed_closed` — только если его
  `last_resolution=accepted_reason`; неизвестный, out-of-scope,
  status-mismatched или resolution-mismatched ID не принимается. После
  `verified_fixed`, `policy_closed` и `human_decision` тот же finding требует
  `reopen_closed`; действительно другая или неуверенно связанная проблема может
  быть `new`.
- **AC-6.** Когда `new`-группа объединяет observations нескольких линий, тогда
  её непустой ground-truth title сохраняется из proposal, first observation
  выбирается детерминированно, owner lane имеет минимальный индекс, а конкретный
  `F-*` в pure domain ещё не существует. Несколько groups одного
  existing/reopened ID дают один round intent с минимальным lane index по их
  общему набору и не могут передать новый title.
- **AC-7.** Когда одна или несколько `reopen_closed` groups указывают на один
  finding с `resolution_authority=human`, тогда результат — один
  `HumanReopenRequest` с их observation IDs/reasons, исходным human-решением и
  severity snapshot; pending observations не получают link, round outcome
  отсутствует.
- **AC-8.** Когда все human-reopen requests получили ответы, тогда `reopen`
  даёт `reopening` и работу автору, `keep_closed` — `reaffirmation` без работы;
  частичный, повторный или чужой ответ не завершает reconciliation.
- **AC-9.** Когда observation нет либо после полного reconciliation остаются
  только `reaffirmation`, тогда исход первичного круга `clean`; присутствие
  хотя бы одной `first_seen`, `recurrence` или `reopening` даёт
  `needs_revision`.
- **AC-10.** Когда исчерпан `contract_retry_budget` reconciliation, тогда
  `build_reconcile_failed_question()` возвращает `reason=reconcile_failed` и
  byte-preserving domain payload всех raw observations этого T1.5 input,
  scoped ledger и
  последних issues; новых identities, links и fallback outcome нет.
- **AC-11.** Контракт production invocation требует отдельную роль
  `reconciler`, свежую session, `explicit` context и exposure; T1.5 не пытается
  продолжить сессию одной из blind lines и не выбирает runtime profile.
- **AC-12.** После реализации полный `./scripts/check.sh` зелёный, dependency
  set не изменён, а implementation diff ограничен тремя модулями T1.5 и тремя
  test-модулями.
- **AC-13.** Когда `new_observations` последнего `fix_check` проходит
  reconciliation с outcome `new`, тогда T1.5 создаёт identity intent с
  `first_round_id=current_round_id` и возвращает её в `FixCheckContribution`
  без `round_result`; T1.7b обязан добавить finding в `CheckFacts.open_findings`
  до T1.4, поэтому `cap_exhausted_new` достижим без сброса cap. Follow-up
  `decisions[*].observation` с известным target в этот input не попадает.

## 12. Допущения и открытые вопросы

**Допущения:**

- T1.3 реализует scoped ledger как данные, а не решает outcome; если repository
  начнёт автоматически фильтровать outcome или назначать identities, граница
  T1.3/T1.5 возвращается на совместное ревью.
- `severity` для fingerprint передаётся уже в persisted effective form; правила
  получения `severity_effective` и периоды принадлежат T1.6/DDL, T1.5 не
  пересчитывает шкалу.
- Canonicalization алгоритма dedup — локальная деталь реализации безопасного
  prefilter: он не является finding identity и никогда не используется между
  rounds/campaigns. Любое расширение нормализации требует новых collision-
  тестов и ревью этой границы.
- Closed ledger содержит контекст исходного human resolution и severity
  snapshot из связанного question/answer. T1.5 не восстанавливает их из
  текущего severity view, потому что оно описывает уже другое время.
- По явному решению владельца Q44 `new` означает другую или неуверенно
  связанную проблему. Для распознанного того же finding `reaffirmed_closed`
  допустим только после `accepted_reason`; после `verified_fixed`,
  `policy_closed` и `human_decision` используется `reopen_closed`.
- По явному решению владельца Q45 follow-up observation внутри решения по
  известному finding не входит в T1.5. Его `unchanged_from` проверяет T1.6, а
  T1.7b атомарно пишет observation + direct `recurrence` + решение; полный
  unlinked query остаётся гейтом всего round. Этот путь допустим только при
  `still_present`/`insists`; сочетание с `verified_fixed`/`accepted_reason`
  T1.7 отклоняет до записи.
- Для context `fix_check_new` scoped ledger снят после применения всех валидных
  решений текущего check. Finding, закрытый этим check, уже находится в closed
  set; попытка сослаться на него как `existing_open` даёт обычный `FAIL-4`.
- Если human-reopen groups несколько, текущая ветка ждёт ответы на все;
  `resolve_human_reopens()` принимает полный набор один раз. T1.7b может
  сохранить безопасные non-human intents рядом с вопросами, но не пишет
  `review_round.result` и не запускает автора до полного покрытия.
- Ошибки всех независимых groups агрегируются в стабильном порядке, чтобы
  retry-agent получил один полный список, но противоречивый input snapshot
