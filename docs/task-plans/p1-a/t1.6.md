## 2. Цель и наблюдаемый результат

**Цель.** Реализовать чистый severity-домен, который без SQLite и процессов
агентов разрешает `unchanged_from`, воспроизводит правила периода накопления,
сравнивает споры с порогом и не теряет ни один одновременно эскалируемый
finding.

У finding две разные оси. `finding_status` отвечает, открыт ли он для работы, а
severity-период отвечает, какие observations участвуют в пороге. Поэтому
`accepted_reason` и `policy_closed` закрывают finding, но сохраняют прежний
период; `verified_fixed` и `human_decision` закрывают обе оси. T1.6 выражает
именно эту разницу и служит независимым oracle для SQL views T1.3/T1.7b.

**Наблюдаемый результат.** Для immutable facts одного finding функции T1.6
детерминированно возвращают `severity_effective`, начало текущего периода,
`escalation_severity`, `historical_max`, эффекты resolution и разбиение всех
`insists` текущего check на `policy_closed` и полный список human escalation.
При нескольких спорах не ниже порога результат содержит их все в стабильном
порядке severity по убыванию, затем finding ID; T1.4 получает один aggregate и
создаёт один human gate по Q46.

## 3. Границы

**Входит:**

- закрытая шкала `low < medium < high < critical`, точное сравнение и запрет
  coercion/default для неизвестного значения;
- разрешение `severity_suggested`/`unchanged_from` при вставке observation:
  ссылка назад, тот же campaign, finding и текущий период, наследование точного
  `severity_effective`;
- индуктивная проверка многошаговой цепочки: каждый новый узел наследует уже
  проверенный immutable `severity_effective` непосредственного родителя;
- pure-проекция `SeverityFacts → SeveritySnapshot`, повторяющая границы
  `finding_period` и семантику `finding_severity` без импорта SQL/store;
- четыре resolution effect: authority и закрывает ли resolution severity-
  период;
- человеческий override как явная граница периода без закрытия: прежние
  observations отсекаются для escalation, последующие снова поднимают максимум,
  а `historical_max` не меняется от самого override;
- сравнение `insists` с campaign snapshot `severity_threshold` через `>=`;
- один `DisputePolicyResult`: все споры ниже порога превращаются в
  `PolicyClosureIntent`, все не ниже порога входят в полный
  `EscalationBatch` по Q46;
- табличные unit-тесты всех последовательностей `db-schema.md` §5.6,
  multi-hop `unchanged_from`, resolution map, границ порога и нескольких
  одновременных disputes.

**Не входит:**

- Pydantic/JSON-схемы, проверка допустимости follow-up только при
  `still_present`/`insists` и transport error rendering — `T1.7`;
- SQL views, repositories, migration и проверка constraint/trigger —
  `T1.2`/`T1.3`; T1.6 не импортирует их DTO;
- identity, reconciliation и выбор human/regular пути для `reopen_closed` —
  `T1.5`, который получает уже вычисленный `resolution_authority`;
- cap, campaign transition и создание `AskHuman` — `T1.4`; T1.6 только
  формирует полный policy result, T1.7b отображает его в типы T1.4;
- выделение event/observation IDs, запись observation/link/resolution/override,
  атомарность round result и вопроса — `T1.7b`/`T1.16`;
- выбор порога из живого конфига: T1.6 принимает snapshot порога и версии
  политики, сохранённый на campaign;
- CLI-рендер трёх величин и текста агрегированного вопроса — `T1.19`/`T1.16`;
- автоматическое понижение severity, fuzzy-normalization enum и изменение
  защищённого findings-контракта.

Follow-up observation Q45 проходит три последовательных гейта: T1.7 допускает
его только при `still_present`/`insists`, T1.6 проверяет семантику
`unchanged_from`, T1.7b одной транзакцией пишет observation + `recurrence` +
решение. Ошибка T1.6 возникает до первого persistence intent и становится
`contract_error` всей попытки.

## 9. Критерии приёмки

- **AC-1.** При одинаковых immutable inputs в любом порядке, когда функции T1.6
  вызываются повторно, тогда результаты и ошибки равны; БД, env, время и I/O не
  читаются.
- **AC-2.** Для каждой пары severity/threshold из четырёх значений, когда
  выполняется сравнение, тогда эскалация истинна ровно при rank severity
  `>=` rank threshold; неизвестная строка отклоняется без default/coercion.
- **AC-3.** Когда observation несёт suggested severity, effective совпадает с
  ней; когда валидная цепочка из двух и более unchanged nodes ссылается назад,
  каждый узел получает effective исходного явного observation.
- **AC-4.** Для missing/forward parent, другой campaign/finding или периода и
  закрытого target period, когда разрешается `unchanged_from`, тогда весь вызов
  даёт точный `SeverityChainError`; persistence intent отсутствует.
- **AC-5.** Для каждой последовательности таблицы `db-schema.md` §5.6, когда
  строится snapshot, тогда `period_start_event_id` и `escalation_severity`
  совпадают с таблицей: accepted/policy closure сохраняют период, verified/human
  closure завершают его, reopen начинает либо продолжает нужный период.
- **AC-6.** Когда finding имеет observations с `first_seen`,
  `recurrence`/`reopening` и `reaffirmation` в разных периодах, тогда
  `severity_suggested` остаётся на каждой исходной записи, escalation берётся
  только из разрешённых links текущего периода, а historical max — из всех
  linked observations за жизнь ID.
- **AC-7.** Когда human override понижает `critical→medium`, затем приходят low
  и high observations, тогда escalation последовательно `medium→medium→high`,
  historical max остаётся `critical`, а override с неверным old/reason или
  второй override того же finding с тем же event ID отклоняется.
- **AC-8.** Для четырёх resolution kinds, когда вызывается
  `resolution_effect()`, тогда authority/closes-period совпадают с DDL 1:1;
  неизвестная или несовместимая комбинация не принимается.
- **AC-9.** При mixed наборе уникальных `insists`, когда часть severity ниже
  campaign threshold, а часть равна/выше, тогда каждый ID встречается ровно в
  одном результате: ниже — `PolicyClosureIntent`, остальные —
  `EscalationBatch`; threshold и policy version сохранены у каждого.
- **AC-10.** Когда два и более disputes достигли порога, тогда один aggregate
  содержит их все без дублей в порядке severity ↓, finding ID ↑; T1.4 boundary
  принимает весь список, а не один выбранный item.
- **AC-11.** Когда `SeverityFacts` имеет структурное противоречие, тогда
  snapshot не строится и возвращается один из кодов `SeverityFactsError`, а не
  частично вычисленные nullable значения.
- **AC-12.** После реализации полный `./scripts/check.sh` зелёный, dependency
  set не изменён, а implementation diff ограничен двумя модулями T1.6 и тремя
  test-модулями.

## 11. Риски и откат

| Риск | Ранний сигнал | Что делать | Граница отката |
|---|---|---|---|
| Pure oracle повторит ошибку SQL вместо правила | T1.6 и view одинаково используют `MAX(open)` либо не отсекают pre-override observations | Строить tests сначала из текстовой таблицы §5.6, затем независимо сверять pure и SQLite в T1.7b | Откатываются `severity.py`/tests; DDL и repositories не меняются |
| `finding_status` подменит severity period | `accepted_reason` даёт `period_start=NULL` только потому, что status closed | Передавать opening/closing event sets отдельно; status использовать лишь на границе допустимого direct follow-up | Меняется mapper/facts, resolution semantics сохраняется |
| Stored `severity_effective` станет непроверяемым третьим входом | Caller передаёт effective, не равный suggested/parent, а T1.6 его принимает | Effective всегда возвращает resolver; T1.7b не принимает его от агента и пишет вычисленное значение | Откатывается observation builder до resolver API; schema не меняется |
| Override понижает навсегда | После `critical→medium` новое `high` остаётся medium | Cutoff включает override и только observations после него; max после cutoff проверяется отдельной последовательностью | Исправляется pure projection/view mapping, persisted immutable facts остаются |
| Historical max начнёт учитывать override или только текущий период | Human downgrade переписывает историю либо verified closure обнуляет CLI diagnosis | Считать historical только по всем linked observations без period/override filters | Исправляется projection helper; storage не меняется |
| Несколько disputes снова сокращаются до одного | `evaluate_disputes()` возвращает optional item либо T1.4 test видит только первый ID | Exhaustive ID partition и equality множества input/output; один nonempty aggregate по Q46 | Откатывается policy mapper; campaign/question DDL не меняется |
| T1.6 и T1.5 начнут по-разному маршрутизировать human reopen | В T1.6 появляется `AwaitHumanReopen` либо в T1.5 дублируется resolution map | T1.6 выводит authority/closes-period, T1.5 единолично превращает `human` в pending human action | Удаляется лишний route helper; публичные severity values сохраняются |
| Sibling-задачи конфликтуют за package exports | Diff T1.6 меняет `review/__init__.py` или импортирует model T1.4 | Импортировать локальные модули напрямую до package boundary review; exports объединить после merge | Откатывается только shared export/import, sibling API остаются независимы |

## 12. Допущения и открытые вопросы

**Допущения:**

- T1.3 сохранит точные event IDs и nullable projections без policy defaults.
  Если repository начнёт скрывать `period_start_event_id=NULL` или вычислять
  resolution effect, T1.3/T1.6 возвращаются на совместное ревью.
- `severity_effective` предыдущего observation уже защищён immutable row и
  trigger T1.2/T1.3. T1.6 проверяет новый edge индуктивно по непосредственному
  parent, а не перечитывает всю цепочку при каждом follow-up.
- Несколько facts одной транзакции могут разделять один `run_event.id`; pure
  projection работает как SQL над множествами и не вводит искусственного
  порядка между ними. Исключение — два overrides одного finding с одинаковым
  event ID: у них нет определимого «последнего» значения, поэтому snapshot
  отклоняется как повреждённый.
- T1.7 проверяет сочетание follow-up только со `still_present`/`insists` до
  вызова T1.6. T1.6 всё равно отклоняет closed/mismatched period, чтобы
  семантическая граница не держалась одной Pydantic-схемой.
- По явному решению владельца Q46 все simultaneous disputes не ниже порога
  входят в один aggregate и один human gate; ответ относится ко всей кампании.
- Общий implementation baseline P1-A будет зафиксирован после индивидуального
  и совместного ревью всех восьми планов. Для T1.6 левой границей реализации
  служит closing commit принятой T1.3; T1.4 и T1.5 — parallel siblings.

**Открытые вопросы:** нет. Q46 закрыт явным ответом владельца и отражён в
требованиях, дизайне, плане T1.4 и этом плане.
