## 2. Цель и наблюдаемый результат

**Цель.** Дать review-core типизированную persistence-границу поверх store из
T1.2 и исполнением доказать те инварианты схемы, которые заявлены как
гарантии SQLite, прежде чем на них ляжет доменная логика.

**Наблюдаемый результат.** Через конкретные репозитории можно внутри одной
транзакции собрать минимальный прогон, кампанию, круг, наблюдения, findings и
вопрос человеку, а затем через read boundary получить неизменяемые проекции
счётчиков, статуса, периода, severity и состояния прогона. Параметризованные
негативные тесты физически пытаются нарушить шесть constraint-гарантий с
пометкой **База**, базовую часть восьми constraint-инвариантов **База + код** из
`db-schema.md` §10 и каждый FK закрытого enum; ожидаемые нарушения отвергаются
самой базой. Оставшиеся две гарантии **База** доказываются отсутствием хранимых
колонок и семантикой представлений; смешанный инвариант №22 — представлением и
recovery-запросами согласованности blocker/state.

## 3. Границы

**Входит:**

- concrete repositories для агрегатов `run`, `attempt`, `campaign`, `finding`
  и `question`; они принимают только scoped `ReadSession`/`Transaction` из
  T1.2, не открывают соединение и не управляют транзакцией;
- immutable input/row/projection types для публичной границы репозиториев;
- именованные write-примитивы для таблиц review-core и read-примитивы для
  `campaign_counters`, `finding_status`, `finding_period`, `finding_severity` и
  `run_state`; `finding_last_override` остаётся внутренним вспомогательным
  представлением `finding_severity`;
- запросы полноты множества, уже зафиксированные схемой: наблюдения круга без
  связи, открытые findings кампании без строки участия в текущем круге,
  незавершённые `finding_round(entry_kind=issued)` и рассогласованные
  branch-scoped blockers/физические состояния веток; отдельный typed read
  возвращает множество finding IDs, уже представленных в current round;
- автоматические негативные тесты шести constraint-гарантий **База** и
  физической половины восьми constraint-гарантий **База + код** из
  `db-schema.md` §10; гарантии №4, №9 и №22 проверяются отдельно структурой,
  результатами views и recovery-запросами;
- параметризованный manifest всех 37 child-колонок, ссылающихся на 27 закрытых
  справочников, и попытка записать неизвестное значение в каждую такую колонку;
- семантические тесты SQL-проекций: счётчики, `finding_status`, границы периода,
  human override severity и приоритеты `run_state`;
- тестовые builders минимального связного набора строк; прямой SQL в них и в
  негативных schema-тестах допустим только как средство попытаться обойти
  production repositories.

**Не входит:**

- решения «продолжать или остановить», кап и переходы кампании — `T1.4`;
- reconciliation, выдача публичной личности, вычисление `dedup_key` и семь
  контрактных проверок — `T1.5`;
- разрешение цепочки `unchanged_from`, выбор порога, семантика resolution и
  полная таблица границ severity — `T1.6`; human-reopen маршрутизирует T1.5,
  а T1.3 проверяет SQL-проекции на
  несущих примерах, но не дублирует доменный алгоритм;
- Pydantic-контракты ответов агентов — `T1.7`, сквозные атомарные операции
  review-протокола с событиями — `T1.7b`;
- запуск/завершение процессов и recovery попыток — `T1.9`/`T1.10a`;
- бизнес-операции вопроса/ответа, outbox и `awaiting_continue` — `T1.16`;
  `QuestionRepository` здесь предоставляет только persistence-примитивы;
- `task_graph` repository, проверка циклов и атомарный импорт: согласно графу
  работ это фаза 2, хотя DDL и её базовые ограничения уже проверяются здесь;
- repositories артефактов, verification и Telegram — `T1.13`, `T1.14` и
  `T1.15`; таблицы проверяются schema-тестами, но публичного API пока не имеют;
- generic repository, ORM, `Protocol`, unit-of-work поверх `Database`, cache и
  отдельное read-соединение;
- изменение DDL `0001_initial.sql`: расхождение с design сначала возвращает
  `db-schema.md`, T1.2 и этот план на ревью.

Repository write-примитивы намеренно не запускают собственную транзакцию и не
вызывают `append_run_event()` автоматически. Потребитель компонует несколько
репозиториев и событие внутри одного callback `Database.transaction()`.
Колонки `event_id`, присутствующие в DDL, обязательны во входном типе; полноту
семантических пар «переход + событие» доказывает T1.7b. Иначе T1.3 либо разорвёт
атомарный workflow на несколько транзакций, либо начнёт принимать доменные
решения, которыми владеют T1.4–T1.6.

| `read_finding_round_history()` | `T1.3` | `read_finding_round_history(campaign_id: int, finding_ids: tuple[int, ...]) -> tuple[FindingRoundHistoryEntry, ...]`. Это история **участия в кругах**, а не жизненный цикл finding'а, и имя это отражает: метод открытость не проверяет и проверять не должен. **Контракт API:** `finding_ids` — authoritative набор caller'а; repository его не выводит и не фильтрует по текущему статусу, поэтому история закрытого finding'а возвращается наравне с остальными. **Обязательство потребителя:** T1.7b передаёт сюда ровно `CheckFacts.open_findings` той же транзакции — выводить «открытые» вторым запросом нельзя, иначе снимок опишет не тот набор, по которому принято решение. Две разные вещи: repository отвечает за отсутствие скрытого фильтра, T1.7b — за то, какой набор он подаёт. Запись — `finding_id`, `finding_public_id`, `round_id`, `round_no`, `round_kind`, `entry_kind`, `disposition`, `reviewer_decision`, `decided_at`. Scope — **одна кампания**: cap и счётчики кампанийные, и строки одноимённого finding из другой кампании прогона объяснили бы cap, которого нет. Входят обе разновидности строк `finding_round` — `issued` и `post_check`; у `post_check` три ответных поля пусты по DDL, и это не пробел, а факт «появился после проверки». Закрытие и переоткрытие внутри кругов видно по `reviewer_decision` соседних строк, но `finding_resolution` в проекцию не входит: закрытия вне круга (policy closure, решение человека) объясняют статус, а не cap, и для них есть `finding_status`/`finding_period`. Свободный `disposition_reason` не входит: snapshot — ограниченное воспроизводимое объяснение (`db-schema.md` §14 п.15), а текст остаётся durable в `finding_round`. | `QuestionRepository` | `T1.3` | Persistence question/answer/outbox/blocker; `create_question()` атомарно выделяет `N`/`Q-N`; scope/reason/presentation/snapshot вопроса immutable, принятый `human_answer` append-only; lifecycle-поля вопроса меняются отдельными точечными методами; не объединяет примитивы в бизнес-переход и не отправляет сообщение | `T1.7b`, `T1.16` | [`db-schema.md` §6.2, §7, §11 и §14 п.20](../../design/db-schema.md) |
| Immutable records | `T1.3` | Frozen dataclasses `New*`/`*Record` повторяют имена и optionality колонок DDL; внутренние IDs — `int`, публичные — `str`, время — epoch ms `int`; произвольный `Mapping` не является публичным input API | Все пять repositories | [`db-schema.md` §1.2–§1.4](../../design/db-schema.md); этот план |

| Mutation result semantics | `T1.3` | `get_*` возвращает `None`; write/update, для которого ID обязан существовать, выдаёт `RepositoryRecordNotFound(entity, id)`. Репозитории возвращают только frozen records/projections, scalar IDs либо
неизменяемые последовательности; `sqlite3.Row`, cursor и SQL-строка публичную
границу `repo` не пересекают. Закрытые значения возвращаются точным текстом из
БД без coercion и default; их Python-enum/Pydantic-представление принадлежит
T1.7. Методы не переводят constraint failure в доменные решения: неизвестный
enum, несовместимый disposition и дубликат — это наблюдаемый
`sqlite3.IntegrityError`, после которого T1.2 откатывает весь callback.

## 9. Критерии приёмки

- **AC-1.** При готовой базе version 1, когда минимальный review aggregate
  создаётся и читается через repositories внутри callback T1.2, тогда все
  методы возвращают frozen records/IDs/projections, raw row/cursor/connection
  наружу не выходит, а repository не выполняет собственный transaction control.
- **AC-2.** Для каждого из шести constraint-инвариантов **База** и базовой части
  каждого из восьми constraint-инвариантов **База + код**, когда отдельная transaction fixture пытается
  записать нарушение, тогда SQLite отвергает его, вся fixture mutation
  откатывается, а следующая штатная repository-операция проходит. Две остальные
  гарантии **База** покрыты `AC-4`–`AC-5` структурой и семантикой views. Для
  design-инварианта №1 отдельно отвергаются `post_check` с любым ответом,
  disposition без author attempt и reviewer decision без attempt/`decided_at`;
  для №30 отдельно отвергаются обе пары: активное состояние с
  непустым `closed_at` и терминальное состояние с `closed_at = NULL`.
- **AC-3.** При introspection всех 37 FK child-колонок на 27 закрытых
  lookup-таблиц, когда
  фактический набор `(child_table, child_column, lookup_table)` сравнивается с
  test manifest и затем в каждую child-колонку подставляется неизвестное
  значение, тогда наборы равны и каждая вставка отвергается FK.
- **AC-4.** При discovery-круге, одной succeeded author revision и закрытых
  review rounds, когда читается `campaign_counters`, тогда revision/check
  counters меняются независимо, discovery входит в число проверок, а в
  `review_campaign` отсутствуют хранимые копии счётчиков.
- **AC-5.** При последовательностях из `db-schema.md` §5.6, когда читаются
  `finding_status`, `finding_period` и `finding_severity`, тогда
  `accepted_reason` закрывает finding, но не период; reopen после него сохраняет
  прежний start, reopen после `verified_fixed` начинает новый период; human
  override отсекает прежний максимум, а последующее более высокое наблюдение
  снова повышает `escalation_severity`. Второй override одной пары
  `(finding_id, event_id)` отвергается; override другого finding в том же
  событии и новый override того же finding в другом событии оба разрешены и не
  раздваивают `finding_last_override`/`finding_severity`.
- **AC-6.** При run с комбинациями terminal, cancel/pause request, активной
  веткой и blocker, когда читается `run_state`, тогда выполняется точный
  приоритет `terminal → cancelling → paused → running → waiting_human → idle`,
  а физической `run.state` в таблице нет.
- **AC-7.** При попытке `UPDATE`, `DELETE` и `INSERT OR REPLACE` по
  конфликтующему ключу каждой из `review_lane`, `lane_waiver`,
  `review_observation`, `finding_observation_link`, `finding_resolution`,
  `reviewer_exposure`, `run_profile_resolution`,
  `human_question_observation` и `human_answer`, когда transaction исполняется,
  тогда соответствующий trigger отвергает изменение, исходная строка
  сохраняется и вызывающий видит `sqlite3.IntegrityError`. Для `run_event` ту же
  тройку отдельно доказывает `T1.2 AC-9`.
- **AC-8.** При чтении отсутствующего ID repository возвращает `None`; при
  обязательном update отсутствующего ID callback получает
  `RepositoryRecordNotFound` и откатывается; nullable view-поля остаются
  `None` без synthetic default.
- **AC-9.** При незавершённом reconciliation запросы Campaign/Finding repository
  возвращают точные ID всех observations без link, открытых findings кампании
  без строки current round и `issued` без той же успешной author revision/
  решения owner; typed current-round read возвращает обе разновидности строк,
  а законный `post_check` не попадает в strict-issued результат. Blocker/state
  queries отдельно находят branch-scoped
  вопрос при `running`, `blocked` без причины и открытый вопрос без matching
  blocker; после заполнения множеств все запросы пусты.
- **AC-10.** После реализации `./scripts/check.sh` завершается кодом 0 без
  изменения dependency set и без новых файлов вне `src/metaswarm/store/repo`
  и `tests/store`, кроме узкого export в `store/__init__.py`.
- **AC-12.** При кампании из четырёх кругов с тремя findings — первый прошёл
  `issued` всеми тремя `fix_check`; второй закрыт `verified_fixed` на третьем и
  переоткрыт строкой `post_check` на четвёртом; третий закрыт `verified_fixed`
  на втором и **остаётся закрытым**, — когда `read_finding_round_history()`
  вызывается с набором из всех трёх, тогда возвращаются строки всех трёх,
  включая закрытый: фильтрации по статусу в методе нет, набор задаёт caller.
  Закрытый finding здесь законен именно потому, что проверяется API, а не
  production-вызов: привязка к `CheckFacts.open_findings` — обязательство T1.7b,
  и доказывает его `AC-8b` того плана.
  Дальше — обе разновидности `entry_kind`, с
  `disposition`/`reviewer_decision`/`decided_at` там, где они есть, и пустыми у
  `post_check`; круг закрытия виден по `reviewer_decision`, а строка
  `finding_resolution` в выдачу не попадает; порядок равен `finding_id ASC,
  round_no ASC` при любом порядке аргумента; строки того же finding из соседней
  кампании прогона не попадают; `disposition_reason` в записи отсутствует.
- **AC-11.** Когда repositories создают observation, finding и question внутри
  transaction, тогда они сразу возвращают окончательные public IDs
  `O-<campaign>-<seq>`, `F-N` и `Q-N`; rollback не оставляет строку/публичную
  identity, а после commit и удаления следующий INTEGER allocator не
  переиспользует `N`.
- **AC-13.** При active attempt, когда `complete_attempt()` получает полный
  `AttemptCompletion`, тогда один CAS сохраняет terminal payload, input/scope
  остаются побайтно прежними и повторный CAS — с тем же либо другим payload —
  даёт `RepositoryAlreadyTerminal` с сохранённым outcome. Для отсутствующего ID
  получается `RepositoryRecordNotFound`. Прямые terminal INSERT, дозапись
  result до завершения, изменение каждого identity/scope/input-поля до и после
  завершения, возврат outcome в NULL, переписывание terminal payload, DELETE и
  замена terminal-строки active-строкой через `INSERT OR REPLACE` отвергаются
  триггерами; `interrupted` законно сохраняется с nullable
  диагностическими полями, но непустым `finished_at`.
- **AC-14.** При open round, когда `close_round()` получает result/closed_at,
  тогда один CAS закрывает его без изменения identity/input. Идентичный или
  другой повтор даёт `RepositoryAlreadyTerminal`, отсутствующий ID —
  `RepositoryRecordNotFound`; terminal INSERT, input UPDATE, повторная смена
  результата, возврат пары в NULL, DELETE и переоткрытие через
  `INSERT OR REPLACE` отвергаются триггерами.
- **AC-15.** При сохранённом вопросе и принятом ответе, когда вызывающий меняет
  scope/reason/text/options/snapshot вопроса, обновляет или удаляет ответ либо
  выполняет `INSERT OR REPLACE` по ID/`question_id`, тогда база отвергает
  операцию; `answered_at` и `reask_count` вопроса остаются разрешёнными
  lifecycle-полями, а исходные показанные/принятые данные не меняются.
- **AC-16.** При `finding_round(entry_kind=issued)` без reviewer decision, когда
  owner записывает согласованную тройку decision/attempt/time, тогда UPDATE
  проходит ровно один раз. Decision на INSERT, изменение input/author-полей,
  частичная тройка, повтор, DELETE и `INSERT OR REPLACE` отвергаются; история
  `read_finding_round_history()` остаётся прежней.

## 11. Риски и откат

| Риск | Ранний сигнал | Что делать | Граница отката |
|---|---|---|---|
| Repository превратится в второй доменный слой и начнёт решать cap/reopen/severity | Метод принимает policy threshold, выбирает link type или сам меняет campaign state | Оставить только persistence и именованные completeness queries; решение вернуть владельцу T1.4–T1.6 и повторить ревью границ P1-A | Откатываются только `store/repo` и его тесты; DDL T1.2 не меняется |
| Row-level API позволит потребителю забыть событие | Workflow меняет состояние без `append_run_event` в том же callback | В T1.7b дать именованные атомарные операции и интеграционные тесты; не лечить это скрытым commit внутри repository | До T1.7b API можно сузить без migration; после совместного ревью изменение публичной границы возвращает затронутые планы |

## 12. Допущения и открытые вопросы

**Допущения:**

- T1.2 будет реализована без изменения её scoped API и модели ошибок. Если
  `ReadSession`/`Transaction` или migration inventory меняются, T1.3
  возвращается на ревью до реализации.
- Все production mutations review-core выполняются через repositories; прямой
  SQL допустим в migration runner и негативных schema-тестах, потому что их
  назначение — проверить обход repository boundary.
- Frozen dataclasses достаточно для v1: сериализация наружу и Pydantic-модели
  принадлежат T1.7/CLI, поэтому persistence layer не получает runtime-
  зависимостей.
- Тесты SQL-проекций создают факты явно и не принимают доменных решений. Полная
  проверка таблицы переходов, reconciliation и severity остаётся за
  T1.4–T1.7b.
- Общий implementation baseline P1-A будет зафиксирован после индивидуального
  и совместного ревью всех восьми планов; SHA паспорта остаётся свидетельством
  версии design, по которой написан именно этот план. Для проверки фактического
  scope T1.3 используется более поздняя левая граница — точный closing commit
  принятой реализации T1.2, записанный до первой правки T1.3.

**Открытые вопросы:** нет.
