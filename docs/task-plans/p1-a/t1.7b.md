## 2. Цель и наблюдаемый результат

**Цель.** Соединить store, строгие agent-contracts и чистые домены T1.4–T1.6
одним тонким application-layer workflow и на настоящем SQLite доказать
достижимость review-протокола до `cap_exhausted_new` без запуска CLI-агентов.

**Наблюдаемый результат.** Из marked JSON-фикстур создаётся реальная review-
кампания: primary discovery выдаёт findings; три успешные авторские ревизии
получают три `fix_check`; `insists` с follow-up observation и
`unchanged_from` атомарно создаёт direct `recurrence`; новый observation
последней проверки проходит повторный reconciliation и получает новую identity
с `first_round_id` последнего круга. После четвёртой проверки база содержит
вопрос `cap_exhausted_new`, branch физически `blocked`, Run —
`waiting_human`, а счётчики, status и severity читаются штатными SQL-
представлениями. Ни одного subprocess, vendor CLI, сети или fake adapter в
сценарии нет.

## 3. Границы

**Входит:**

- application service, который отображает `ValidatedAgentResult` T1.7 в
  immutable inputs T1.4–T1.6 и компонует repositories T1.3 внутри
  `Database.transaction()` T1.2;
- запись validated blind/new observations с окончательными
  `O-<campaign>-<seq>` и domain `dedup_key`;
- primary и fix-check-new reconciliation: identity/link/resolution intents,
  атомарные `F-N` и только отсутствующие
  `finding_round(entry_kind=post_check)`;
- атомарная запись успешной author revision, нового `fix_check` и точного
  roster строк `entry_kind=issued` с dispositions;
- запись owner decisions; direct follow-up при
  `still_present`/`insists` после повторной проверки T1.6 пишется вместе с
  observation, `recurrence` и решением;
- вычисление policy closures/escalation через T1.6, сбор `CheckFacts` из
  актуальных SQL-проекций и единственный вызов `decide_after_check()` T1.4;
- три глобальных гейта перед `review_round.result`: ни одного observation без
  link, ни одного открытого finding кампании без строки участия в текущем
  круге и ни одного незавершённого/неверно привязанного `issued`; законный
  `post_check` текущий круг не блокирует;
- branch-scoped human gate: round result, question `Q-N`, CLI outbox, blocker
  с `branch_id/question_id`, `branch.state=blocked` и событие одной
  транзакцией;
- каноничный default-cap сценарий: discovery/check 1, три author revisions,
  fix-checks 2–4, после чего `review_check_count=4` и
  `author_revision_count=3`;
- интеграционные отказы и fault injection, доказывающие отсутствие частичных
  decisions/observations/links/resolutions/events.

**Не входит:**

- запуск, resume, timeout и убийство процесса агента — T1.8/T1.9;
- retries, бюджеты, выбор профиля и фактический orchestration попыток —
  T1.18;
- scheduler и автоматический выбор следующей стадии — T1.18; T1.7b вызывает
  application operations явно в тесте;
- production prompt assembly — T1.20; входом служат нормативные marked
  fixtures тех же восьми схем;
- production-формулирование human question и интерпретация ответа — T1.16.
  T1.7b определяет frozen `PreparedHumanGate` и чистый синхронный
  `HumanGateFormatter`-порт; formatter вызывается только с уже готовым
  `AskHuman`, T1.16 позднее даёт production-реализацию порта;
- отправка outbox, Telegram и `continue` — T1.15/T1.16/T1.19; тест проверяет
  durable CLI outbox и состояние до ответа;
- универсальный recovery repair — T1.10b. Здесь проверяются те же mismatch-
  запросы и атомарность, но рестарт сервиса не симулируется;
- все варианты review-протокола. Это один несущий вертикальный путь плюс
  узкие негативные швы, а полные unit-матрицы остаются у T1.2–T1.7;
- новый ORM, unit-of-work, event bus, generic workflow engine или
  `Protocol`-абстракции.

Primary fixture содержит два findings. Первый автор аргументированно отклоняет;
owner отвечает `insists` с follow-up observation ниже порога, поэтому T1.6
создаёт `policy_closed`, но сохраняет severity-период. Второй finding остаётся
открытым через проверки 2 и 3 и ведёт цикл к третьей правке. На check 4 owner
закрывает его как `verified_fixed` и одновременно возвращает действительно
новый observation. После reconciliation открыта только новая identity; поэтому
причина `cap_exhausted_new` доказывается без примеси `dispute` либо
`cap_exhausted_same`.

внутри той же TX непосредственно перед несущим решением: успешная validation
по прежнему snapshot не даёт права записать переход поверх изменившегося
ledger/round.

## 9. Критерии приёмки

- **AC-1.** Когда две валидные blind-line fixtures записываются в primary
  discovery, тогда observations получают последовательные
  `O-<campaign>-<seq>`, effective severity/dedup key совпадают с T1.5, а
  порядок строк детерминирован; reviewer attempt становится `succeeded` в той
  же транзакции, а до commit обе стороны отсутствуют. Созданный до spawn
  `reviewer_exposure` уже существует и эта операция его не меняет.
- **AC-2.** Когда валидный primary reconciliation классифицирует observations
  в две новые groups, тогда одной TX создаются две `F-N`, все links,
  `post_check`-строки с минимальными owners и событие; primary round получает
  `needs_revision` и campaign — `fix_cycle` только после пустых unlinked,
  missing-participation и strict-issued gates; reconciler attempt становится
  `succeeded` в той же TX.
- **AC-5b.** Когда `apply_reconciliation()` получает от T1.5 исход
  `reconcile_failed` либо `AwaitHumanReopen`, тогда вызывается соответствующая
  операция — `open_reconcile_failed_gate()` или `open_human_reopen_gate()`, — и
  одной TX с вопросом записываются все строки `human_question_observation`:
  для первой причины — полный набор сырых
  observations круга, для второй — точный pending-набор, каждая строка с
  target `finding_id`. Fault injection между вопросом и набором не оставляет ни
  одной из сторон; formatter в выборе состава не участвует (test spy), а
  попытка дописать строку после `human_answer` отвергается базой.
- **AC-3.** Когда succeeded author attempt возвращает exact dispositions всех
  открытых IDs, тогда одной TX создаются `author_revision`, следующий
  `fix_check(preceding_revision_id)` и exact `issued` roster с тем же
  `author_attempt_id`, а сама attempt становится `succeeded`; лишний/
  пропущенный ID ничего не пишет и не завершает attempt.
- **AC-4.** Когда owner отвечает `insists` и прикладывает follow-up с
  `unchanged_from` того же finding/периода, тогда decision, observation,
  effective severity, direct `recurrence`, event и `succeeded` reviewer
  attempt коммитятся вместе; T1.6 ниже порога создаёт `policy_closed` без
  закрытия severity-периода.
- **AC-5.** Для `verified_fixed` и `accepted_reason` с вложенным follow-up
  strict marked fixture отклоняется до workflow, а counts решений,
  observations, links, resolutions и events до/после byte-for-byte равны.
- **AC-6.** Когда check 4 содержит валидное closing decision старого finding и
  отдельный `new_observation`, тогда decision TX сохраняет observation с
  окончательным `O-*` без link, а следующая reconciliation TX через T1.5
  создаёт новую `F-N` с `first_round_id=current_round_id`, link и ровно одну
  `post_check`; уже представленный target второй строки/нового owner не
  получает. Между этими TX открытый круг восстановим, но закрыть его нельзя.
- **AC-7.** Перед result, когда unlinked и missing-participation queries пусты,
  а каждый `issued` связан с той же succeeded author revision и successful
  owner reviewer attempt, тогда законный `post_check` не блокирует close.
  Пропущенная строка участия, `issued` в discovery и каждый из пяти нарушенных
  fix-check issued-фактов отдельно возвращают `RoundClosureInvariantError` и
  оставляют result NULL.
- **AC-8.** Когда после check 4 открыта новая identity, author count равен 3,
  escalating disputes нет, тогда единственный T1.4-вызов возвращает
  `AskHuman(cap_exhausted_new)`, formatter-spy получает именно это action и
  context и возвращает envelope. Одной TX round получает `escalated`, campaign
  остаётся `fix_cycle`, создаются `Q-N`/CLI outbox/blocker, branch становится
  `blocked`, а Run — `waiting_human`; вызывающий reason не передаёт.
- **AC-9.** При том же human gate и второй независимой branch в
  `ready/running/retry_wait` target branch остаётся `blocked`, но
  `run_state` равен `running`; blocker содержит точные branch/question IDs.
- **AC-10.** После direct `insists → policy_closed` и финального
  `verified_fixed` SQL `finding_status`/`finding_period`/
  `finding_severity` на каждом checkpoint совпадают с независимыми ожидаемыми
  значениями T1.6, включая historical maximum и незакрытый policy period.
- **AC-11.** Полный сценарий заканчивается counters
  `author_revision_count=3`/`review_check_count=4`; discovery учтён как check
  1, failed/contract-error fixture не меняет ни один счётчик.
- **AC-12.** Для fault injection после каждого существенного write и для
  cancellation после принятия job текущая операция либо коммитится целиком,
  либо откатывается целиком; event без state и state без event не остаются.
- **AC-13.** Allocators создают только окончательные `O-*`/`F-*`/`Q-*`;
  rollback не оставляет строку/имя, а после удаления committed finding/question
  следующий INTEGER ID больше прежнего.
- **AC-14.** После реализации полный `./scripts/check.sh` зелёный, production
  diff ограничен application mapping/transactions и joint exports, а imports
  domain не направлены обратно в service/store/agents.

## 11. Риски и откат

| Риск | Ранний сигнал | Что делать | Граница отката |
|---|---|---|---|
| Application service превратится в второй domain | `review_transactions.py` самостоятельно выбирает reconciliation outcome, severity rank или cap branch | Оставить только explicit mapping/orchestration; каждое решение вызвать у T1.4–T1.6 и сопоставить result исчерпывающе | Откатывается service layer; pure domains/store сохраняются |
| Один большой transaction скроет промежуточные durable границы | Весь campaign выполняется одним callback, recovery не видит завершённых attempts/rounds | Держать пять именованных операций из §5; атомарность — внутри операции, не внутри всего сценария | Разделить application method до принятия API; DDL не меняется |
| Срез станет тестом собственной модели вместо SQL | Assertions берут expected severity/counters из тех же views или копируют SQL | Expected sequence строить из текстовых таблиц и pure T1.4–T1.6 до чтения БД; сравнивать каждый checkpoint | Меняются fixtures/assertions; production operations сохраняются |
| `insists` преждевременно остановит сценарий dispute или закроет единственную работу | Fixture severity достигла threshold либо primary содержит один finding | Держать первый finding ниже critical threshold и закрывать его policy; второй независимо ведёт цикл до check 4 | Меняется только нормативная fixture, правила policy/cap не ослабляются |
| New observation последнего check получит duplicate current-round row | T1.5 не получил current-round set либо repository UNIQUE падает после domain success | Snapshot строить в TX, intent создавать только для absent target; отдельный present-target test | Исправляется mapping/snapshot, identity/link не меняются |
| Human gate снова станет только декоративным blocker | Question/outbox есть, но branch остаётся running либо blocker без branch ID | Одна repository-composed TX и обязательные mismatch/run_state assertions до commit acceptance | Откатывается только human operation; campaign остаётся на последнем безопасном round |
| Caller либо formatter начнёт повторно решать reason | `finalize_fix_check()` принимает prepared question/expected reason или formatter получает raw facts вместо `AskHuman` | Constructor принимает pure formatter-port; method передаёт ему только фактический action после единственного T1.4-вызова, spy проверяет call count/value и отсутствие вызова для non-human path | Откатывается formatter adapter/API до порта §5; T1.4 и persistence остаются |
| Fault injection требует test-only hook в production API | Появляется публичный `fail_after_step` | Инъецировать исключение monkeypatch/wrapper concrete repository method; production signatures не расширять | Удаляются test wrappers, workflow API неизменен |
| Пять operations не укладываются в 2 дня | К концу первого дня primary discovery и один direct recurrence не проходят на SQLite | Не сокращать gates/rollback matrix; сузить production export до методов реального среза и вернуть оценку/граф на ревью до merge | T1.2–T1.7 остаются самостоятельным M1; неполный T1.7b не принимается |

## 12. Допущения и открытые вопросы

**Допущения:**

- После общего merge публичные имена T1.2–T1.7 совпадут с принятыми планами.
  Механическая смена имени отражается в этом плане; перенос authority или
  transaction boundary требует повторного совместного ревью P1-A.
- Test `HumanGateFormatter` строит `PreparedHumanGate` только из фактически
  переданного `AskHuman` и immutable context, записывает вызов для assertions и
  не содержит заранее ожидаемого reason. Production-формулировка,
  interpretation/reask и answer принадлежат T1.16.
- Event payloads содержат только IDs/snapshot, нужные для audit, и не являются
  вторым хранилищем status/counters/severity. Registry остаётся открытым и
  versioned.
- File-backed SQLite используется во всех integration tests; `:memory:`
  запрещён как основной witness из-за отличия `journal_mode`. Временный каталог
  создаёт pytest, а не production code.
- Общий implementation baseline P1-A фиксируется только после реализации и
  индивидуальной приёмки T1.2–T1.7. Design baseline этого плана остаётся
  точным SHA из паспорта.

**Открытые вопросы:** нет.
