## 2. Цель и наблюдаемый результат

**Цель.** Создать низкоуровневую SQLite-границу, через которую все последующие
модули безопасно читают состояние и атомарно записывают его вместе с событием,
не блокируя `asyncio`-петлю и не получая сырой доступ к соединению.

**Наблюдаемый результат.** Пустой временный файл открывается как база версии 1:
в нём целиком создана схема из `db-schema.md`, включены все пять PRAGMA, а
`foreign_key_check` чист. Конкурентные корутины выполняют транзакции
последовательно в одном writer-thread; ошибка откатывает транзакцию целиком,
запись через read API отвергается, а строки `run_event` нельзя изменить или
удалить.

## 3. Границы

**Входит:**

- одно `sqlite3.Connection`, которое создаётся, используется и закрывается в
  выделенном потоке с FIFO-очередью работ;
- асинхронный lifecycle `Database.open()` / `Database.close()`, read API и
  `Database.transaction()` с синхронной callback-функцией как неделимым
  элементом очереди;
- `ReadSession` в режиме `PRAGMA query_only = ON` с authorizer-запретом записи и
  смены connection policy, а также транзакционно-ограниченный `Transaction`;
  сырой `sqlite3.Connection` наружу не выдаётся;
- пять PRAGMA из `db-schema.md` §1.1: `journal_mode=WAL`, `foreign_keys=ON`,
  `synchronous=FULL`, `busy_timeout=5000`, `trusted_schema=OFF`;
- нумерованный migration runner без downgrade и миграция `0001_initial.sql` со
  всеми 65 таблицами, 33 явными индексами, 7 представлениями, 37 триггерами и
  начальными значениями 27 справочников из `db-schema.md` — 25 простых
  одно-колоночных плюс `severity_scale` и `resolution_kind`;
- атомарная запись применённой версии в `schema_migration` и
  `PRAGMA foreign_key_check` перед commit каждой миграции;
- append-only API `append_run_event()`, детерминированная JSON-сериализация
  payload и возврат монотонного внутреннего ID события;
- автоматические тесты соединения, миграций, транзакций, конкуренции и событий,
  включая наличие SQL-миграции в собранном wheel.

**Не входит:**

- репозитории агрегатов, запросы представлений и полный набор негативных тестов
  инвариантов схемы — `T1.3`;
- правила капа, reconciliation и severity — `T1.4`–`T1.6`;
- Pydantic-контракты событий или закрытый реестр `run_event.kind`: kind остаётся
  открытым версионированным пространством, как требует `db-schema.md` §1.4;
- создание и завершение записей `service_epoch`, а также recovery —
  `T1.10a`/`T1.10b`; instance lock и readiness — `T1.11`;
- проверка, что каталог состояния расположен вне агентского клона, и создание
  этого каталога: это граница `T1.11`/`T1.17`, а не низкоуровневого store;
- запрет открыть два объекта `Database` на одном файле: T1.2 гарантирует один
  writer на экземпляр store, а межпроцессный и process-wide запрет обеспечивает
  instance lock из `T1.11` до открытия базы;
- семантическая проверка «каждый конкретный переход состояния сопровождается
  событием»: T1.2 даёт общую атомарную границу, а полноту именованных операций
  обеспечивают репозитории `T1.3` и вертикальный срез `T1.7b`;
- отдельные read-only соединения, connection pool, ORM, downgrade migrations,
  backup/retention и оптимизация тяжёлых чтений;
- изменение DDL относительно `db-schema.md`: найденное расхождение сначала
  возвращает дизайн и этот план на ревью.

Миграции являются единственным внутренним исключением из публичного правила
«запись только через `Database.transaction()`»: runner выполняет их до возврата
от `Database.open()`, но использует ту же атомарную границу
`BEGIN IMMEDIATE`/`COMMIT`. После открытия произвольный SQL на запись доступен
только callback-функции, получившей активный `Transaction`.

## 5. Контракты и владельцы

| Контракт / граница | Владелец | Что создаётся или меняется | Потребители | Источник истины |
|---|---|---|---|---|
| `Database` lifecycle | `T1.2` | `await Database.open(path, core_version=core_version)` возвращает готовую мигрированную базу; `await close()` перестаёт принимать работы, завершает уже принятую работу и освобождает соединение/поток; повторный `close()` безопасен | `T1.3`, `T1.7b`, сервис и recovery | Этот план; [`architecture.md` §4.2](../../design/architecture.md) |
| Read boundary | `T1.2` | `await Database.read(fn)` выполняет синхронный `fn(ReadSession)` одним элементом очереди при `query_only=ON`; connection authorizer запрещает write/DDL/transaction control и изменение PRAGMA, попытка получает `WriteOutsideTransactionError` | Репозитории чтения `T1.3`, scheduler/CLI поздних задач | Этот план; [`task-plans.md`, T1.2](../../design/task-plans.md) |
| Write boundary | `T1.2` | `await Database.transaction(fn)` ставит целиком синхронный `fn(Transaction)` в очередь, выполняет `BEGIN IMMEDIATE`, commit либо rollback; callback не может быть async, выполнять DDL/`ATTACH`/`DETACH`, управлять транзакцией или менять connection PRAGMA, а `Transaction` недействителен после возврата | Все репозитории и шесть атомарных операций `db-schema.md` §11 | Этот план; [`architecture.md` §2 и §4.2](../../design/architecture.md); [`db-schema.md` §10–§11](../../design/db-schema.md) |
| Модель ошибок store | `T1.2` | `StoreError` — база для lifecycle/policy ошибок `StoreClosedError`, `DatabasePragmaError`, `WriteOutsideTransactionError`, `TransactionUsageError`, `MigrationError`, `IncompatibleSchemaError`, `EventPayloadError`; `DatabasePragmaError` несёт имя PRAGMA и expected/actual, constraint-ошибки SQLite не маскируются | `T1.3`, recovery, service composition root | Этот план |
| Версия схемы | `T1.2` | Поддерживаемая версия ядра — `1`; применённые версии и `core_version` записываются в `schema_migration`; база с `MAX(version) > 1` отвергается до пользовательской записи | Все задачи, читающие SQLite | [`decision.md` §5](../../metaResearches/decision.md); [`db-schema.md` §3 и §13](../../design/db-schema.md) |
| SQL migration resources | `T1.2` | Строго именованные и упорядоченные `NNNN_*.sql` загружаются через `importlib.resources`, входят в wheel и применяются без зависимости от текущего cwd | Startup сервиса, будущие schema migrations | [`db-schema.md` §13](../../design/db-schema.md); этот план |
| DDL `0001` | `T1.2` | Точный перенос нормативных `CREATE`/seed-операторов `db-schema.md` §1–§12 без нового доменного решения | `T1.3` и весь RunStore | [`db-schema.md` §1–§13](../../design/db-schema.md) |
| `run_event` append API | `T1.2` | `NewRunEvent` принимает `run_id`, `kind`, mapping-payload, `created_at` в epoch ms и optional `branch_id`/`stage_id`; `append_run_event(tx, event) -> int` сериализует JSON с `sort_keys=True`, compact separators, UTF-8 и запретом NaN | Все доменные переходы и репозитории | [`decision.md` §5, §6.6](../../metaResearches/decision.md); [`db-schema.md` §6.3–§6.4](../../design/db-schema.md) |
| Aggregate repositories | `T1.3` | Получают только `ReadSession`/`Transaction`; не открывают соединения, не выполняют собственные `BEGIN`/`COMMIT` и добавляют `run_event` только через `append_run_event` | `T1.4`–`T1.7b` | Граница пакета P1-A в [`task-plans.md` §3.1](../../design/task-plans.md); этот план |

Минимальная публичная поверхность конкретных классов (не `Protocol`):

| Вызов | Результат |
|---|---|
| `await Database.open(path, *, core_version: str)` | Готовый `Database` после PRAGMA и migrations |
| `await Database.read(fn: Callable[[ReadSession], T])` | Результат `T` после завершения одной read job |
| `await Database.transaction(fn: Callable[[Transaction], T])` | Результат `T` после commit |
| `await Database.close()` | Соединение и worker закрыты |
| `ReadSession.fetch_one(sql, parameters)` / `fetch_all(sql, parameters)` | `sqlite3.Row \| None` / неизменяемая последовательность строк |
| `Transaction.execute(sql, parameters)` / `executemany(sql, parameter_rows)` | Immutable `StatementResult(lastrowid, rowcount)` |
| `append_run_event(transaction, event)` | Внутренний `int` ID вставленного события |

`Transaction` также предоставляет `fetch_one`/`fetch_all`. Параметры SQL —
`Sequence[SQLiteValue] | Mapping[str, SQLiteValue]`, где `SQLiteValue` ограничен
значениями, принимаемыми stdlib `sqlite3`. `fetch_all` возвращает неизменяемую
последовательность `sqlite3.Row`, `fetch_one` — строку или `None`, а immutable
`StatementResult` содержит только `lastrowid` и `rowcount`; живой
`sqlite3.Cursor` за пределы worker не выходит. Generic-результат callback
передаётся вызывающей корутине только после завершения read job либо commit.

Синхронность callback-функции — часть контракта, а не деталь реализации. Она
не позволяет держать SQLite-транзакцию открытой вокруг сетевого или
процессного `await`; внешний эффект обязан оформляться отдельно как
intent → effect → reconcile.

## 6. Инварианты и отказные сценарии

| ID | Инвариант или сценарий | Где обеспечивается | Как проверяется |
|---|---|---|---|
| `INV-1` | Соединение создаётся, используется и закрывается только writer-thread; event loop не вызывает блокирующий `sqlite3` | Очередь команд + владение соединением внутри worker | `AC-1`, `AC-6`, `V-1` |
| `INV-2` | `open()` возвращает базу только после readback всех пяти нормативных PRAGMA; несовпадение не допускает молчаливого fallback | Инициализация и проверка соединения до миграций | `AC-1`, `AC-12`, `V-1` |
| `INV-3` | Публичная запись возможна только внутри активного `Transaction`; read callback работает при `query_only=ON` и не может отключить защиту, а сохранённая после callback scoped session недействительна | Разные scoped session-типы + authorizer + отсутствие raw connection | `AC-5`, `V-1` |
| `INV-4` | В очереди одной работой является вся транзакция, поэтому две корутины не могут перемежать операторы или открыть второй `BEGIN` до завершения первого | FIFO worker + `BEGIN IMMEDIATE` внутри transaction job | `AC-4`, `V-1` |
| `INV-5` | Callback либо фиксируется целиком, либо его записи и событие целиком откатываются; исключение возвращается вызывающему без подмены | `BEGIN IMMEDIATE` + `COMMIT`/`ROLLBACK` в worker | `AC-3`, `V-1`, `V-3` |
| `INV-6` | Нумерованные миграции образуют уникальную непрерывную последовательность, применяются ровно один раз и в той же транзакции проходят `foreign_key_check` | Migration runner + `schema_migration` | `AC-2`, `AC-7`, `V-2` |
| `INV-7` | `0001` создаёт полную схему design-baseline и все seed-значения из любого cwd, а SQL resource входит в собранный wheel | Packaged SQL resource + schema inventory tests | `AC-2`, `AC-8`, `AC-13`, `V-2`, `V-5`, `V-6`, `V-7` |
| `INV-8` | `run_event.id` задаёт общий монотонный порядок, а существующие строки нельзя обновить или удалить | База: AUTOINCREMENT и два BEFORE-триггера | `AC-9`, `V-3` |
| `INV-9` | После принятия transaction job отмена ожидающей корутины наблюдается только после commit/rollback; фоновая запись не продолжается после возврата `CancelledError` | Состояние queue job + cancellation handshake | `AC-10`, `V-1` |
| `INV-10` | `append_run_event` принимает только сериализуемый mapping-payload, сохраняет детерминированный JSON-объект и запрещает NaN/Infinity | Код event API | `AC-3`, `AC-9`, `V-3` |
| `FAIL-1` | В read callback выполняется `INSERT`, `UPDATE`, `DELETE` или DDL | Операция отвергается как `WriteOutsideTransactionError`, состояние не меняется, соединение остаётся пригодным | `AC-5`, `V-1` |
| `FAIL-2` | Transaction callback или commit завершается исключением | Выполняется rollback, исходное исключение возвращается; частичного state/event нет | `AC-3`, `V-1`, `V-3` |
| `FAIL-3` | В базе записана schema version новее поддерживаемой ядром | `open()` завершается `IncompatibleSchemaError` до миграции и пользовательской записи; файл не изменяется | `AC-7`, `V-2` |
| `FAIL-4` | SQL migration не исполняется либо `foreign_key_check` вернул строки | Вся миграция, включая её строку в `schema_migration`, откатывается и возвращается `MigrationError` с version/name | `AC-7`, `V-2` |
| `FAIL-5` | После `close()` приходит новая read/transaction работа | Работа не ставится в очередь и завершается `StoreClosedError`; повторный `close()` не падает | `AC-6`, `V-1` |
| `FAIL-6` | Event payload не сериализуется, не является mapping или содержит NaN/Infinity | `append_run_event` выдаёт `EventPayloadError` до INSERT; окружающая транзакция следует обычной rollback-семантике | `AC-3`, `V-3` |
| `FAIL-7` | Transaction coroutine отменена до старта либо во время выполнения callback | Не начатая job пропускается; начатая доходит до результата: после успешного commit вызывающий получает `CancelledError`, а ошибка callback/commit не скрывается отменой | `AC-10`, `V-1` |
| `FAIL-8` | Transaction callback возвращает awaitable либо пытается выполнить DDL, `ATTACH`/`DETACH`, собственный `BEGIN`/`COMMIT`/`ROLLBACK`/`SAVEPOINT` или изменить connection PRAGMA | Работа откатывается с `TransactionUsageError`; схема и управление соединением остаются у migration runner/`Database` | `AC-11`, `V-1` |
| `FAIL-9` | В непустой базе нет `schema_migration` | Runner не пытается усыновить неизвестную схему и завершает `open()` с `MigrationError` без изменения файла | `AC-7`, `V-2` |
| `FAIL-10` | Readback после установки PRAGMA отличается от нормативного значения, в частности `journal_mode` не стал `wal` | `open()` завершается `DatabasePragmaError(pragma, expected, actual)` до миграций, закрывает соединение/worker и не включает fallback | `AC-12`, `V-1` |

## 8. Порядок реализации

1. Создать пакет `store`, типы ошибок и dedicated worker, который открывает
   `sqlite3.Connection` с `isolation_level=None` внутри собственного потока,
   применяет и считывает обратно пять PRAGMA, при несовпадении выдаёт
   `DatabasePragmaError` до миграций и не публикует raw connection.
2. Реализовать migration discovery с проверкой строгих имён, уникальности и
   непрерывности версий. SQL выполнять по полным операторам, выделенным через
   `sqlite3.complete_statement`, внутри явного `BEGIN IMMEDIATE`: не использовать
   `Connection.executescript()` как вложенный transaction runner.
3. Перенести нормативную DDL в `0001_initial.sql`, после SQL выполнить
   `foreign_key_check`, записать version/core version и только затем commit.
   Добавить package-data и тест точного inventory схемы.
4. Добавить `read(fn)` и `transaction(fn)`. На время read job включать
   `query_only` и authorizer, запрещающий запись и смену connection policy;
   transaction job целиком — от `BEGIN IMMEDIATE` до commit/rollback — держать
   одним элементом очереди, запрещать callback DDL, attach, собственный
   transaction control и смену connection policy, после callback закрывать
   scoped session.
5. Реализовать `NewRunEvent`/`append_run_event`, затем тесты атомарной пары
   state+event, append-only триггеров и JSON payload.
6. Проверить повторное открытие, PRAGMA mismatch на `:memory:`, новую
   несовместимую schema version, поломанный migration/FK, конкурентные
   корутины, закрытие worker и наличие SQL в wheel; завершить общей проверкой
   проекта.

## 9. Критерии приёмки

- **AC-1.** При новом пути к файлу во временном существующем каталоге, когда
  выполняется `Database.open()`, тогда соединение открыто writer-thread,
  event loop остаётся отзывчивым, а запрос значений пяти PRAGMA возвращает
  `wal`, `1`, `2` (`FULL`), `5000` и `0` соответственно.
- **AC-2.** При пустом файле, когда выполняется `open()`, тогда `0001`
  применяется одной транзакцией, `schema_migration` содержит ровно version 1,
  `sqlite_master` после фильтра `name NOT LIKE 'sqlite_%'` содержит 65
  пользовательских таблиц, 33 явных индекса, 7 представлений и 37 триггеров,
  все 27 справочников засеяны, каждый view запрашивается на пустой базе, а
  `PRAGMA foreign_key_check` не возвращает строк.
- **AC-3.** При callback, записывающем новый run и связанный `run_event`, когда
  callback завершается нормально, тогда обе записи видны после commit; когда
  после обеих вставок callback либо сериализация payload падает, тогда не видна
  ни одна запись и вызывающий получает исходную ошибку.
- **AC-4.** При двух конкурентных корутинах, первая из которых удерживает
  transaction callback на управляемом тестом барьере, когда вторая запрашивает
  транзакцию, тогда её callback не начинается до commit/rollback первой; SQL
  двух транзакций не перемежается и ошибка nested transaction не возникает.
- **AC-5.** При read callback, пытающемся выполнить запись, или при повторном
  использовании сохранённого `ReadSession`/`Transaction` после выхода из
  callback, когда выполняется SQL, тогда операция отвергается типизированной
  ошибкой, данные не меняются, а следующий штатный запрос проходит.
- **AC-6.** При открытой базе с принятыми в очередь работами, когда вызывается
  `close()`, тогда принятые работы завершаются, новые отвергаются, соединение и
  worker-thread закрываются; повторный `close()` успешен.
- **AC-7.** При повторном открытии базы version 1 миграция не применяется
  второй раз; при version 2, непустой неверсионированной базе либо при
  синтетической ошибке SQL/FK `open()` завершается соответствующей
  migration-ошибкой без частично записанной версии, без изменения существующих
  пользовательских данных и без оставленного worker-thread.
- **AC-8.** При запуске из рабочего каталога, отличного от корня checkout,
  когда открывается пустая база, тогда `0001_initial.sql` находится как package
  resource и создаёт ту же полную schema version 1.
- **AC-9.** При двух успешно добавленных событиях одного run, когда читается
  журнал, тогда второе ID больше первого, payload декодируется в исходный JSON-
  объект; прямые `UPDATE` и `DELETE` через активный `Transaction` отвергаются
  триггерами `run_event is append-only`.
- **AC-10.** При отмене корутины до начала transaction job callback не
  исполняется; при отмене после начала callback сначала наблюдаемо завершается
  commit либо rollback. После успешного commit вызывающий получает
  `CancelledError`; ошибка callback/commit имеет приоритет и возвращается
  вызывающему. В обоих случаях после результата в worker не остаётся фоновой
  записи этой job.
- **AC-11.** При transaction callback, который возвращает awaitable или
  выполняет DDL, `ATTACH`/`DETACH` либо собственный
  transaction-control/connection-policy SQL, когда job доходит до worker,
  тогда она откатывается с `TransactionUsageError`, а следующая штатная
  транзакция проходит на том же соединении.
- **AC-12.** При SQLite-соединении, на котором установка `journal_mode=WAL`
  читается обратно другим значением (детерминированный свидетель —
  `:memory:` возвращает `memory`), когда выполняется `Database.open()`, тогда
  вызывающий получает `DatabasePragmaError` с `journal_mode`, expected `wal` и
  actual `memory`; миграции не начинаются, worker-thread закрывается.
- **AC-13.** При сборке wheel, когда проверяется inventory дистрибутива, тогда
  он содержит `metaswarm/store/migrations/0001_initial.sql`.

## 11. Риски и откат

| Риск | Ранний сигнал | Что делать | Граница отката |
|---|---|---|---|
| `executescript()` или пооператорный commit незаметно разрушит атомарность migration | После намеренной ошибки часть объектов `0001` остаётся в файле либо строка версии расходится со схемой | Выполнять полные statements через `sqlite3.complete_statement` под одним явным `BEGIN IMMEDIATE`; держать негативный тест частичной миграции | До появления пользовательской базы откатываются `store/`, package-data и его тесты; существующую базу вниз не мигрировать |
| Async API позволит SQL разных корутин вклиниться внутрь транзакции | Барьерный тест видит начало второго callback до завершения первого либо SQLite сообщает nested transaction | Очередью считать весь callback, не отдельный `execute`; не превращать callback в async context manager без повторного ревью границы | Откатить реализацию очереди к последней версии, прошедшей serialization test; DDL не затронута |
| Отменённый asyncio caller оставит неотслеживаемую запись в worker | Coroutine уже получила `CancelledError`, а база позже меняется | После принятия transaction job задерживать доставку отмены до её commit/rollback; до старта отменённую job не исполнять; добавить барьерный тест | Меняется только lifecycle очереди, публичная транзакционная сигнатура сохраняется |
| SQL resource доступен из checkout, но отсутствует в wheel | Editable-тест зелёный, inventory wheel не содержит `0001_initial.sql` | Явно включить package data и держать пару проверок `V-6`/`V-7` | Откатить только package-data/migration packaging до исправления; не выпускать артефакт без `0001` |
| Нормативная DDL изменится во время реализации T1.3 | Schema inventory или invariant test расходится с `0001` | Изменить `db-schema.md`, migration и оба затронутых плана одним решением; до первой реальной базы допустимо переписать `0001`, после — только новая migration | До M1 тестовые базы одноразовы; после появления реального state file `0001` неизменяема, отката вниз нет |
| WAL недоступен на конкретной файловой системе | Проверка после `PRAGMA journal_mode=WAL` возвращает не `wal`; тот же путь детерминированно воспроизводится на `:memory:` | Завершить `open()` с `DatabasePragmaError`, проверяемым `FAIL-10`/`AC-12`/`V-1`; не делать молчаливый fallback, а вынести смену режима на ревью решения | Файл, на котором schema migration не началась, можно удалить как тестовый; пользовательские базы не удаляются автоматически |

## 12. Допущения и открытые вопросы

**Допущения:**

- T1.1 будет реализована и принята до начала T1.2; baseline в паспорте фиксирует
  код и документы, по которым написан план, а фактический implementation-base
  дополнительно фиксируется общим baseline-коммитом пакета P1-A после ревью его
  границ.
- Целевые WSL2 и Linux VPS используют файловую систему, на которой SQLite
  поддерживает WAL; база не размещается на сетевом filesystem и не лежит в
  агентском clone.
- `sqlite3` из CPython 3.12 предоставляет `complete_statement`,
  `PRAGMA trusted_schema` и WAL; на текущем VPS это Python 3.12.3 с SQLite
  3.45.1. Проект не требует совпадения patch-версий между средами.
- Transaction callback содержит только короткий синхронный SQL-код. Сеть,
  subprocess, файловые эффекты и ожидание asyncio внутри неё запрещены и позже
  оформляются через intent → effect → reconcile.
- До первого production state file миграция `0001` может уточняться вместе с
  design; после появления такого файла опубликованная `0001` считается
  неизменяемой, а любое развитие идёт новой migration.

**Открытые вопросы:** нет.
