## 2. Цель и наблюдаемый результат

**Цель.** Создать одну строгую машинную границу для всех восьми ответов
агентов: извлечь payload из маркеров, без неявных преобразований проверить JSON,
схему и snapshot-зависимые правила и вернуть либо typed result, либо
детерминированный список ошибок для повторной попытки.

**Наблюдаемый результат.** Потребитель передаёт валидатору уже извлечённый
адаптером финальный текст, ожидаемое имя схемы и immutable context конкретной
попытки. Валидный ответ превращается в один из восьми typed results; невалидный
целиком отклоняется с адресными `ContractIssue`. Для `verification.plan.v1`
структурная ошибка остаётся `contract_error`, а запрет политики возвращается
отдельным `VerificationPolicyRejection`, сохраняющим сам валидный план. Ни БД,
ни checkout, ни процессы T1.7 не читает.

## 3. Границы

**Входит:**

- точные begin/end markers, единственный JSON-object до `1 MiB`, запрет
  duplicate keys, любого non-finite числа, включая `NaN`/`Infinity` и
  переполнение `1e999`, lone Unicode surrogate в строке/ключе, неизвестных
  полей и type coercion;
- закрытый registry восьми agent-authored схем v1 и строгие Pydantic-модели
  всех вложенных значений;
- distinct observation types: blind/new с обязательным
  `severity_suggested` и follow-up с XOR
  `severity_suggested`/`unchanged_from`;
- immutable contexts с разрешёнными файлами/ID, scoped ledger, dispositions,
  ownership, policy snapshot, reachable SHA и reason human-вопроса;
- все проверки `agent-contracts.md` §11: observations, reconciliation,
  dispositions, decisions, verification plan, graph, cut-off и human question;
- плоский reconciliation context по raw observation IDs без `dedup_key`,
  representative, aliases или скрытого раскрытия; одинаковые записи остаются
  отдельными элементами exact-set проверки;
- обязательный пустой или непустой `new_observations`, direct follow-up только
  при `still_present`/`insists` и только на показанный caller'ом target;
- структурное отделение пяти `VerificationPolicyRejection` от
  `contract_error`, без запуска команды и без создания вопроса в этой задаче;
- канонические bytes cut-off и SHA-256, вычисленный сервисным кодом после
  валидации, а не принятый от агента;
- нормализованный стабильный список ошибок и retry feedback не больше 50
  целых issues / 16 KiB UTF-8 без partial result и без повторения недоверенных
  значений;
- первая runtime-зависимость `pydantic>=2.13,<2.14` с синхронным обновлением
  `pyproject.toml` и `uv.lock`.

**Не входит:**

- разбор vendor stream-json, `extract_result()`, коды выхода, resume и
  исполняемый fake CLI — `T1.8`; тесты T1.7 получают синтетический финальный
  текст уже после vendor adapter boundary;
- запуск/убийство процесса, расход `contract_retry_budget`, persistence попытки
  и выбор retry — `T1.8`/`T1.18`; T1.7 только формирует ошибку и feedback;
- правила campaign/cap, identity/reconciliation и severity/period как
  самостоятельный домен — `T1.4`/`T1.5`/`T1.6`; их владельцы повторно проверяют
  несущие правила перед созданием persistence intents;
- атомарная запись observations, links, decisions, resolutions, round result и
  human gate — `T1.7b`/`T1.16`;
- авторитетная повторная policy-проверка непосредственно перед исполнением,
  запуск verification steps и создание human question при запрете — `T1.14`;
- Pydantic-конфиг проекта/флоу — `T1.17`; он переиспользует выбранную
  зависимость, но не модели ответов агента;
- хранение cut-off как артефакта — `T1.13` и фаза 2; T1.7 отдаёт только
  проверенные canonical bytes + digest;
- интерпретация ответа человека — `T1.16`; `human.question.v1` описывает вопрос,
  а не `human_answer`;
- формулировка review-вопросов (`dispute`, `cap_exhausted_*`, `reconcile_failed`,
  `reopen_human_closed`) и их наборы вариантов — детерминированный formatter
  (Q51): через агента и через T1.7 они не проходят вовсе. T1.7 валидирует
  `human.question.v1` только для единственной agent-authored причины
  `open_question`;
- `verification.result.v1`: его пишет детерминированный сервис, поэтому это не
  девятая модель ответа агента;
- prompt templates, локализация сообщений и настройка моделей — `T1.20`.

Контекстные проверки T1.7 — ранняя защита и качественный feedback, а не новый
владелец домена. Например, T1.7 проверяет, что `unchanged_from` был показан
ревьюеру для этого finding, но тот же finding и текущий severity-период
подтверждает T1.6; T1.14 повторно применяет verification policy к актуальному
checkout непосредственно перед внешним эффектом.

`ValidatedAgentResult` всегда хранит typed payload. Поле
`policy_rejections` существует только как результат проверки валидного
`VerificationPlan` и в остальных семи контекстах пусто. Таким образом policy
rejection нельзя случайно потратить как contract retry и нельзя потерять сам
предложенный агентом план, который должен попасть в вопрос человеку.
Frozen top-level недостаточен: model fields с коллекциями объявляются tuple, а
любой mapping в служебном outcome сначала копируется в frozen DTO. Критерий
границы простой — из `ValidatedAgentResult` не достижим mutable container,
который можно изменить после enqueue.

## 8. Порядок реализации

1. Добавить Pydantic в `project.dependencies`, обновить `uv.lock` и сразу
   подтвердить `uv run --locked`; не менять dev/build constraints.
2. Реализовать transport layer отдельно от моделей: точный подсчёт markers,
   типизированный отказ на не кодируемую в UTF-8 подстроку между markers, byte
   boundary `1_048_576`, strict loader с `object_pairs_hook` и
   `parse_constant`, а также `parse_float`, отклоняющим любой результат, для
   которого `math.isfinite()` ложен; после parse рекурсивно отвергать surrogate
   в key/value и только затем проверять top-level object/Pydantic. Внешний text
   не кодировать и не валидировать.
3. Описать strict frozen nested models и восемь top-level schemas; все поля
   JSON-array представить tuple через общий before-validator, принимающий
   только parser-produced list, и исключить mutable containers из достижимого
   result graph. На каждую
   сначала добавить один normative valid sample из `agent-contracts.md`, затем
   parameterized extra/coercion/missing-field cases и проверку закрытого
   registry.
4. Ввести frozen `ContractIssue`, `AgentContractError`,
   `ValidationContextError` и глубоко immutable typed `ValidatedAgentResult`;
   нормализовать Pydantic paths/codes без `input`/raw value, неизвестный
   model-controlled key заменить полным SHA-256 и длиной UTF-8.
5. Реализовать immutable review contexts и проверки по слоям: observations →
   reconciliation → dispositions → decisions. Проверить exact set equality,
   напрямую по raw IDs, scope/ownership, допустимые пары, новый observation и
   direct follow-up Q45; не принимать dedup/alias map и не импортировать
   T1.4–T1.6.
6. Реализовать operational validators: структура verification step, затем все
   пять policy rejections; graph completeness/cycle path; cut-off references,
   nullable implementation scope с exact context match, canonical bytes/digest;
   human question — только agent-authored
   `open_question`, включая отказ каллеру с чужой причиной.
7. Реализовать retry renderer поверх normalized issues: стабильный порядок,
   не больше 50 целых записей и 16 KiB после UTF-8 encoding, с резервированием
   footer, точным числом опущенных причин и требованием resend full result.
   Policy и caller-context failures через этот renderer не проходят.
8. Выполнить пять целевых test-модулей, locked dependency check и общий
   `./scripts/check.sh`; metadata-тест обязан увидеть ровно Pydantic, а
   inspection подтвердит, что собственный implementation diff ограничен
   contract boundary, пятью целевыми модулями, package metadata-тестом и
   dependency pair.

## 9. Критерии приёмки

- **AC-1.** Когда финальный текст содержит произвольный reasoning до и после
  единственной пары markers и валидный payload внутри, тогда возвращается один
  typed result; изменение внешнего текста не меняет результат.
- **AC-2.** Для каждого transport defect — missing/duplicate/reversed marker,
  пустого/oversize/malformed/non-object/duplicate-key/trailing JSON, явного
  `NaN`/`Infinity` и обычного числового литерала `1e999`, превратившегося в
  infinity, direct lone surrogate в подстроке между markers и escaped lone
  high/low surrogate в любом key/value после parse — когда вызывается
  validator, тогда результат целиком отклонён issue `invalid_unicode` до
  выбора Pydantic-модели. Тот же direct surrogate вне markers игнорируется;
  корректная escaped surrogate pair декодируется в один Unicode scalar и
  принимается.
- **AC-3.** Для каждой из ровно восьми схем normative sample валиден, а wrong
  expected/unknown/service schema, extra field, missing field и coercible wrong
  type отклоняются без fallback на другую модель.
- **AC-4.** Для blind и fix-check new observations допустимые lengths,
  path/range и suggested severity принимаются, пустой список законен;
  `unchanged_from`, `finding_id`, overlong text, отсутствующий файл, invalid
  range и 101-я запись отклоняют весь result.
- **AC-5.** Для discovery и fix-check-new reconciliation каждый exposed raw
  observation ID встречается ровно один раз без раскрытия aliases; две записи с
  одинаковыми шестью полями и разными evidence остаются двумя IDs и обе обязаны
  быть покрыты. Четыре outcome используют только разрешённые open/closed subsets, Q44
  допускает `reaffirmed_closed` только после `accepted_reason`, а восьмая
  проверка требует непустой title только у `new` и запрещает его трём исходам
  существующего ID.
- **AC-6.** Dispositions принимаются только как exact set ожидаемых open IDs с
  одной записью на ID и обязательной reason для `rejected`/`wont_fix`; ни один
  partial/foreign/duplicate набор не возвращает typed payload.
- **AC-7.** Decisions принимаются только от owner как exact set с допустимой
  disposition pair; обязательный пустой `new_observations` валиден, новый
  элемент не принимает identity/unchanged fields, а direct follow-up допустим
  только при `still_present`/`insists` и на показанный observation этого ID.
- **AC-8.** Валидный verification plan с непустыми steps/rationale, argv-list,
  точным `expect=exit_zero` и positive optional timeout возвращается typed.
  Пустой план, другое значение expect и structural defects дают contract error;
  нарушения каждого из пяти policy rules возвращают все соответствующие
  `VerificationPolicyRejection` вместе с планом и не превращаются в retry.
- **AC-9.** Для валидного DAG graph result принимается независимо от порядка
  input; duplicate ID/edge, dangling endpoint, self-edge и cycle отклоняют весь
  graph, причём cycle issue содержит конкретный воспроизводимый путь.
- **AC-10.** Валидный non-implementation cut-off с `implementation_scope=null`
  и валидный implementation cut-off с двумя expected SHA, объявленными в
  `referenced_shas`, возвращают canonical bytes и SHA-256; перестановка JSON keys
  не меняет их. Пустое поле, нерезолвимый file/SHA, частичная/переставленная
  пара, object при non-implementation context или `null` при implementation
  context не отдаёт artifact result.
- **AC-11.** Валидный `open_question` принимается и с пустыми options, и с
  набором из уникальных keys, непустых labels и confidence `[0,1]`; пустой
  `question_text`, duplicate key, пустой label и confidence вне диапазона
  отклоняются. Попытка построить `HumanQuestionContext` для любой другой
  причины даёт `ValidationContextError`, а не разбор payload: нормативных
  наборов вариантов review-вопросов T1.7 не знает и не проверяет.
- **AC-12.** При нескольких независимых ошибках одного parseable payload
  feedback содержит не больше первых 50 **целых** issues в стабильном порядке
  normalized path/code и не превышает `16_384` UTF-8 bytes вместе с
  header/footer. Ключ extra-поля почти размером с `MAX_RESULT_BYTES` не
  отражается: path содержит только полный SHA-256 и исходную byte length.
  Renderer сообщает точное число остальных по обоим пределам, заканчивается
  требованием прислать полный результат, не режет строку/code point; повторный
  вызов byte-for-byte равен первому.
- **AC-13.** После реализации `./scripts/check.sh` зелёный,
  `pydantic` установлен в версии `2.13.x` из неизменяемого lockfile, а diff от
  implementation parent T1.7 содержит только `agents` contract boundary, пять
  test-модулей, package metadata-тест, согласованную пару
  `pyproject.toml`/`uv.lock` и это принятое уточнение собственного плана.
- **AC-14.** Для normative sample каждой из восьми схем после получения
  `ValidatedAgentResult` тест пытается изменить вложенную коллекцию **самого
  результата** (не исходный raw list/dict), nested model и
  `policy_rejections`: мутация невозможна. Изменение исходного input после
  validation также не меняет result, а рекурсивный обход не находит достижимых
  `list`/`dict`/`set`.

## 12. Допущения и открытые вопросы

**Допущения:**

- На baseline проектирования stable Pydantic — линия 2.13, поэтому узкий
  диапазон `>=2.13,<2.14` соответствует принятой политике зависимостей. Если до
  реализации 2.14 станет необходимой из-за исправления, диапазон и lockfile
  меняются отдельным решением с повторным ревью этого плана.
- Adapter T1.8 передаёт сюда только финальный текст результата, уже отделённый
  от vendor stream. Нормативные synthetic tests T1.7 не утверждают ничего о
  stdout/stderr/exit code конкретного CLI.
- `MAX_RESULT_BYTES` измеряется по UTF-8 bytes между markers, а не по Python
  characters и не по полному transcript; не кодируемая подстрока сначала даёт
  `invalid_unicode`, для кодируемой ровно `1_048_576` bytes допустимо, следующее
  значение отклоняется. Surrogate во внешнем noise в размер не входит.
- `MAX_RETRY_FEEDBACK_BYTES=16_384` измеряется по готовому UTF-8 блоку вместе с
  header/footer; byte-cap не разрешает обрезать issue или Unicode code point.
- Immutable context построен из snapshot той же attempt/revision, которую видел
  агент. Изменение snapshot identity после вызова — caller bug и не может быть
  исправлено schema retry.
- `referenced_files` и `referenced_shas` — исчерпывающие structured references
  cut-off. `implementation_scope` назначает роли уже объявленным SHA; свободный
  текст не парсится эвристиками, renderer строит ссылки только из проверенных
  полей.
- Planning baseline P1-A фиксирует принятую версию восьми планов. Фактический
  scope T1.7 считается только от implementation parent перед первой правкой;
  принятые ранее независимые задачи в этот diff не входят.

**Открытые вопросы:** нет.
