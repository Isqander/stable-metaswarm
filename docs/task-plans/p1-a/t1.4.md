## 2. Цель и наблюдаемый результат

**Цель.** Реализовать единственную чистую точку принятия решения после
`fix_check` в цикле правок и таблицу допустимых переходов кампании так, чтобы
кап правок нельзя было проверить на неверной границе или обойти новым
finding'ом.

Здесь **кампания** — один непрерывный цикл проверки одного предмета ревью в
конкретной стадии и ветке: от первичной ревизии и слепого ревью через
reconciliation и последующие правки автора до чистого завершения, отмены либо
окончательного решения человека. Терминальное состояние означает, что эта
запись кампании завершена и больше не имеет исходящих переходов. Поэтому
`closed_escalated` — не «система сейчас ждёт человека», а «человек уже
окончательно принял результат или остановил ветку».

**Наблюдаемый результат.** По неизменяемому набору фактов завершившейся
проверки авторской правки функция
`decide_after_check()` возвращает ровно одно типизированное действие: завершить
кампанию чисто, отправить автора на следующую правку либо закрыть текущий круг
как `escalated` и поставить human gate. Третья разрешённая правка всегда доходит
до четвёртой проверки; чистая четвёртая проверка завершается успехом; новое
замечание в ней не сбрасывает кап. Пока человек не ответил, campaign остаётся
`fix_cycle`, а `closed_escalated` достижим только окончательным human-решением.
Все ветви проверяются табличными unit-тестами без SQLite, asyncio и процессов.

## 3. Границы

**Входит:**

- чистые immutable input/output types review-cycle без зависимости от store;
- `decide_after_check(facts)` только для `fix_check` при состоянии кампании
  `fix_cycle`; функция одновременно задаёт `round_result` и campaign event для
  persistence-слоя;
- `decide_after_revision(campaign_state)`, всегда запускающая проверку после
  состоявшейся авторской ревизии и не принимающая счётчики капа;
- `next_campaign_state(current, event)` как единственная таблица допустимых
  переходов `discovery`/`reconciliation`/`fix_cycle`/трёх терминалов;
- приоритет решения: `clean` → немедленный dispute gate → следующая правка →
  cap gate;
- различение `cap_exhausted_same` и `cap_exhausted_new` по `first_round_id`
  открытых findings относительно текущего круга;
- проверка достижимого соотношения счётчиков в момент до закрытия текущего
  круга и post-decision assert `review_check_count <= max_author_revisions + 1`;
- self-transition `fix_cycle` при открытии human gate и разрешении ещё одной
  правки; терминальность `closed_clean`, `closed_escalated`,
  `closed_cancelled`;
- табличные unit-тесты всей state machine, обеих off-by-one границ, причин
  остановки, приоритетов и невалидных input snapshots.

**Не входит:**

- чтение/запись SQLite, repository DTO и транзакции — `T1.2`/`T1.3`;
  orchestration позже отображает repository projections в domain facts;
- определение, какие observations относятся к одному finding, выдача ID и
  проверка полноты reconciliation — `T1.5`. Для первичного `discovery` T1.5
  возвращает `clean` без работы автору либо `needs_revision` при её наличии;
  через `decide_after_check()` этот первичный круг намеренно не проходит. Для
  `new_observations` последующего `fix_check` T1.5 дополняет open set текущего
  круга до вызова T1.4;
- вычисление `escalation_severity`, сравнение с порогом, создание
  `policy_closed`, выбор/агрегация следующего dispute snapshot и правила reopen
  — `T1.6`; T1.4 получает уже вычисленный optional `EscalatingDispute` и
  post-policy множество открытых findings;
- разбор ответов агентов и Pydantic-схемы — `T1.7`;
- создание кампании сразу в начальном состоянии `discovery`, формирование
  `discovery_completed` и атомарная запись domain outcomes, round result,
  campaign state, event и human gate — `T1.7b`; создание строки не считается
  переходом state machine, а T1.4 только задаёт допустимые рёбра и возвращает
  значения для fix-cycle;
- формирование/отправка вопроса, обработка human answer, увеличение
  `stage_execution.max_author_revisions`, `awaiting_continue` и окончательный
  переход в `closed_escalated` — `T1.16`;
- scheduler, retry-бюджеты попыток, параллелизм веток и применение отмены
  кампании — `T1.9`, `T1.18`; пользовательская команда отмены принадлежит
  `T1.19`;
- универсальная state-machine библиотека, `Protocol` и runtime registry.

Первичный `discovery`-круг — отдельная граница: T1.5 задаёт его результат после
reconciliation, T1.7b записывает его, и `review_check_count` становится равен
1 до первой авторской правки. `decide_after_check()` начинает работать только
с последующими `fix_check` и вызывается **до** записи результата текущего
круга. Поэтому при первом вызове после первой правки оба входных счётчика равны
1; `review_check_count_before` ещё не включает текущий `fix_check`, а
возвращённое действие закрывает его. Ожидаемое значение после commit равно
`review_check_count_before + 1`. Это различие не оставляется на догадку
реализатору: иначе assert капа получает систематическую ошибку на единицу.

Закрытый словарь `CampaignEvent` и вся transition matrix:

| Событие | Исходное состояние | Следующее состояние | Кто производит смысл события |
|---|---|---|---|
| `discovery_completed` | `discovery` | `reconciliation` | Review workflow T1.7b после полного набора blind outputs; production orchestration — T1.18 |
| `reconciliation_has_findings` | `reconciliation` | `fix_cycle` | Outcome T1.5 отображается и пишется T1.7b |
| `reconciliation_clean` | `reconciliation` | `closed_clean` | Outcome T1.5 отображается и пишется T1.7b |
| `check_needs_revision` | `fix_cycle` | `fix_cycle` | `decide_after_check` T1.4; persistence — T1.7b |
| `human_gate_opened` | `fix_cycle` | `fix_cycle` | `decide_after_check` T1.4; question/persistence — T1.7b |
| `human_extra_revision` | `fix_cycle` | `fix_cycle` | Ответ обрабатывает T1.16 |
| `check_clean` | `fix_cycle` | `closed_clean` | `decide_after_check` T1.4; persistence — T1.7b |
| `human_finalized` | `fix_cycle` | `closed_escalated` | Окончательный ответ обрабатывает T1.16 |
| `cancelled` | `discovery`, `reconciliation` или `fix_cycle` | `closed_cancelled` | T1.18 применяет запрос отмены, полученный через T1.19 |

Создание `review_campaign(state=discovery)` в T1.7b — начальная вставка, а не
событие перехода, поэтому ребро `[*] → discovery` в эту таблицу не входит.
Других событий и рёбер после создания нет. Разные причины одного self-transition не
схлопываются: они нужны событиям аудита и потребителям, хотя состояние кампании
до и после совпадает.

Типы действий различаются классом, а не nullable-набором флагов. Публичный
consumer не может получить одновременно `clean` и human reason или
`needs_revision` и `closed_clean`. Строковые значения совпадают с DDL, но
domain не делает fallback/coercion неизвестных значений.

## 8. Порядок реализации

1. Определить `Literal`-значения, frozen inputs/actions и две domain errors;
   constructors действий должны исключать несовместимые result/reason/snapshot.
2. Записать campaign transition table из `architecture.md` §6.2, включая два
   human self-transition и отсутствие исходящих рёбер у terminal states;
   параметризовать позитивную и негативную матрицы.
3. Реализовать валидацию `CheckFacts`: состояние, неотрицательные counters,
   равенство counters до check, cap bound, уникальность/open membership и
   временной порядок `first_round_id`.
4. Реализовать `decide_after_check` четырьмя ветвями в нормативном порядке и
   `decide_after_revision` без counters; через campaign state table пропускать
   только действия, которые несут `CampaignEvent`. `StartReviewCheck` сам
   состояние кампании не меняет.
5. Взять результат T1.5 `discovery=needs_revision` как уже закрытый первый
   check, затем таблично прогнать default cap через три пары revision/fix-check:
   четвёртая общая проверка даёт clean либо escalated. В case нового замечания
   получить `OpenFinding(first_round_id=current_round_id)` из reconciliation
   `review.decisions.v1.new_observations`, а не конструировать недостижимый
   snapshot без владельца; отдельно проверить ранний dispute и post-policy
   набор findings.
6. Проверить invalid snapshots и pure-domain границу, затем выполнить общий
   `./scripts/check.sh` и inspection implementation diff.

## 9. Критерии приёмки

- **AC-1.** При одинаковом `CheckFacts`, когда `decide_after_check()` вызывается
  многократно, тогда возвращаются равные frozen values; функция не читает время,
  БД, env и не выполняет I/O.
- **AC-2.** При непустом open set без escalating dispute, когда
  `author_revision_count < max_author_revisions`, тогда результат — только
  `StartAuthorRevision(round_result=needs_revision)` и campaign остаётся
  `fix_cycle` независимо от `review_check_count_before` как отдельного гейта.
- **AC-3.** После третьей правки при default cap 3, когда четвёртая проверка не
  оставляет open findings, тогда результат `CloseClean(clean)` и target state
  `closed_clean`; human gate не создаётся.
- **AC-4.** После последней разрешённой author revision, когда вызывается
  `decide_after_revision(fix_cycle)`, тогда без чтения counters возвращается
  `StartReviewCheck`; cap проверяется только после результата этой проверки.
- **AC-5.** При open finding с preselected escalating dispute, когда cap ещё
  имеет остаток или уже исчерпан, тогда возвращается `AskHuman(dispute,
  escalated)`; round закрывается, campaign остаётся `fix_cycle`, snapshot
  содержит finding/severity/threshold/policy version.
- **AC-6.** При исчерпанном cap и open findings, когда T1.5 выдал хотя бы один
  новый finding из `new_observations` текущего `fix_check`, тогда его
  `first_round_id` равен `current_round_id` и результат T1.4 —
  `cap_exhausted_new`; без таких findings — `cap_exhausted_same`. В обоих
  случаях следующая author revision не стартует и cap не сбрасывается.
- **AC-7.** Когда все настаивания ниже порога уже представлены закрытыми
  `policy_closed` и open set пуст, тогда тот же check даёт `clean`; если в open
  set остаются другие findings, результат определяется обычным остатком cap без
  дополнительного подтверждающего круга.
- **AC-8.** При любом недостижимом snapshot counters/findings, когда вызывается
  decision function, тогда получается `CycleInvariantError`, а не штатное
  действие; post-decision check count никогда не выше `max + 1`.
- **AC-9.** Полная transition table принимает human gate и дополнительную
  правку как `fix_cycle → fix_cycle`, final human answer как
  `fix_cycle → closed_escalated`, оба результата reconciliation, cancellation
  из трёх активных состояний и не принимает ни одного события из terminal
  states; создание кампании в `discovery` переходом не считается.
- **AC-10.** Для каждого action class его `round_result`, campaign event,
  stop reason и dispute snapshot образуют ровно допустимую комбинацию;
  неизвестные строки и ручная несовместимая комбинация отвергаются.
- **AC-11.** После реализации полный `./scripts/check.sh` зелёный, dependency
  set не изменён, а implementation diff ограничен `domain/review` и его тестами.

## 11. Риски и откат

| Риск | Ранний сигнал | Что делать | Граница отката |
|---|---|---|---|
| Counters сняты после записи текущего fix-check result, хотя API ожидает snapshot до неё | Первый вызов после `rev1` приходит как `review_check_count_before=2` вместо 1, sequence test смещён | Discovery-result сначала записывать как check 1; facts каждого последующего fix-check собирать до его result, затем закрывать round и писать event по возвращённому action одной транзакцией T1.7b | Меняется mapper/orchestration, pure domain API и DDL сохраняются |
| `review_check_count` случайно становится вторым лимитом | Решение меняется при том же author count только из-за check count либо clean блокируется | Оставить review count только во входной валидации/assert; branch cap использует исключительно author count | Откатить `transition.py` к таблично проверенной четырёхветочной версии |
| T1.4 начнёт вычислять severity или выбирать один из нескольких disputes | В domain появляются rank/threshold lookup или сортировка observations | Передавать уже выбранный snapshot из T1.6; в T1.4 проверять только наличие и приоритет human gate | Удаляется лишняя policy-логика, action/input types сохраняются |
| Human gate снова будет принят за terminal campaign | `AskHuman` возвращает `closed_escalated` либо test ожидает `closed_at` до ответа | Держать отдельные event `human_gate_opened` и `human_finalized`; первый — self-transition, второй — terminal | Исправляется state table без migration; согласованное решение записано в design baseline |
| Доменные типы начнут импортировать store DTO ради удобства | `metaswarm.domain.review` импортирует `metaswarm.store.repo` | Оставить структурно одинаковые, но независимые frozen facts; mapping тестируется в T1.7b | Откатывается только import/mapping, repository API не меняется |
| Недостижимый snapshot будет обработан как cap exhaustion | Негативный counter или dispute вне open set возвращает штатный `AskHuman` | Валидировать весь snapshot до первой decision branch и возвращать domain error | Изменение локально в input validation, persisted state не затронут |

## 12. Допущения и открытые вопросы

**Допущения:**

- T1.3 будет реализована без изменения смысла counters и IDs. Если текущий
  незакрытый round начнёт входить в `campaign_counters`, timing contract и оба
  плана возвращаются на ревью.
- T1.5 возвращает исход первичного круга независимо от типов T1.4, а для
  последующих `fix_check` возвращает domain contribution новых identities и
  links. T1.7b сохраняет contribution, затем отображает собранный open set в
  `CheckFacts`. Если T1.5 начнёт импортировать T1.4, это новое ребро графа и
  повод вернуть границы P1-A на совместное ревью.
- T1.6 предоставляет не более одного preselected escalating dispute на один
  вызов решения; политика выбора/агрегации нескольких споров принадлежит T1.6,
  а не скрывается в T1.4.
- Набор `open_findings` собирается после применения `verified_fixed`,
  `accepted_reason` и `policy_closed` текущей проверки; T1.4 не выводит status
  из reviewer decisions повторно.
- Внутренние IDs round/finding — положительные `int`; сравнение нового finding
  использует равенство `first_round_id == current_round_id`, не близость
  `round_no` и не текст finding'а.
- Общий package baseline P1-A фиксирует принятую версию планов. Для фактического
  scope реализации T1.4 левой границей служит более поздний closing commit
  принятой T1.3, записанный до первой правки T1.4.

**Открытые вопросы:** нет.
