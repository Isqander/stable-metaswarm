# **Анализ архитектурных подходов и инструментария для оркестрации гетерогенных CLI-агентов с графовым планированием**

Развитие систем автоматизированной разработки программного обеспечения на базе искусственного интеллекта переходит от парадигмы интерактивных ассистентов в среде разработки к созданию полностью автономных конвейеров, способных выполнять долгоживущие и многоэтапные задачи1. Ключевым барьером на пути к автономному проектированию является деградация рассуждений автономных агентов при раздувании контекстного окна3. По мере накопления истории диалога и промежуточных результатов работы модели теряют способность к точной логической адресации, пропускают критические инструкции и совершают деструктивные изменения в файловой системе5.  
Для преодоления контекстной аберрации и построения надежных производственных конвейеров требуется формирование управляющего слоя (Control Plane), сочетающего детерминированные внешние графы задач, изоляцию процессов через механизмы системы контроля версий, состязательные циклы перекрестной проверки (Peer Review) и асинхронные механизмы привлечения человека в контур управления (Human-in-the-Loop)7.

## **Архитектурные требования и системные вызовы автономной разработки**

### **Контекстная изоляция и механизм сброса рабочей памяти**

Архитектура многоагентной оркестрации требует полного разрыва контекстной истории при передаче управления между последовательными этапами исполнения3. Накопление полного трейса рассуждений приводит к квадратичному росту затрат на токены и логическому «зашумлению» модели5. Передача управления между агентами должна осуществляться через формирование компактного артефакта передачи — так называемого cut-off файла, содержащего сжатую сводку предыдущего этапа, линзы архитектурных решений и текущие диффы исходного кода3. В альтернативном режиме оркестратор передает следующему агенту исключительно сжатую постановку задачи, обеспечивая эффект «свежего взгляда» на проверяемый или дорабатываемый код4.

### **Графовое планирование задач на базе Beads**

Традиционные подходы к планированию, использующие плоские списки задач в формате Markdown (TASKS.md), демонстрируют неэффективность в многоагентных системах из\-за высокой вероятности возникновения гонок состояний, неспособности детерминированно отслеживать зависимости и некорректного редактирования одного файла несколькими агентами3.  
Проблема решается интеграцией ориентированных ациклических графов (DAG) через специализированные системы управления задачами, такие как Beads (bd), разработанная Стивом Егги6. Система Beads хранит источник правды в виде JSON-строк (issues.jsonl), версионируемых внутри Git-репозитория, а для высокоскоростной выборки использует локальный SQLite-кэш (beads.db)3. Механизм bd ready \--json выполняет топологическую сортировку задач и гарантирует, что агенты берут в работу только те узлы графа, для которых полностью завершены все блокирующие зависимости6.

### **Управление гетерогенными CLI-агентами и изоляция окружений**

Современный ландшафт инструментов разработки представлен широким спектром автономных CLI-агентов от различных вендоров: Anthropic Claude Code1, OpenAI Codex CLI1, OpenCode12, Aider1, Block Goose1 и Pi12. Каждая из этих систем имеет собственные паттерны автономии, системы вызова инструментов (MCP) и специфику оптимизации под конкретные семейств моделей1.  
Оркестратор должен управлять не вызовами API языковых моделей, а полноценными консольными процессами через псевдотерминальные интерфейсы (PTY) или системные обертки. Для предотвращения конфликтов во время параллельного исполнения задач оркестратор обязан изолировать рабочие пространства агентов, динамически создавая для каждой активной задачи изолированные Git Worktrees (.worktrees/bd-{ID})9.

### **Приостановка потоков исполнения и Human-in-the-Loop**

В процессе выполнения любого этапа — от формирования тех-дизайна до реализации кода — агент может столкнуться с неопределенностью, которую невозможно разрешить путем анализа имеющегося кода и документации. В этих случаях оркестратор должен автоматически выявлять формулировку открытого вопроса, приостанавливать выполнение конкретной ветки графа задач, сохранять её состояние и инициировать асинхронное уведомление ответственных лиц через внешние каналы связи (Telegram, Email, Webhook)8. При этом оркестратор сохраняет возможность продолжения параллельного исполнения тех веток графа задач, которые не зависят от заблокированного узла.

### **Детерминированные циклы рецензирования и каскадная эскалация**

Для обеспечения высокого качества артефактов (тех-дизайна, планов задач, исходного кода) в систему закладывается циклический процесс перекрестной проверки:

> * **Базовый цикл (А \<-\> Б)**: Исполнитель (Агент А) создает или модифицирует артефакт, после чего Рецензент (Агент Б) проводит критический анализ. В случае обнаружения замечаний Агент А либо вносит исправления, либо предоставляет мотивированный отказ. Процесс повторяется до получения явного подтверждения качества от Агента Б.  
> * **Порог эскалации**: Для предотвращения зацикливания количество итераций в цикле «А \<-\> Б» ограничено тремя прогонами. Если после третьего цикла Агент Б не выражает согласие, система блокирует автоматическое исполнение и передает задачу на рассмотрение человеку (Human Escalation)15.  
> * **Каскадное рецензирование (Б \<-\> В)**: Для критически важных или архитектурно сложных этапов после успешного завершения цикла «А \<-\> Б» запускается аналогичный цикл проверки между Агентом Б и Агентом В (например, узкоспециализированным агентом по безопасности или производительности)9.

## **Анализ современного ландшафта готовых решений и оркестраторов**

Рынок специализированных систем оркестрации AI-агентов в терминальном окружении пережил масштабное формирование на рубеже 2025–2026 годов1. Анализ доступных инструментов позволяет разделить их на готовые циклические оркестраторы и мультиагентные панели управления.

### **Специализированные циклические системы**

#### **Mala (Multi-Agent Loop Architecture)**

Открытая система Mala представляет собой специализированный оркестратор, созданный для автоматической обработки задач из графа Beads в циклическом режиме4. Mala поддерживает подключение гетерогенных бэкендов, включая Claude Code, Sourcegraph Amp и OpenAI Codex CLI4.  
Система автоматически запрашивает неблокированные задачи через bd ready \--json, запускает отдельный процесс CLI-агента с полной очисткой контекста для каждой задачи, проводит проверку через встроенные ворота качества (Quality Gates) и автоматически фиксирует результат в Git4.  
Главным ограничением Mala является её ориентированность на монолитный цикл «реализация \-\> коммит»4. В Mala отсутствуют встроенные механизмы для многопроходных ревью-петель A/B/C, проверки границ графов планирования и асинхронной приостановки потоков при возникновении открытых вопросов4.

#### **Conductor-Beads и Claude Protocol**

Комплексный шаблон Conductor-Beads объединяет методологию спецификаций Conductor с распределенной памятью Beads16. В свою очередь, архитектурный набор create-beads-orchestration (Claude Protocol) предлагает изготовительный каркас для оркестрации ролевых агентов (Архитектор, Детектив, Рецензент) с принудительной изоляцией в Git Worktrees (.worktrees/bd-{ID})9.  
Данные решения из коробки поддерживают этапность тех-дизайна, декомпозицию на эпики и последовательное распределение задач9. Однако они жестко привязаны к экосистеме Claude Code и используют текстовые хуки оболочки (Shell Hooks) для контроля дисциплины агентов, что затрудняет их адаптацию для управления CLI-инструментами других производителей, такими как OpenAI Codex CLI или OpenCode1.

### **Мультиагентные панели управления и рабочие пространства**

Инструменты категории визуальных и консольных диспетчеров рабочих пространств — Nimbalyst14, Pane17, Vibe Kanban14, Conductor от Melty Labs14 и CodeAgentSwarm17 — обеспечивают параллельный запуск различных CLI-агентов в изолированных окружениях Git Worktree14.  
Они эффективно решают проблему изоляции файловой системы и предотвращения конфликтов при одновременной работе нескольких агентов14. При этом данные платформы функционируют как пассивные контрольные панели, перекладывая задачу принятия решений о передаче управления, отслеживании циклов проверки и эскалации на человека-оператора14. Они не содержат программного движка для автоматической реализации сложных правил ветвления и многоэтапного состязательного рецензирования.

| Инструмент / Платформа | Интеграция с Beads DAG | Поддержка гетерогенных CLI | Циклы проверки (A/B/C) | Паузы и HITL-эскалация | Оценка объема необходимых доработок |
| :---- | :---- | :---- | :---- | :---- | :---- |
| **Mala** \[cite: 4\] | Нативная (bd ready)4 | Высокая (Claude, Codex, Amp)4 | Базовая (одноэтапный quality gate)4 | Отсутствует | Средний: требуется внешняя система управления состоянием для циклов A/B/C и паузы ветки. |
| **Conductor-Beads / Claude Protocol** \[cite: 9, 16\] | Полная нативная интеграция9 | Низкая (ориентировано на Claude Code)9 | Высокая (специализированные роли)9 | Частичная (через терминальный запрос)9 | Высокий: необходима переработка ядра для поддержки CLI-агентов сторонних вендоров. |
| **Nimbalyst / Pane / Vibe Kanban** \[cite: 14, 17\] | Косвенная (через визуализацию Worktrees)14 | Высокая (любые CLI-агенты)14 | Ручной контроль пользователем14 | Ручной выбор оператором14 | Высокий: требуют создания внешнего программного контроллера, управляющего их API. |

## **Сравнительный анализ SDK и фреймворков для создания кастомного оркестратора**

Ввиду отсутствия на рынке готового продукта, полностью удовлетворяющего всем элементам запрашиваемого конвейера, наиболее рациональным решением является сборка кастомного оркестратора на базе профильного фреймворка управления процессами.

### **ControlFlow и экосистема Prefect 3.0**

ControlFlow представляет собой специализированный Python-фреймворк с открытым исходным кодом, созданный компанией Prefect для управления структурированными агентными процессами8. Платформа специально спроектирована для решения проблемы ухода ИИ-агентов в неконтролируемые состояния за счет разбиения работы на дискретные, наблюдаемые задачи8.  
Архитектура ControlFlow предоставляет ключевые механизмы для реализации целевого конвейера:

> * **Транзакционная оркестрация и откат состояний**: Построение поверх ядра Prefect 3.0 обеспечивает транзакционную семантику8. Если агент в процессе выполнения задачи заходит в тупик или повреждает окружение, оркестратор выполняет автоматический откат рабочей директории и контекстной памяти агента к последней сохраненной чистой транзакции8.  
> * **Стратегии передачи управления (Turn Strategies)**: Встроенные механизмы Moderated, Delegation и Round-robin позволяют программно задавать правила взаимодействия агентов в циклах ревью (например, управляющий агент-модератор определяет, кому передать слово на этапе исправления)19.  
> * **Первоклассная поддержка Human-in-the-Loop**: Фреймворк включает нативные операторы приостановки процессов, позволяющие полностью замораживать граф исполнения задачи, сохранять состояние в базу данных и ожидать внешнего REST API вызова или вебхука от Telegram-бота8.

### **Альтернативные оркестрационные платформы**

#### **Temporal**

Temporal является промышленным стандартом для обеспечения надежного выполнения распределенных бизнес-процессов (Durable Execution). Платформа обеспечивает абсолютную надежность сохранения состояния workflows при сбоях инфраструктуры и поддерживает асинхронное ожидание внешних событий любой длительности.  
Однако Temporal не содержит специализированных абстракций для ИИ-агентов, манипуляции контекстами и интеграции с LLM. Использование Temporal потребует написания низкоуровневой обвязки для управления PTY-процессами CLI-агентов, парсинга их вывода и интеграции с Beads внутри Activity-функций.

#### **LangGraph**

LangGraph предоставляет широкие возможности для моделирования цикличных агентов в виде графов состояний. Инструмент отлично справляется с управлением вызовами API языковых моделей, но создавал существенные сложности при попытке управлять долгоживущими консольными процессами CLI-агентов, манипулировать файловой системой через Git Worktrees и обрабатывать локальные блокировки базы данных Beads.

#### **AutoGen v0.4**

Асинхронная событийно-ориентированная архитектура AutoGen v0.4 позволяет организовывать сложные многоагентные диалоги21. Однако фреймворк обладает избыточной сложностью при попытке принудительного ограничения автономии агентов детерминированными внешними правилами и требует написания сложного кода для координации вызовов CLI-инструментов в изолированных каталогах.

| Фреймворк / SDK | Управление CLI-процессами (PTY) | Графовые циклы и состояния | Приостановка и HITL | Транзакционные откаты (Rollback) | Сложность реализации оркестратора |
| :---- | :---- | :---- | :---- | :---- | :---- |
| **ControlFlow (Prefect 3.0)** \[cite: 8, 18\] | Средняя (через Python Subprocess / Pexpect) | Высокая (нативные абстракции задач)18 | Нативная (приостановка потока)8 | Нативная (транзакции Prefect 3.0)8 | **Низкая**: Оптимальный баланс готовых агентных абстракций и гибкости. |
| **Temporal** | Низкая (требует написания custom Activities) | Высокая (нативный State Machine Engine) | Промышленный стандарт (Signals) | Ручная реализация (Saga Pattern) | **Высокая**: Высокий порог входа и избыточность для локального CLI-конвейера. |
| **LangGraph** | Низкая (ориентирован на API-модели) | Высокая (StateGraph) | Нативная (Interrupt Nodes) | Ручная обработка состояний | **Средняя**: Требует большого объема кода для связи с CLI-инструментами. |
| **AutoGen v0.4** \[cite: 21\] | Средняя (через Runtime Agents)21 | Средняя (Event-Driven)21 | Средняя (асинхронные сообщения) | Отсутствует | **Высокая**: Сложность контроля детерминированных ограничений. |

## **Проектирование сквозного процесса разработки и управления задачами**

На основе анализа требований и возможностей ControlFlow и Beads формируется архитектура сквозного конвейера исполнения задач.

### **Фаза технического дизайна и разрешение неопределенностей**

Входная задача поступает на обработку Агенту-Архитектору. В случае высокой сложности исходного требования оркестратор автоматически декомпозирует задачу создания тех-дизайна на подзадачи. На данном этапе выполняется динамический анализ генерируемого текста на наличие открытых вопросов. При обнаружении маркерных конструкций оркестратор изолирует текущую ветку, переводит её в статус SUSPENDED и отправляет сообщение с контекстом вопроса в Telegram-канал аналитика. Исполнение независимых веток графа продолжается.  
После формирования проектного документа .designs/{EPIC\_ID}.md запускается детерминированный цикл проверки (п. 5):

> 1. **Агент А (Архитектор)** передает документ **Агенту Б (Техлид / Security)**.  
> 2. В случае наличия замечаний Агент А вносит исправления с полным сбросом истории диалога (получая на вход только проект и список замечаний).  
> 3. Процесс повторяется до получения статуса APPROVED, но не более 3 итераций. При превышении лимита инициируется Human Escalation.  
> 4. При высокой важности модуля утвержденный файл автоматически передается в аналогичный цикл проверки между **Агентом Б** и **Агентом В** (Principal Architect).

### **Фаза декомпозиции, формирования графа Beads и ревью границ**

После утверждения технического дизайна Агент-Планировщик формирует структурированный файл декомпозиции задач, который проходит аналогичный цикл проверки (А \<-\> Б). На основе утвержденного файла оркестратор программно вызывает команды bd create с заполнением граней зависимостей \--deps и указанием родительского эпика \--parent7.  
До начала реализации запускается этап скопового ревью (Boundary Review):

> * Оркестратор запрашивает полный граф задач командой bd list \--json7.  
> * Агент-Аудитор проверяет граф в целом на предмет дублирования функциональности, полноты покрытия требований тех-дизайна и отсутствия циклических блокировок.  
> * Граф корректируется до момента успешного прохождения цикла проверки границ.

### **Фаза параллельного исполнения и автоматизированного валидирования**

Оркестратор запускает постоянный цикл опроса состояния графа через команду bd ready \--json4. Для каждой возвращенной неблокированной задачи выполняются следующие шаги:

> 1. Создается изолированный каталог git worktree add .worktrees/bd-{ID} \-b feature/bd-{ID}9.  
> 2. Запускается целевой CLI-агент (Claude Code, OpenAI Codex CLI или OpenCode) в режиме чистой сессии1. На вход агенту подаются только описание конкретной задачи из Beads и утвержденный тех-дизайн10.  
> 3. По завершении работы Агента-Исполнителя запускается цикл проверки кода (А \<-\> Б)4.  
> 4. По завершении рецензирования Агент-Валидатор оценивает необходимость выполнения тестов (билд, деплой, вызовы API или прогон сценариев в Headless Browser).При необходимости оркестратор запускает тестовый скрипт. В случае провала тестов формируется отчет об ошибках, и задача возвращается в цикл исправления (А \<-\> Б) с последующим повторным прогоном тестирования.

### **Фаза перекрестного рецензирования и динамического устранения дефектов**

После того как все задачи графа переведены в статус CLOSED и слиты в основную ветку, запускается финальный этап сквозного аудита:

> * Оркестратор параллельно инициализирует нескольких независимых агентов-аудиторов с различными специализациями (Безопасность, Производительность, Архитектурная чистота).  
> * Если Агент-Аудитор А находит дефект в модуле, созданном Агентом Б, он создает новую задачу в Beads и напрямую назначает ее на Агента Б.  
> * Агент Б вносит исправления в изолированном Worktree, после чего результат направляется Агенту А для валидации.  
> * Параллельные потоки аудита функционируют независимо, обеспечивая разностороннюю проверку всей системы перед финальным релизом.

## **Заключение и стратегические рекомендации**

Проведенный анализ показывает, что ни одно из существующих на рынке готовых решений не закрывает полностью весь запрашиваемый функционал из коробки. Оптимальным инженерным путем является создание кастомного оркестратора с использованием правильного сочетания существующих управляющих фреймворков и инструментальных средств.

### **Стратегический выбор архитектурного стека**

> 1. **Базовый фреймворк оркестрации**: **ControlFlow (на базе Prefect 3.0)**8. Фреймворк предоставляет готовую структуру для управления задачами, контроля передач ходов, транзакционного отката состояний и нативной асинхронной приостановки потоков для реализации Human-in-the-Loop8.  
> 2. **Система управления памятью и графом задач**: **Beads (bd)**6. Обеспечивает детерминированное хранение DAG-структур задач в Git, исключает гонки состояний и предоставляет идеальный JSON-интерфейс для работы оркестратора6.  
> 3. **Исполнительный слой**: Кастомный модуль-адаптер на Python (с использованием asyncio.subprocess или pexpect), обеспечивающий запуск гетерогенных CLI-агентов (Claude Code, OpenAI Codex CLI, OpenCode, Aider) в изолированных каталогах Git Worktrees1.  
> 4. **Интеграционный слой уведомлений**: Telegram Bot API / Webhooks, подключенные к точкам останова ControlFlow для мгновенной доставки открытых вопросов аналитикам и получения ответов без сброса состояния оркестратора8.

Данный подход обеспечивает создание масштабируемой, устойчивой к сбоям и независимой от конкретных вендоров системы автоматической разработки, полностью удовлетворяющей всем предъявленным функциональным требованиям.
